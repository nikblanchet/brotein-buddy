# Accessibility Implementation: WCAG 2.1 AA Compliance

This document explains how we made BroteinBuddy accessible to users with disabilities, achieving WCAG 2.1 AA compliance and Lighthouse Accessibility scores of 95+.

## What We Built

Phase 3.3 added comprehensive accessibility features to BroteinBuddy:

- ARIA live regions for loading states and errors
- Skip-to-main-content link for keyboard navigation
- Dynamic page titles for screen readers
- Visible form labels for all inputs
- Color contrast improvements (WCAG AA compliant)
- 60+ automated accessibility tests with @axe-core/playwright

The result: an app that works for everyone, regardless of how they interact with technology.

## Why This Approach

### Understanding WCAG Levels

WCAG (Web Content Accessibility Guidelines) has three conformance levels:

**Level A (Minimum):**

- Most basic accessibility features
- Severe barriers removed
- Example: All images have alt text

**Level AA (Recommended):**

- Addresses major accessibility barriers
- Legally required in many jurisdictions
- Example: Color contrast ratio of 4.5:1 for normal text
- **This is what we target**

**Level AAA (Enhanced):**

- Highest level of accessibility
- Not always achievable for all content
- Example: Color contrast ratio of 7:1 for normal text

**Why we chose AA:**

- Industry standard for web applications
- Balances accessibility with development effort
- Legally compliant in most jurisdictions (ADA, AODA, EAA)
- AAA is often overkill for utility apps (very strict requirements)

### The Problem We Solved

Without accessibility features, BroteinBuddy would be unusable for:

- **Screen reader users** (blind or low vision) - can't see the screen
- **Keyboard-only users** (motor disabilities) - can't use a mouse
- **Users with color blindness** - can't distinguish colors alone
- **Users with cognitive disabilities** - need clear structure and labels

That's not acceptable. If we're building software, it should work for EVERYONE.

### Options We Considered

#### Option 1: Manual ARIA Implementation

**How it works:** Manually add ARIA attributes (`aria-label`, `aria-live`, etc.) to components as needed.

**Pros:**

- Full control over accessibility
- No dependencies
- Lightweight (no library overhead)

**Cons:**

- Easy to miss patterns
- Requires deep WCAG knowledge
- No automated verification
- Inconsistent implementation across team

**Why we chose this:** BroteinBuddy is small enough that manual implementation is manageable, and we added automated tests to catch violations.

#### Option 2: Accessible Component Library (Radix UI, React Aria)

**How it works:** Use pre-built components with accessibility baked in.

**Pros:**

- Accessibility handled by experts
- Battle-tested patterns
- Consistent implementation

**Cons:**

- Not compatible with Svelte 5
- Adds significant bundle size (50-100 KB)
- Less control over implementation
- May not match design system

**Why we didn't choose it:** Svelte 5 ecosystem lacks mature accessible component libraries. We'd rather build accessible components ourselves than compromise on framework choice.

#### Option 3: Skip Accessibility (Anti-Pattern)

**How it works:** Ship without accessibility features, "fix it later."

**Pros:**

- Faster initial development
- Fewer lines of code

**Cons:**

- Excludes users with disabilities (unethical)
- Legal risk (ADA lawsuits)
- Harder to retrofit later (accessibility should be built-in)
- Fails Lighthouse audits

**Why we didn't choose it:** Accessibility is not optional. It's the right thing to do, and it makes the app better for EVERYONE (not just users with disabilities).

## How It Works

### 1. ARIA Live Regions for Dynamic Content

**The Problem:** Screen readers don't automatically announce content changes. If a loading spinner appears or an error shows, screen reader users don't know.

**The Solution:** ARIA live regions announce changes as they happen.

#### Polite Announcements (Non-Urgent)

Use `aria-live="polite"` for status updates that don't require immediate attention:

```svelte
<!-- Random.svelte - Loading state -->
<div role="status" aria-live="polite">
  {#if isLoading}
    <div class="spinner" aria-hidden="true"></div>
    <p>Selecting random flavor...</p>
  {/if}
</div>
```

**What this does:**

- `role="status"` indicates a status update
- `aria-live="polite"` tells screen readers to announce when convenient (after current speech)
- Spinner has `aria-hidden="true"` because it's decorative (the text provides the information)

**Screen reader behavior:**

- User triggers random selection
- Screen reader says: "Selecting random flavor..."
- When selection completes, screen reader announces the result

#### Assertive Announcements (Urgent)

Use `aria-live="assertive"` for errors that require immediate attention:

```svelte
<!-- InventoryBoxEdit.svelte - Error state -->
{#if error}
  <div role="alert" aria-live="assertive" class="error-message">
    {error}
  </div>
{/if}
```

**What this does:**

- `role="alert"` indicates an important message
- `aria-live="assertive"` interrupts current speech to announce immediately
- Red styling provides visual indicator (but ARIA provides the semantic meaning)

**Screen reader behavior:**

- User submits invalid form
- Screen reader IMMEDIATELY says: "Error: Quantity must be between 1 and 12"
- User knows what went wrong before continuing

#### Common Mistake: Adding Live Regions Dynamically

**Wrong:**

```svelte
{#if error}
  <div role="alert" aria-live="assertive">{error}</div>
{/if}
```

**Problem:** Live regions must exist in the DOM BEFORE content changes. If you create the `<div>` at the same time as the content, screen readers might miss it.

**Right:**

```svelte
<!-- Always present, even when empty -->
<div role="alert" aria-live="assertive">
  {#if error}
    {error}
  {/if}
</div>
```

**Why:** Screen readers monitor existing live regions for changes. If the region is created dynamically, there's no guarantee it will be announced.

### 2. Skip-to-Main-Content Link

**The Problem:** Keyboard users have to Tab through ALL navigation links on EVERY page just to reach the main content. Imagine pressing Tab 20 times every time you load a page.

**The Solution:** A skip link that jumps directly to main content.

```svelte
<!-- App.svelte -->
<a href="#main-content" class="skip-link">Skip to main content</a>

<main id="main-content">
  <Router {routes} />
</main>

<style>
  .skip-link {
    position: absolute;
    top: -40px; /* Hidden off-screen */
    left: 0;
    background: var(--color-primary);
    color: var(--color-text-inverse);
    padding: var(--space-2) var(--space-4);
    z-index: 100;
  }

  .skip-link:focus {
    top: 0; /* Visible when focused */
  }
</style>
```

**What this does:**

- Link is visually hidden by default (positioned off-screen)
- When user presses Tab (first thing after page load), skip link becomes visible
- Clicking it jumps focus to `<main id="main-content">`
- Keyboard users save 10-20 Tab presses per page

**Why not just hide it with `display: none`?**

- `display: none` removes the element from the accessibility tree
- Screen readers wouldn't announce it
- Keyboard users couldn't focus it
- Visual off-screen positioning keeps it accessible while hidden

### 3. Dynamic Page Titles

**The Problem:** Single-page applications (SPAs) don't update the browser's page title when navigating. Screen readers announce "BroteinBuddy" for EVERY page, giving no indication of where you are.

**The Solution:** Reactively update `document.title` based on route.

```svelte
<!-- App.svelte -->
<script lang="ts">
  import { location } from 'svelte-spa-router';

  const pageTitles: Record<string, string> = {
    '/': 'Home',
    '/random': 'Random Selection',
    '/random/confirm': 'Confirm Selection',
    '/inventory': 'Inventory',
    '/inventory/rearrange': 'Rearrange Inventory',
  };

  $effect(() => {
    const currentPath = $location;
    let title = 'BroteinBuddy';

    if (currentPath in pageTitles) {
      title = `${pageTitles[currentPath]} - BroteinBuddy`;
    } else if (currentPath.startsWith('/inventory/') && currentPath.endsWith('/edit')) {
      title = 'Edit Box - BroteinBuddy';
    }

    document.title = title;
  });
</script>
```

**What this does:**

- Svelte 5's `$effect` watches for route changes
- Updates `document.title` to match current page
- Screen readers announce: "Home - BroteinBuddy" or "Inventory - BroteinBuddy"

**Why this matters:**

- Screen readers announce page title on navigation
- Browser tabs show current page
- Browser history is more useful
- Users know where they are in the app

**WCAG Criterion:** 2.4.2 Page Titled (Level A)

### 4. Visible Form Labels

**The Problem:** Placeholder text is NOT a substitute for labels. Screen readers don't announce placeholders consistently, and placeholders disappear when you start typing.

**Wrong:**

```svelte
<!-- Bad: No label -->
<input type="number" placeholder="Enter quantity" />
```

**Right:**

```svelte
<!-- Good: Visible label -->
<label for="quantity-input" class="form-label"> Quantity </label>
<input id="quantity-input" type="number" />
```

**Even Better (with context):**

```svelte
<!-- InventoryBoxEdit.svelte -->
<label id="add-quantity-label" class="numberpad-label">
  Select number of bottles to add (current: {box.quantity}):
</label>
<NumberPad max={12} onselect={handleAddQuantitySelect} ariaLabelledBy="add-quantity-label" />
```

**What this does:**

- Label is ALWAYS visible (doesn't disappear when typing)
- Label is associated with the control via `id` and `ariaLabelledBy`
- Screen reader announces: "Select number of bottles to add, current 5"
- User knows exactly what they're entering and the current value

**WCAG Criterion:** 3.3.2 Labels or Instructions (Level A)

### 5. Color Contrast

**The Problem:** Low contrast text is hard to read for users with low vision or color blindness. Our original design had secondary text at `opacity: 0.6` (~4.6:1 contrast), just below the WCAG AA threshold of 4.5:1.

**The Solution:** Increase opacity to meet minimum contrast ratios.

```css
/* Before (4.6:1 contrast) */
--color-text-secondary: rgba(0, 0, 0, 0.6);

/* After (5.0:1 contrast) - WCAG AA compliant */
--color-text-secondary: rgba(0, 0, 0, 0.65);
```

**Minimum contrast requirements (WCAG AA):**

- Normal text: 4.5:1
- Large text (18pt+ or 14pt bold+): 3:1
- UI components: 3:1

**How we fixed multiple contrast violations:**

1. **Primary button color:** Darkened from `#4F46E5` to `#4d54df` (4.53:1)
2. **Danger button color:** Darkened from `#EF4444` to `#dc2626` (4.51:1)
3. **Secondary text:** Increased from `0.6` to `0.65` opacity (5.0:1)
4. **Badge colors:** Used semantic color system with sufficient contrast:

```css
/* Status badges with contrasting foreground/background */
--color-success-bg: #dcfce7; /* Light green background */
--color-success-dark: #15803d; /* Dark green text (6.2:1 contrast) */
```

**Special case: Dynamic box colors on Rearrange screen**

The visual inventory uses flavor colors for boxes. Problem: Flavor colors are user-configurable and might have low contrast.

**Solution:** Semi-transparent dark background provides contrast floor:

```css
.box-label {
  background: rgba(0, 0, 0, 0.6); /* Semi-transparent dark overlay */
  color: white; /* Always sufficient contrast */
  padding: var(--space-2);
  border-radius: var(--radius-sm);
}
```

**How this works:**

- Flavor color shows through as the box background
- Text sits on dark overlay, ensuring readability
- User sees their flavor color + readable text
- Works with ANY background color

**WCAG Criterion:** 1.4.3 Contrast Minimum (Level AA)

### 6. Strategic Deferral: When to Skip Advanced Features

**We deferred 2D keyboard navigation for the visual inventory grid.**

**Why?**

- **Complexity:** Arrow key navigation through a 2D grid is complex (up/down/left/right, edge wrapping, focus management)
- **Alternative exists:** Table view provides full keyboard access to ALL inventory features
- **Usage:** Visual grid is mouse/touch-optimized; power users prefer table view anyway
- **Time:** Implementing 2D nav would delay shipping by 1-2 weeks for a feature few users would use

**How we made this decision:**

1. Identified the gap (visual grid not keyboard accessible)
2. Verified an accessible alternative exists (table view)
3. Confirmed the alternative provides equivalent functionality
4. Documented the limitation in ADR-008
5. Created issue #68 to track future enhancement
6. Skipped related E2E tests with clear comments

**This is PRAGMATIC accessibility:**

- We didn't ship an inaccessible feature
- We provided an accessible alternative
- We documented the limitation
- We can enhance later if users request it

**WCAG allows this:** If you provide an accessible alternative that offers equivalent functionality, you can defer advanced patterns.

## Common Accessibility Patterns

### Pattern 1: Loading States

```svelte
<div role="status" aria-live="polite">
  {#if isLoading}
    <span class="spinner" aria-hidden="true"></span>
    <p>Loading...</p>
  {/if}
</div>
```

**When to use:**

- Async operations (API calls, random selection)
- Background processing
- Progress indicators

**When to avoid:**

- Instant operations (< 100ms)
- Decorative animations

### Pattern 2: Error Messages

```svelte
<div role="alert" aria-live="assertive">
  {#if error}
    <p>{error}</p>
  {/if}
</div>
```

**When to use:**

- Form validation errors
- API failures
- User-triggered errors

**When to avoid:**

- Info messages (use `aria-live="polite"`)
- Non-critical warnings

### Pattern 3: Modal Dialogs

```svelte
<div role="dialog" aria-modal="true" aria-labelledby="modal-title">
  <h2 id="modal-title">Confirm Action</h2>
  <!-- Modal content -->
</div>
```

**When to use:**

- Confirmation prompts
- Forms in overlays
- Critical interruptions

**When to avoid:**

- Non-modal overlays (tooltips, popovers)

### Pattern 4: Custom Controls

```svelte
<div role="group" aria-labelledby="label-id">
  <div id="label-id">Select quantity:</div>
  <!-- Custom control (NumberPad) -->
</div>
```

**When to use:**

- Custom components without native HTML equivalents
- Grouped form controls

**When to avoid:**

- Native HTML controls exist (`<select>`, `<input>`, `<button>`)

## Testing Strategies

### 1. Automated Testing with @axe-core/playwright

We added 60+ automated accessibility tests:

```typescript
import AxeBuilder from '@axe-core/playwright';

test('should not have accessibility violations', async ({ page }) => {
  await page.goto('/');

  const accessibilityScanResults = await new AxeBuilder({ page }).analyze();

  expect(accessibilityScanResults.violations).toEqual([]);
});
```

**What this catches:**

- Missing ARIA labels
- Color contrast violations
- Improper heading hierarchy
- Missing alt text
- Form label associations

**What this DOESN'T catch:**

- Keyboard navigation flow (manual testing required)
- Screen reader announcements (manual testing required)
- Logical tab order (automated tools can't determine "logical")

### 2. Manual Testing with Screen Readers

**VoiceOver (macOS/iOS):**

```bash
# Enable VoiceOver
Cmd + F5

# Navigate
Ctrl + Option + Arrow Keys

# Interact with elements
Ctrl + Option + Space
```

**Testing checklist:**

- Can you navigate the entire app without seeing the screen?
- Are buttons and links announced correctly?
- Do loading states announce?
- Do errors announce immediately?
- Can you complete all workflows (add box, random selection, etc.)?

### 3. Keyboard-Only Testing

**Remove your mouse. Navigate using only:**

- Tab (next element)
- Shift + Tab (previous element)
- Enter (activate button/link)
- Space (activate button, toggle checkbox)
- Escape (close modal)

**Testing checklist:**

- Can you reach every interactive element?
- Is the tab order logical?
- Are focus indicators visible?
- Can you close modals with Escape?
- Can you submit forms with Enter?

### 4. Lighthouse Audits

```bash
# Run Lighthouse in Chrome DevTools
1. Open DevTools (F12)
2. Navigate to "Lighthouse" tab
3. Select "Accessibility" category
4. Click "Generate report"
```

**What to look for:**

- Accessibility score: 90+ (we achieved 95+)
- Zero violations
- Passed audits: ARIA attributes, color contrast, labels

## Design Trade-offs

### What We Optimized For

1. **WCAG AA compliance**: Industry standard, legally sound
2. **Screen reader compatibility**: Full announcements, logical structure
3. **Keyboard navigation**: All features accessible via keyboard (with documented exception for visual grid)
4. **Automated testing**: 60+ tests prevent regressions
5. **Incremental improvement**: Ship with accessible alternatives, enhance over time

### What We Sacrificed

1. **WCAG AAA compliance**: Not required, very strict (7:1 contrast, sign language videos, etc.)
2. **2D keyboard navigation**: Deferred to issue #68, table view provides alternative
3. **Perfect Lighthouse score**: 95+ is excellent; chasing 100 has diminishing returns
4. **Development velocity**: Accessibility adds 20-30% time to feature work

### When to Defer Features

**Defer if:**

- Accessible alternative exists with equivalent functionality
- Feature is infrequently used (< 5% of users)
- Implementation complexity is high (> 1 week)
- No legal/ethical barriers (e.g., don't defer form labels)

**Don't defer if:**

- Feature is core workflow (home screen, primary navigation)
- No accessible alternative exists
- Legal requirement (WCAG A/AA standards)
- Affects user data input or safety

## Real-World Compromises

### Contrast: AA vs AAA

We chose **WCAG AA (4.5:1 for normal text)** instead of **AAA (7:1)**.

**Why AA is enough:**

- 4.5:1 is readable for most users with low vision
- 7:1 severely limits color palette (very dark text on light bg, very light text on dark bg)
- AA is legally compliant in US (ADA), Canada (AODA), EU (EAA)
- Can always increase contrast later if users request it

**When to use AAA:**

- Medical applications (critical information)
- Government services (required by law in some jurisdictions)
- Text-heavy applications (news, documentation)

### Manual ARIA vs Component Libraries

We manually implemented ARIA attributes instead of using accessible component libraries.

**Trade-off:**

- More work upfront (understanding WCAG, testing patterns)
- Smaller bundle size (no library overhead)
- Full control over implementation
- Risk of missing patterns (mitigated with automated tests)

**When component libraries make sense:**

- Large team (consistency matters)
- Complex components (date pickers, autocompletes)
- Framework with mature ecosystem (React, not Svelte 5)

### CI/CD Time: Comprehensive vs Fast

Adding accessibility tests increased CI/CD time from ~5 minutes to ~8-10 minutes.

**Why we accepted this:**

- Accessibility regressions are hard to catch manually
- Automated tests prevent shipping inaccessible features
- 3-5 minute increase is acceptable for quality assurance
- Can optimize later (parallel test execution, sharding)

## What You Should Learn From This

### 1. Accessibility is Not Optional

**Pattern:** Build accessibility in from the start.

**Why:** Retrofitting accessibility is 3-5x harder than building it in. ARIA attributes, keyboard navigation, and labels should be part of every component from day one.

**How:**

- Use semantic HTML (`<button>`, `<nav>`, `<main>`)
- Add ARIA attributes when creating components
- Test with keyboard and screen reader during development
- Run automated accessibility tests in CI/CD

### 2. Automated Tests Catch 60-80% of Issues

**Pattern:** Use @axe-core for automated accessibility testing.

```typescript
import AxeBuilder from '@axe-core/playwright';

const results = await new AxeBuilder({ page }).analyze();
expect(results.violations).toEqual([]);
```

**Why:** Manual testing is time-consuming and inconsistent. Automated tests catch common violations (missing labels, low contrast, improper ARIA) on every commit.

**Limitations:** Automated tests can't verify keyboard navigation flow, screen reader announcements, or logical tab order. You still need manual testing.

### 3. ARIA Live Regions for Dynamic Content

**Pattern:** Use `aria-live="polite"` for status updates, `aria-live="assertive"` for errors.

```svelte
<!-- Status updates -->
<div role="status" aria-live="polite">
  {#if isLoading}Loading...{/if}
</div>

<!-- Errors -->
<div role="alert" aria-live="assertive">
  {#if error}{error}{/if}
</div>
```

**When to use:**

- Loading states
- Error messages
- Success confirmations
- Dynamic content changes (search results, notifications)

**When to avoid:**

- Static content (doesn't change)
- Decorative elements
- Content that changes > 1/second (too noisy)

### 4. Color Contrast Tools

**Pattern:** Use contrast checkers during design.

**Tools:**

- [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/)
- Chrome DevTools (Inspect element → Accessibility pane)
- [Coolors Contrast Checker](https://coolors.co/contrast-checker)

**Workflow:**

1. Designer picks colors
2. Check contrast ratio (4.5:1 for normal text, 3:1 for large/UI)
3. If below threshold, darken foreground or lighten background
4. Verify in browser with DevTools

### 5. Skip Links are Easy Wins

**Pattern:** Always add a skip-to-main-content link.

```svelte
<a href="#main-content" class="skip-link">Skip to main content</a>

<main id="main-content">
  <!-- App content -->
</main>

<style>
  .skip-link {
    position: absolute;
    top: -40px;
    left: 0;
  }

  .skip-link:focus {
    top: 0;
  }
</style>
```

**Why:** Keyboard users save 10-20 Tab presses per page. Takes 5 minutes to implement, huge UX improvement.

### 6. Strategic Deferral with Alternatives

**Pattern:** If a feature is complex to make accessible, provide an accessible alternative.

**Example:** We deferred 2D keyboard navigation for the visual inventory grid, but table view provides equivalent functionality.

**When to use:**

- Advanced pattern requires > 1 week of work
- Accessible alternative exists
- Feature is infrequently used
- Document the limitation and track enhancement

**When NOT to use:**

- Core feature (home screen, primary navigation)
- No alternative exists
- Legal/ethical requirement (form labels, contrast)

## Questions to Think About

1. **When is WCAG AAA worth the effort?** What types of applications justify 7:1 contrast and enhanced audio descriptions?

2. **How would you test with users who have disabilities?** Automated tests catch 60-80% of issues, but real users find the rest. How do you recruit testers?

3. **What if your design system conflicts with accessibility?** Designers want thin fonts and subtle colors. How do you balance aesthetics with contrast requirements?

4. **Should accessibility be part of "Definition of Done"?** If yes, how do you enforce it (checklists, automated tests, manual QA)?

5. **How do you prioritize accessibility work?** If you have limited time, which WCAG criteria are most critical? (Hint: Start with Level A, then AA for high-traffic features.)
