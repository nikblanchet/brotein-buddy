## Introduction

The Individual Box Edit Screen is the primary interface for managing boxes in the BroteinBuddy inventory system. It provides comprehensive CRUD (Create, Read, Update, Delete) operations for individual boxes, including quantity adjustments, location changes with conflict resolution, open/closed status toggling, and box deletion.

This feature is notable for several reasons:

1. **Shared utility design** - Location validation logic was extracted into a reusable utility (`location-validation.ts`) that will be shared with Task 2.7 (box creation/addition)
2. **Complex modal orchestration** - Seven different modals handle all user interactions, preventing accidental data loss
3. **Sophisticated conflict resolution** - When location conflicts occur, users can choose to swap or displace boxes
4. **Comprehensive E2E testing** - 50 E2E tests ensure all user flows work correctly across desktop and mobile

## What We Built

The Individual Box Edit Screen allows users to:

1. **View box details** - Displays flavor name, quantity, location (stack/height), and open/closed status
2. **Add quantity** - Uses NumberPad to add 1-12 bottles, validates max 12 per box
3. **Remove quantity** - Uses NumberPad to remove bottles, auto-prompts to delete if quantity reaches 0
4. **Change location** - Allows moving box to new stack/height with conflict detection and resolution
5. **Toggle open/closed** - One-click toggle of box status (used by random selection algorithm)
6. **Delete box** - Manual deletion with confirmation

All operations validate against business rules:

- Maximum 12 bottles per box
- No negative quantities
- No gaps in stacks (stack N requires stacks 1..N-1)
- No gaps in heights (height H requires heights 1..H-1)
- No floating boxes (each box must rest on ground or another box)

When location conflicts occur, users choose between:

- **Swap** - Trade locations with the conflicting box
- **Displace** - Move conflicting box to orphaned state (stack 0, height 0)
- **Cancel** - Abort the location change

## Key Design Decisions

### 1. Why Extract location-validation.ts as a Shared Utility?

**The Problem:**

Task 2.6 (box edit) and Task 2.7 (box add/create) both need identical location validation logic. Duplicate code would lead to maintenance issues and potential inconsistencies.

**The Solution:**

Extract all location validation into a standalone utility module:

```typescript
// src/lib/utils/location-validation.ts

export function validateLocationNoGaps(
  stack: number,
  height: number,
  allBoxes: Box[],
  excludeBoxId?: string
): { isValid: boolean; error?: string };

export function getLocationConflict(
  stack: number,
  height: number,
  allBoxes: Box[],
  excludeBoxId?: string
): Box | null;

export function formatLocation(stack: number, height: number): string;

// Plus: getValidLocations(), suggestNextLocation(), canSwapLocations()
```

**Why This Design?**

1. **Single source of truth** - One implementation of "no gaps" rule
2. **Reusable across features** - Both 2.6 and 2.7 can import the same logic
3. **Easier to test** - Pure functions with no component dependencies
4. **Future-proof** - When rules change, update in one place

**What Goes in the Utility vs Component?**

**Utility (Pure Logic):**

- Validation rules (no gaps, positive integers)
- Conflict detection (is location occupied?)
- Helper functions (formatLocation, getValidLocations)
- Pure functions with no side effects

**Component (UI Logic):**

- Modal state management
- User interaction handling
- Conflict resolution strategy (swap vs displace)
- State updates via stores
- Error message display

This separation keeps the utility testable and reusable while keeping UI concerns in the component.

### 2. Why Modal-Based UI for All Actions?

**Alternative Approaches Considered:**

1. **Inline editing** - Edit quantity directly in text fields
2. **Immediate actions** - Click +/- buttons to change quantity without confirmation
3. **Mixed approach** - Modals for some actions, inline for others

**Why We Chose Modal-Based Workflow:**

Every action (add, remove, change location, delete) uses a modal:

```svelte
<!-- Add Quantity Modal -->
<Modal open={showAddQuantityModal} title="Add Quantity">
  <NumberPad max={12} onselect={handleAddQuantitySelect} />
  <Button onclick={handleConfirmAddQuantity}>Confirm</Button>
  <Button onclick={handleCancelQuantityChange}>Cancel</Button>
</Modal>
```

**Advantages:**

1. **Prevents accidental changes** - Explicit confirm/cancel for every operation
2. **Consistent UX** - Same pattern for all actions (user learns once)
3. **Clear focus** - Modal dims background, focuses attention on current task
4. **Mobile-friendly** - Large touch targets, full-screen on mobile
5. **Validation happens before commit** - Can show errors in modal context

**Trade-offs:**

- **More clicks required** - Each change needs open modal → select → confirm
- **Not ideal for bulk operations** - Would want inline editing for many changes at once
- **Modal fatigue** - Too many modals can frustrate power users

**Why This Trade-off Makes Sense:**

BroteinBuddy is a utility app for personal use, not a professional inventory system. Users typically:

- Make one or two changes per session
- Want to avoid mistakes (destructive operations like delete)
- Use on mobile where modals are natural

For future bulk operations, we could add an "Edit Mode" that enables inline editing for multiple boxes simultaneously.

### 3. Why Check Conflicts Before Validation?

**Critical Implementation Detail:**

In `handleConfirmLocationChange()`, we check for conflicts BEFORE validation:

```typescript
function handleConfirmLocationChange() {
  if (!box || newStack === null || newHeight === null) return;

  // STEP 1: Check for conflicts FIRST
  const conflict = getLocationConflict(newStack, newHeight, $appState.boxes, boxId);
  if (conflict) {
    // Show conflict resolution modal
    showConflictModal = true;
    return;
  }

  // STEP 2: Validate location ONLY if no conflict
  const validation = validateLocationNoGaps(newStack, newHeight, $appState.boxes, boxId);
  if (!validation.isValid) {
    locationError = validation.error;
    return;
  }

  // STEP 3: Update location
  updateBoxLocation(boxId, { stack: newStack, height: newHeight });
}
```

**Why This Order Matters:**

If we validated first and then checked conflicts, we'd reject valid moves that could be resolved via swap or displace.

**Example Scenario:**

```
Current state:
- Box A at (1,1)
- Box B at (1,2)

User wants to move Box A to (1,2) (currently occupied by Box B)
```

**If we validate first:**

1. Location (1,2) is occupied → conflict exists
2. But validation passes (no gaps)
3. We'd show error: "Location occupied"
4. User is stuck - can't use (1,2) even though swap could work

**By checking conflicts first:**

1. Detect conflict with Box B at (1,2)
2. Show conflict resolution options: Swap or Displace
3. If user chooses Swap:
   - Box A moves to (1,2)
   - Box B moves to (1,1)
   - No gaps created, both boxes happy
4. If user chooses Displace:
   - Box A moves to (1,2)
   - Box B moves to (0,0) - orphaned
   - User can manually relocate Box B later

**The Key Insight:**

Conflict resolution (swap/displace) can **resolve** gap issues that would otherwise fail validation. By checking conflicts first, we give users the tools to fix their own problems.

## Location Validation Utility (Shared Logic)

### The "No Gaps" Rule

The core business rule: inventory must have no gaps in stacks or heights.

**Stack Rule:**

- Stack N requires non-empty stacks 1 through N-1
- Can't have Stack 3 if Stack 2 is empty
- Prevents: `[Stack 1] [Empty] [Stack 3]`

**Height Rule:**

- Height H in a stack requires heights 1 through H-1 in that stack
- Can't have height 3 if height 2 doesn't exist
- Prevents floating boxes

### Core Functions

#### validateLocationNoGaps()

Validates a proposed location against the no-gaps rule:

```typescript
export function validateLocationNoGaps(
  stack: number,
  height: number,
  allBoxes: Box[],
  excludeBoxId?: string
): { isValid: boolean; error?: string } {
  // Filter out the box being moved (if any)
  const boxes = excludeBoxId ? allBoxes.filter((b) => b.id !== excludeBoxId) : allBoxes;

  // Validate positive integers
  if (stack < 1 || !Number.isInteger(stack)) {
    return { isValid: false, error: 'Stack must be a positive integer' };
  }
  if (height < 1 || !Number.isInteger(height)) {
    return { isValid: false, error: 'Height must be a positive integer' };
  }

  // Check for gaps in stacks (stack N requires stacks 1..N-1)
  if (stack > 1) {
    const requiredStacks = new Set(Array.from({ length: stack - 1 }, (_, i) => i + 1));
    const occupiedStacks = new Set(boxes.map((b) => b.location.stack));

    for (const requiredStack of requiredStacks) {
      if (!occupiedStacks.has(requiredStack)) {
        return {
          isValid: false,
          error: `Stack ${stack} requires non-empty stack ${requiredStack}`,
        };
      }
    }
  }

  // Check for gaps in heights within this stack
  if (height > 1) {
    const boxesInStack = boxes.filter((b) => b.location.stack === stack);
    const occupiedHeights = new Set(boxesInStack.map((b) => b.location.height));

    for (let requiredHeight = 1; requiredHeight < height; requiredHeight++) {
      if (!occupiedHeights.has(requiredHeight)) {
        return {
          isValid: false,
          error: `Height ${height} in stack ${stack} requires height ${requiredHeight}`,
        };
      }
    }
  }

  return { isValid: true };
}
```

**Why excludeBoxId Parameter?**

When moving a box, we need to validate the destination as if the box **doesn't exist** at its current location. Otherwise, the box would validate against itself and potentially fail.

**Example:**

```
Moving Box A from (1,2) to (2,1):
- Without excludeBoxId: (2,1) validation would see Box A at (1,2), potentially creating issues
- With excludeBoxId='boxA': (2,1) validation ignores Box A's current position
```

#### getLocationConflict()

Finds a box occupying the target location:

```typescript
export function getLocationConflict(
  stack: number,
  height: number,
  allBoxes: Box[],
  excludeBoxId?: string
): Box | null {
  const boxes = excludeBoxId ? allBoxes.filter((b) => b.id !== excludeBoxId) : allBoxes;

  return boxes.find((b) => b.location.stack === stack && b.location.height === height) || null;
}
```

Simple but crucial: Returns the conflicting box if one exists, null otherwise.

#### Helper Functions

**formatLocation()** - Human-readable location strings:

```typescript

```

**getValidLocations()** - All currently valid locations (for Task 2.7):

```typescript
// Returns: [{ stack: 1, height: 3 }, { stack: 2, height: 2 }, { stack: 3, height: 1 }]
```


## InventoryBoxEdit Component Deep Dive

### Route Params and Derived State

**Svelte 5 Pattern:**

```typescript
// Extract route params
const { params = {} }: { params?: Record<string, string> } = $props();
const boxId = params.boxId || '';

// Derived state (auto-updates when appState changes)
const box = $derived($appState.boxes.find((b) => b.id === boxId));
const flavor = $derived(box ? maybeGetFlavor(box.flavorId, $appState.flavors) : null);
const boxColor = $derived(box && flavor ? getFlavorColor(flavor.id) : '#cccccc');
```

**Why $derived?**

Svelte 5's `$derived` creates reactive computed values:

- Automatically re-computes when dependencies change
- More performant than `$:` reactive statements
- Type-safe and explicit

When `$appState` updates (e.g., after quantity change), `box`, `flavor`, and `boxColor` automatically update.

### Modal State Management

**Seven modals, seven state variables:**

```typescript
let showAddQuantityModal = $state(false);
let showRemoveQuantityModal = $state(false);
let showLocationModal = $state(false);
let showDeleteConfirmModal = $state(false);
let showConflictModal = $state(false);

```

**Why separate state for each modal?**

- Explicit control over which modal is visible
- Easy to track in React DevTools / Svelte DevTools
- No complex state machine needed
- Each modal can have its own onclose handler

**Alternative Approach:**

Could use a single state machine:


**Trade-off:** State machine is more structured but adds complexity for a simple use case.

```typescript
// Step 3: Store pending selection
function handleAddQuantitySelect(value: number | 'keyboard') {
  if (value === 'keyboard') {
    // TODO: Future enhancement
    return;

  pendingQuantityChange = value; // Stored in $state

// Step 4: Validate and update
function handleConfirmAddQuantity() {

  // Validate max 12 per box

    errorMessage = 'Quantity cannot exceed 12. Maximum quantity per box is 12.';

    return;

  showAddQuantityModal = false;
  pendingQuantityChange = null;
```

**Key Pattern:**

1. **Pending state** - Store selection before committing
2. **Validation before commit** - Can show errors without changing state
3. **Atomic updates** - State only changes on successful validation
4. **Auto-save** - stores.ts subscription persists to LocalStorage

### Remove Quantity Flow with Auto-Delete

**Special Case:** When quantity reaches 0, auto-prompt to delete box.

```typescript
function handleConfirmRemoveQuantity() {
  if (!box || pendingQuantityChange === null) return;

  const newQuantity = box.quantity - pendingQuantityChange;

  // Validate non-negative
  if (newQuantity < 0) {
    errorMessage = `Cannot remove ${pendingQuantityChange} bottles. Current quantity is only ${box.quantity}.`;
    showErrorModal = true;
    return;
  }

  // Special case: quantity reaches 0
  if (newQuantity === 0) {
    updateBoxQuantity(boxId, 0); // Update to 0 first
    showRemoveQuantityModal = false;
    showAutoDeleteModal = true; // Auto-show delete prompt
  } else {
    updateBoxQuantity(boxId, newQuantity);
    showRemoveQuantityModal = false;
  }

  pendingQuantityChange = null;
}
```

**Why update to 0 before showing delete prompt?**

- State always reflects truth (quantity is 0)
- User can see "Quantity: 0" when deciding to delete or keep
- If user cancels, box remains with quantity 0 (valid state)

**Auto-Delete Modal:**

## Conflict Resolution Strategies

### Strategy 1: Swap Locations

**User Story:**

> I want to swap two boxes - put mine where the other one is, and move the other one to my current location.

**Implementation:**

```typescript
function handleSwapLocations() {
  if (!box || !conflictingBoxId || newStack === null || newHeight === null) return;

  const conflictingBox = $appState.boxes.find((b) => b.id === conflictingBoxId);
  if (!conflictingBox) return;

  // Step 1: Move conflicting box to current box's location
  updateBoxLocation(conflictingBoxId, { ...box.location });

  // Step 2: Move current box to new location
  updateBoxLocation(boxId, { stack: newStack, height: newHeight });

  // Close modal and reset
  showConflictModal = false;
  conflictingBoxId = null;
}
```

**Example:**

```
Before swap:
- Box A at (1,1) ← User is editing this box
- Box B at (1,2) ← Target location

User wants to move Box A to (1,2)

After swap:
- Box A at (1,2) ← Moved to target
- Box B at (1,1) ← Moved to Box A's original location
```

**Why This Works:**

- Both boxes remain in valid locations
- No gaps created (if locations were valid before, they're valid after)
- Atomic operation (both updates happen in sequence)

**When to Use Swap:**

- User wants to reorganize stacks
- Both locations are valid and desirable
- Preserves inventory structure

---

### Strategy 2: Displace Box

**User Story:**

> I want to move my box to this location, and I'll deal with the other box later. Just move it out of the way.

**Implementation:**

```typescript
function handleDisplaceBox() {
  if (!box || !conflictingBoxId || newStack === null || newHeight === null) return;

  // Step 1: Orphan the conflicting box (move to 0,0)
  updateBoxLocation(conflictingBoxId, { stack: 0, height: 0 });

  // Step 2: Move current box to target location
  updateBoxLocation(boxId, { stack: newStack, height: newHeight });

  // Close modal and reset
  showConflictModal = false;
  conflictingBoxId = null;
}
```

**Example:**

```
Before displace:
- Box A at (1,1) ← User is editing this box
- Box B at (1,2) ← Target location

User wants to move Box A to (1,2)

After displace:
- Box A at (1,2) ← Moved to target
- Box B at (0,0) ← ORPHANED (no valid location)
```

**What is "Orphaned" State?**

- Location (0,0) represents "no valid location"
- Box still exists in state, just not displayed in visual view
- Appears in "Out of Stock / Orphaned Boxes" section (inventory screen)
- User can manually relocate later

**Why Allow Orphaning?**

- Gives user flexibility to reorganize incrementally
- Can't always find perfect swap immediately
- User might want to delete the displaced box anyway

**When to Use Displace:**

- Target location is critical (must move there)
- Don't care about conflicting box's location
- Planning to delete or relocate conflicting box anyway

## State Management Integration

### New Store Action: updateBoxIsOpen()

**Added to stores.ts for this feature:**

```typescript
/**
 * Updates the open/closed status of a box.
 *
 * @param boxId - The ID of the box to update
 * @param isOpen - The new open/closed status
 * @throws {Error} If box not found
 */
export function updateBoxIsOpen(boxId: string, isOpen: boolean): void {
  appState.update((state) => {
    const boxIndex = state.boxes.findIndex((b) => b.id === boxId);
    if (boxIndex === -1) {
      throw new Error(`Box with ID "${boxId}" not found`);
    }

    // Create new state with updated box (immutable update)
    const updatedBoxes = [...state.boxes];
    updatedBoxes[boxIndex] = {
      ...updatedBoxes[boxIndex],
      isOpen,
    };

    return {
      ...state,
      boxes: updatedBoxes,
    };
  });
}
```

**Why a Dedicated Action?**

Could have reused `updateBox()` with partial updates, but dedicated actions:

- Make intent explicit (`updateBoxIsOpen` vs generic `updateBox`)
- Provide type safety (isOpen must be boolean)
- Easier to test (single responsibility)
- Self-documenting code

**Usage in Component:**

```typescript
function handleToggleOpenClosed() {
  if (!box) return;
  updateBoxIsOpen(boxId, !box.isOpen);
}
```

One line. Clear intent. Type-safe.

### Auto-Save Behavior

All state updates auto-save to LocalStorage via stores.ts subscription:

```typescript
// In stores.ts
appState.subscribe((state) => {
  saveState(state); // Persists to LocalStorage on every change
});
```

**What This Means:**

- Every `updateBoxQuantity()` call → LocalStorage update
- Every `updateBoxLocation()` call → LocalStorage update
- Every `updateBoxIsOpen()` call → LocalStorage update
- No manual save button needed
- Can close browser mid-edit, changes are saved

**Trade-off:**

- **Pro:** Can't lose data, always persisted
- **Con:** No "cancel all changes" option (would need undo/redo)

For a personal utility app, auto-save is the right choice. Professional apps might want explicit save/cancel.

## Modal-Based Workflow Pattern

### Why This Pattern?

**Core Principle:** Every destructive or significant action requires explicit confirmation.

**Benefits:**

1. **Prevents accidental changes** - User must consciously confirm
2. **Consistent UX** - Same pattern for all actions
3. **Clear focus** - Modal dims background, focuses attention
4. **Mobile-friendly** - Large touch targets, full-screen on mobile
5. **Error handling in context** - Can show validation errors inside modal

### Pattern Template

```svelte
<!-- 6. Handlers -->
<script>
  let showModal = $state(false);
  let pendingValue = $state(null);
  let error = $state(null);

  function handleSelection(value) {
    pendingValue = value;
    error = null; // Clear previous errors
  }

  function handleConfirm() {
    // Validate
    if (!isValid(pendingValue)) {
      error = 'Validation error message';
      return; // Stay in modal
    }

    // Update state
    performAction(pendingValue);

    // Close and reset
    showModal = false;
    pendingValue = null;
    error = null;
  }

  function handleCancel() {
    showModal = false;
    pendingValue = null;
    error = null;
  }
</script>

<!-- 1. Trigger Button -->
<Button onclick={() => (showModal = true)}>Action Name</Button>

<!-- 2. Modal Component -->
<Modal open={showModal} title="Action Title" onclose={handleCancel}>
  <!-- 3. Input/Selection UI -->
  <InputComponent onselect={handleSelection} />

  <!-- 4. Error Display (conditional) -->
  {#if error}
    <p class="error-message">{error}</p>
  {/if}

  <!-- 5. Action Buttons -->
  <Button onclick={handleConfirm}>Confirm</Button>
  <Button onclick={handleCancel}>Cancel</Button>
</Modal>
```

### Modal Composition

**Seven modals, same structure:**

1. **Add Quantity Modal** - NumberPad → Confirm/Cancel
2. **Remove Quantity Modal** - NumberPad → Confirm/Cancel
3. **Change Location Modal** - Number inputs → Confirm/Cancel
4. **Conflict Modal** - Swap/Displace/Cancel buttons
5. **Auto-Delete Modal** - Keep/Delete buttons
6. **Manual Delete Modal** - Confirm delete/Cancel
7. **Error Modal** - OK button

All use the same Modal component, different content and handlers.

### Why E2E Tests Caught the Critical Bug

**The Bug:**

Original implementation validated location BEFORE checking conflicts:

```typescript
// BUGGY VERSION
function handleConfirmLocationChange() {
  // Step 1: Validate first
  const validation = validateLocationNoGaps(...);
  if (!validation.isValid) {
    locationError = validation.error;
    return; // Blocks valid swaps!
  }

  // Step 2: Check conflicts second
  const conflict = getLocationConflict(...);
  if (conflict) {
    showConflictModal = true;
    return;
  }

  updateBoxLocation(...);
}
```

**What Went Wrong:**

E2E test failed:

```typescript

  await page.goto('/#/inventory/box_test_1/edit');

  // Try to move Box A from (1,1) to (1,2) where Box B lives
  await page.click('button:has-text("Change Location")');
  await page.fill('input#stack', '1');
  await page.fill('input#height', '2');
  await page.click('button:has-text("Confirm")');

  // Actual: Error "Height 2 requires height 1" (which Box A already is!)
  await expect(page.locator('h2:has-text("Location Conflict")')).toBeVisible(); // FAILED
});
```

**Root Cause:**

Validation ran first, saw (1,2) occupied, and incorrectly rejected the move. Conflict resolution never had a chance to run.

**The Fix:**

Check conflicts first, then validate:

```typescript
// FIXED VERSION
function handleConfirmLocationChange() {
  // Step 1: Check conflicts FIRST
  const conflict = getLocationConflict(...);
  if (conflict) {
    showConflictModal = true;
    return;
  }

  // Step 2: Validate ONLY if no conflict
  const validation = validateLocationNoGaps(...);
  if (!validation.isValid) {
    locationError = validation.error;
    return;
  }

  updateBoxLocation(...);
}
```

**Lesson Learned:**

E2E tests catch logic bugs that unit tests miss. The conflict-then-validate ordering is not obvious from reading code or unit tests - you need to exercise the full user flow to catch it.

## Trade-offs and Design Compromises

### 1. Modal-Based vs Inline Editing

**What We Chose:** Modal-based workflow for all actions

**Alternative:** Inline editing (edit quantity directly, click to toggle open/closed)

**Trade-offs:**

| Aspect             | Modal-Based (Chosen)         | Inline Editing                |
| ------------------ | ---------------------------- | ----------------------------- |
| Accidental changes | Prevented (confirm required) | Risk of misclick              |
| Speed for experts  | Slower (more clicks)         | Faster (direct edit)          |
| Mobile UX          | Excellent (large targets)    | Harder (small inputs)         |
| Error handling     | Clear (in modal context)     | Harder (where to show?)       |
| Learning curve     | Lower (consistent pattern)   | Lower (familiar input fields) |

**Why Modals Win:**

- Personal utility app → preventing mistakes > speed
- Mobile-first design → large touch targets critical
- Consistent UX → learn once, apply everywhere

**Future Enhancement:**

Could add "Expert Mode" toggle that enables inline editing for power users who want speed over safety.

---

### 2. Orphaned State (0,0) vs Deletion

**What We Chose:** Displace allows orphaning boxes to (0,0)

**Alternative:** Force user to choose valid location or delete immediately

**Trade-offs:**

| Aspect         | Orphaned State (Chosen)       | Force Valid Location      |
| -------------- | ----------------------------- | ------------------------- |
| Flexibility    | High (deal with it later)     | Low (must decide now)     |
| Complexity     | Higher (need orphan handling) | Lower (only valid states) |
| User control   | More control                  | Less control              |
| Data integrity | Can have "bad" states         | Always valid states       |

**Why Orphaning Works:**

- User might not know where to put displaced box yet
- Can delete orphaned box later after review
- Inventory screen shows orphaned boxes clearly
- Personal app → user is trusted to clean up later

**In a professional system:**

Might require immediate resolution - can't leave boxes in invalid states. For personal use, flexibility wins.

---

### 3. Auto-Save vs Manual Save

**What We Chose:** Auto-save to LocalStorage on every change

**Alternative:** Manual save button, batch updates

**Trade-offs:**

| Aspect            | Auto-Save (Chosen)            | Manual Save                  |
| ----------------- | ----------------------------- | ---------------------------- |
| Data loss risk    | None (always saved)           | Higher (can forget to save)  |
| Undo/redo         | Harder (need separate system) | Easier (just don't save)     |
| Performance       | More writes to storage        | Fewer writes (batched)       |
| User mental model | Simpler (no save button)      | More control (explicit save) |

**Why Auto-Save Wins:**

- LocalStorage writes are fast (synchronous, sub-millisecond)
- Personal app → unlikely to need undo across sessions
- Simpler UX (no save button to forget)
- Mobile-friendly (no risk of closing browser before save)

**Future Enhancement:**

Could add undo/redo stack in memory (separate from auto-save) for within-session undo.

## Lessons Learned

### 1. Check Conflicts Before Validation

**The Mistake:**

Validating location before checking conflicts blocks valid moves that could be resolved via swap/displace.

**The Fix:**

Always check conflicts first. If conflict exists, show resolution options. Only validate if no conflict.

**The Principle:**

When you have **resolution strategies** for edge cases, check for those edge cases BEFORE applying general validation rules.

### 2. Extract Shared Logic Early

**The Temptation:**

Implement location validation inline in InventoryBoxEdit.svelte, refactor later when Task 2.7 needs it.

**The Better Way:**

Extract location-validation.ts immediately. Benefits:

- Easier to test (pure functions)
- Reusable from day one
- Clearer component code (imports utility, doesn't implement logic)
- Task 2.7 starts faster (utility already exists)

**The Principle:**

If you **know** two features will need the same logic, extract it upfront. Don't wait for duplication to happen.

### 3. E2E Tests Find Integration Bugs

**Unit tests validate:**

- validateLocationNoGaps() works correctly
- getLocationConflict() works correctly

**E2E tests validate:**

- Component uses them in the correct order
- Modal workflows complete successfully
- State persists to LocalStorage
- User can actually accomplish their goals

**The Principle:**

Unit tests validate **components work**. E2E tests validate **the system works**.

### 4. Modal-Based Workflows for Destructive Actions

**The Pattern:**

Every destructive or significant action (delete, change location, remove quantity) requires:

1. Explicit modal confirmation
2. Clear description of action
3. Ability to cancel
4. Validation before commit

**The Benefit:**

Users feel safe. They can explore without fear of breaking things.

**The Principle:**

In personal utility apps, **safety > speed**. Users will tolerate extra clicks if it prevents mistakes.

### 5. Pending State for Multi-Step Actions

**The Pattern:**

```typescript
// Step 1: User selects value (stored in pending state)
let pendingQuantityChange = $state<number | null>(null);

function handleSelection(value: number) {
  pendingQuantityChange = value; // Not committed yet
}

// Step 2: User confirms (commit to real state)
function handleConfirm() {
  if (isValid(pendingQuantityChange)) {
    updateState(pendingQuantityChange); // Now committed
    pendingQuantityChange = null; // Reset pending
  }
}

// Step 3: User cancels (discard pending)
function handleCancel() {
  pendingQuantityChange = null; // Just reset, nothing committed
}
```

**The Benefit:**

- Can validate before committing
- Can show preview of changes
- Can cancel without side effects
- Clear separation of "draft" vs "committed" state

**The Principle:**

For multi-step user interactions, use **pending state** to represent in-progress changes before committing to real state.
