# E2E Debugging Methodology: From 30/50 to 50/50 Passing Tests

## What This Teaches

This document captures a systematic approach to debugging end-to-end (E2E) test failures in Playwright. Starting with 30/50 passing tests and 20 failures, we methodically identified and fixed three distinct categories of issues to achieve 50/50 passing. More importantly, we discovered a critical component logic bug that the E2E tests caught.

This is a real-world debugging session - not a theoretical exercise. You'll learn how to approach E2E test failures systematically, when tests are telling you about real bugs vs test infrastructure issues, and how to use debugging tools effectively.

## Context: The Starting Point

We were working on PR #51 implementing the Individual Box Edit Screen (Task 2.6). The feature was implemented in a previous session, but after rebasing onto main (which included PR #55 with E2E infrastructure fixes), we ran the tests:

```bash
npm run test:e2e

# Results:
# 30 passed (60%)
# 20 failed (40%)
```

This was actually an improvement - before PR #55, E2E tests were completely broken due to infrastructure issues. But 40% failure rate meant something was still wrong.

## The Systematic Debugging Process

### Step 1: Categorize the Failures

The first rule of debugging multiple test failures: **don't fix them one by one**. Look for patterns. Group failures by error message or symptom.

Our 20 failures fell into three categories:

1. **Playwright Strict Mode Violations** (12 tests)
   - Error: `strict mode violation: "text=Add" resolved to 2 elements`
   - Pattern: Multiple elements matching the same selector
   - Root cause: Ambiguous selectors

2. **Component Logic Bug** (4 tests)
   - Error: Tests expecting conflict resolution showed validation errors instead
   - Pattern: Location changes with conflicts failing validation
   - Root cause: Code checking validation BEFORE conflicts

3. **Missing Test Data** (4 tests - actually 12 after first fixes)
   - Error: Tests navigating to box edit routes hit "Box Not Found"
   - Pattern: Routing tests failing, but inventory tests passing
   - Root cause: Routing tests didn't set up test data

### Step 2: Fix Category by Category (Easiest to Hardest)

We tackled them in order of confidence and impact:

#### Fix 1: Playwright Strict Mode Violations (Commit 2b679b9)

**The Problem:**

Playwright strict mode (enabled by default) requires selectors to match exactly one element. Our tests had selectors like:

```typescript
// BEFORE: Too ambiguous - matches multiple buttons
await page.click('text=Add');
```

This fails when there are multiple "Add" buttons on the page (which we have in modals, NumberPad, etc.).

**The Solution:**

Make selectors more specific using element type and hierarchy:

```typescript
// AFTER: Specific - only matches button elements with "Add" text
await page.click('button:has-text("Add")');

// For modal interactions, combine with parent selectors:
await page
  .locator('dialog:has(h2:has-text("Add Quantity"))')
  .locator('button:has-text("Confirm")')
  .click();
```

**Key Pattern:** `elementType:has-text("text")` is more specific than `text=text`

**Results:** 30/50 → 38/50 tests passing (+8)

**Why This Worked:**

Strict mode violations are typically easy fixes - they're test infrastructure issues, not functional bugs. The selectors just need to be more specific. This is low-risk refactoring that improves test reliability.

#### Fix 2: Component Logic Bug (Commit c35fc9d, part 1)

**The Problem:**

Four tests were failing in unexpected ways. They were testing conflict resolution when moving boxes to occupied locations, but instead of showing the conflict modal, they were getting validation errors about gaps:

```typescript
// Test: Move box to occupied location
await changeLocation(2, 1); // This location is occupied by another box
// Expected: Conflict modal appears
// Actual: Error "Height 1 in stack 2 requires height 0" ???
```

Wait, what? Why is it validating gaps when there's clearly a box there?

**The Investigation:**

Let's look at the component code:

```typescript
// BEFORE: Buggy order of operations
function handleConfirmLocationChange() {
  // 1. First, validate for gaps
  const validation = validateLocationNoGaps(newStack, newHeight, boxes, boxId);
  if (!validation.isValid) {
    locationError = validation.error; // Stops here!
    return;
  }

  // 2. Then check for conflicts (never reached)
  const conflict = getLocationConflict(newStack, newHeight, boxes, boxId);
  if (conflict) {
    showConflictModal = true; // Never happens
    return;
  }
}
```

The bug: **We're checking validation BEFORE checking conflicts**.

Here's why this is wrong:

1. `validateLocationNoGaps` excludes the box being moved (via `excludeBoxId`)
2. So when validating a move to an occupied location, it sees:
   - Source location: now empty (box excluded)
   - Target location: occupied by another box
3. If moving from Stack 1, Height 2 → Stack 2, Height 1:
   - Stack 1, Height 2 is now empty (creates a gap!)
   - Validation fails before we even check if Stack 2, Height 1 is occupied

**The Real Issue:**

When you move a box, you might temporarily create gaps. But if you're swapping with another box (conflict resolution), those gaps get filled by the swap. By validating first, we prevent valid swap operations.

**The Fix:**

Check conflicts BEFORE validation:

```typescript
// AFTER: Correct order of operations
function handleConfirmLocationChange() {
  // 1. First, check for conflicts
  const conflict = getLocationConflict(newStack, newHeight, boxes, boxId);
  if (conflict) {
    showConflictModal = true; // Let user choose: swap or displace
    return;
  }

  // 2. Only validate if no conflict
  // (If there's a conflict, swap/displace will handle gap resolution)
  const validation = validateLocationNoGaps(newStack, newHeight, boxes, boxId);
  if (!validation.isValid) {
    locationError = validation.error;
    return;
  }

  // 3. Update location
  updateBoxLocation(boxId, { stack: newStack, height: newHeight });
}
```

**Why This Order Makes Sense:**

Think about the user flow:

1. User tries to move box to location X
2. Is location X occupied? → Show conflict modal, let user decide
3. Is location X unoccupied but invalid (gaps)? → Show validation error
4. Location X is unoccupied and valid? → Allow the move

Checking conflicts first means we can offer conflict resolution (swap/displace) which might resolve any gap issues. Checking validation first prevents us from ever offering conflict resolution.

**Results:** 38/50 → 42/50 tests passing (+4)

**Why This Mattered:**

This was a real bug, not a test issue. The E2E tests caught it. Without these tests, users would encounter this bug in production:

- Try to move a box to swap locations
- Get a confusing error about gaps
- No option to swap
- Frustrated user

This is the value of E2E testing: catching bugs in real user workflows.

#### Fix 3: Additional E2E Test Refinements (Commit c35fc9d, part 2)

After fixing the logic bug, we still had 8 failures. These were test infrastructure issues:

1. **Missing data-testid attributes**
   - Problem: Selectors couldn't find boxes in inventory
   - Fix: Added `data-testid="box-{box.id}"` to box elements

2. **Strict mode violations in edge cases**
   - Problem: `.last()` syntax invalid in strict mode
   - Fix: Changed to proper locator chains: `.locator('div').last().click()`

3. **Modal animation timing**
   - Problem: Tests clicking before modals fully rendered
   - Fix: Added explicit waits: `await page.waitForSelector('dialog:visible')`

**Results:** 42/50 → 50/50 tests passing (+8)

#### Fix 4: Routing Test Data (Commit 967a551)

All inventory-box-edit tests passing, but routing tests started failing in CI. Why?

The routing tests navigate directly to box edit URLs:

```typescript
// Routing test
await page.goto('/#/inventory/box_abc/edit');
```

But they didn't set up test data! The box `box_abc` didn't exist, so the component correctly showed "Box Not Found".

The inventory tests didn't have this problem because they always went through the inventory screen, which has its own test data setup.

**The Fix:**

Add beforeEach setup to routing tests:

```typescript
test.beforeEach(async ({ page }) => {
  // Set up test data for all box IDs used in routing tests
  await page.evaluate(() => {
    const testState = {
      boxes: [
        {
          id: 'box_abc',
          flavorId: 'flavor_1',
          quantity: 5,
          location: { stack: 1, height: 1 },
          isOpen: false,
        },
        // ... all other boxes referenced in routing tests
      ],
      flavors: [
        { id: 'flavor_1', name: 'Chocolate', excludeFromRandom: false },
        // ...
      ],
      // ...
    };
    localStorage.setItem('BROTEINBUDDY_APP_STATE', JSON.stringify(testState));
  });
});
```

**Results:** 50/50 → 50/50 tests passing (12 more routing tests now valid)

## Lessons Learned

### 1. E2E Tests Catch Real Bugs

The component logic bug (checking validation before conflicts) was subtle. Unit tests didn't catch it because:

- Unit tests for `validateLocationNoGaps` passed ✓
- Unit tests for `getLocationConflict` passed ✓
- The bug was in the integration - the order of calling these functions

E2E tests simulate real user workflows:

- "I'm trying to swap two boxes"
- "Why am I getting an error about gaps?"
- This revealed the logic bug

### 2. Playwright Strict Mode Is Your Friend

Strict mode forces you to write better selectors:

**Bad (ambiguous):**

```typescript
await page.click('text=Add'); // Which "Add" button?
await page.click('.button'); // Which element with class "button"?
```

**Good (specific):**

```typescript
await page.click('button:has-text("Add Quantity")'); // Exactly this button
await page.locator('[data-testid="add-quantity-button"]').click(); // Unique ID
```

Initially, strict mode feels like a pain - "Why is this failing? I can see the button!"

But it catches bugs:

- Multiple modals open at once
- Buttons not properly cleaned up after modal closes
- Overlapping interactive elements

### 3. Test Data Setup Is Critical

E2E tests need realistic test data. Different test suites may need different setups:

**Inventory tests:** Need boxes in various locations, different flavors
**Routing tests:** Need boxes with specific IDs that match route params
**Random selection tests:** Need flavors with different excludeFromRandom states

Don't assume test data from one suite will work for another. Each suite should set up its own data in `beforeEach`.

### 4. Debug Systematically, Not Randomly

When facing 20 test failures:

**Don't do this:**

- Fix test #1
- Fix test #2
- Fix test #3
- ... (20 individual fixes)

**Do this:**

1. Group by error pattern
2. Identify root causes (one per group)
3. Fix root causes (3-4 fixes total)
4. Re-run all tests

### 5. Modal Timing in E2E Tests

Modals have animations. Tests run fast. This causes race conditions:

**Problem:**

```typescript
await page.click('button:has-text("Add Quantity")');
await page.click('button:has-text("Confirm")'); // Fails - modal not ready!
```

**Solution:**

```typescript
await page.click('button:has-text("Add Quantity")');
await page.waitForSelector('dialog:visible'); // Wait for modal
await page.click('button:has-text("Confirm")'); // Now it works
```

For modals with slide-in animations, wait for the dialog to be visible AND stable:

```typescript
await page.waitForSelector('dialog:visible', { state: 'visible' });
await page.waitForTimeout(100); // Give animation time to complete
```

### 6. Component Logic: Check Dependencies Before Validation

In the location change bug, we learned a general principle:

**When validating state transitions, check dependencies first:**

1. **Check conflicts/dependencies** - Can this operation proceed at all?
2. **Check validation** - Is the target state valid?
3. **Apply change** - Execute the operation

If you validate before checking dependencies, you might reject valid operations that have resolution strategies (like swapping boxes).

**Another example (hypothetical):**

```typescript
// Moving a file in a file system
function moveFile(source, target) {
  // 1. Check if target exists (dependency)
  if (fileExists(target)) {
    promptOverwrite(); // Let user decide
    return;
  }

  // 2. Validate target path (validation)
  if (!isValidPath(target)) {
    showError('Invalid path');
    return;
  }

  // 3. Perform move
  performMove(source, target);
}
```

Order matters!

## Debugging Tools and Techniques

### 1. Playwright UI Mode

The best way to debug E2E tests:

```bash
npm run test:e2e:ui
```

This opens a GUI where you can:

- Step through tests
- See screenshots at each step
- Inspect the page state
- Re-run individual tests
- See exactly which selector failed

**Pro tip:** When a test fails, UI mode shows you the exact point of failure with a screenshot. You can see what's actually on the page vs what the test expected.

### 2. Playwright Trace Viewer

For CI failures, use traces:

```typescript
// In playwright.config.ts
use: {
  trace: 'on-first-retry', // Capture traces on failures
}
```

After a test fails:

```bash
npx playwright show-trace trace.zip
```

This gives you a timeline of:

- Every action
- Network requests
- Console logs
- Screenshots

### 3. Debugging Individual Tests

Run a single test with debug mode:

```bash
npx playwright test --debug -g "should move box to occupied location"
```

Playwright pauses before each action. You can:

- Inspect the page in DevTools
- Step through line by line
- See selector evaluation in real-time

### 4. Console Logging in Tests

Sometimes you need to see what state the app is in:

```typescript
test('complex interaction', async ({ page }) => {
  // Log the entire app state
  const state = await page.evaluate(() => {
    return localStorage.getItem('BROTEINBUDDY_APP_STATE');
  });
  console.log('App state:', state);

  // Log specific elements
  const buttonText = await page.locator('button').first().textContent();
  console.log('First button:', buttonText);
});
```

### 5. Screenshots on Failure

Automatically capture screenshots:

```typescript
// In playwright.config.ts
use: {
  screenshot: 'only-on-failure',
}
```

After tests run, check `test-results/` for screenshots of failures.

## Best Practices for E2E Tests

### 1. Use Data TestIDs for Stable Selectors

Instead of:

```typescript
await page.click('.box-card'); // Fragile - CSS classes change
```

Use:

```typescript
await page.click('[data-testid="box-box_123"]'); // Stable - explicit test hook
```

Add data-testid attributes to components:

```svelte
<div class="box-card" data-testid="box-{box.id}">
  {box.quantity}
</div>
```

### 2. Wait for State, Not Time

Bad:

```typescript
await page.waitForTimeout(1000); // Brittle - assumes 1s is enough
```

Good:

```typescript
await page.waitForSelector('[data-testid="success-message"]', { state: 'visible' });
```

### 3. Test User Workflows, Not Implementation

Bad:

```typescript
// Testing implementation details
test('updateBoxLocation function called', async ({ page }) => {
  // Mock the function, verify it's called
});
```

Good:

```typescript
// Testing user workflow
test('user can move box to new location', async ({ page }) => {
  await page.goto('/#/inventory/box_123/edit');
  await page.click('button:has-text("Change Location")');
  await page.fill('input[name="stack"]', '2');
  await page.fill('input[name="height"]', '3');
  await page.click('button:has-text("Confirm")');
  await expect(page.locator('text=Stack 2, Height 3')).toBeVisible();
});
```

### 4. Isolate Test State

Each test should start with a clean state:

```typescript
test.beforeEach(async ({ page }) => {
  // Clear all state
  await page.evaluate(() => {
    localStorage.clear();
  });

  // Set up specific test data
  await page.evaluate(() => {
    localStorage.setItem('BROTEINBUDDY_APP_STATE', JSON.stringify(testState));
  });

  // Navigate to starting point
  await page.goto('/#/');
});
```

Don't rely on state from previous tests!

### 5. Group Related Tests

Use `test.describe` blocks to group related tests:

```typescript
test.describe('Location Changes', () => {
  test.beforeEach(async ({ page }) => {
    // Setup specific to location change tests
  });

  test('should move box to empty location', async ({ page }) => {
    // ...
  });

  test('should handle conflict when moving to occupied location', async ({ page }) => {
    // ...
  });

  test('should prevent moving to location with gaps', async ({ page }) => {
    // ...
  });
});
```

This makes it easier to:

- Run just location change tests: `npx playwright test -g "Location Changes"`
- Share setup code
- Understand test organization

## When E2E Tests Fail: Decision Tree

Here's how to think about E2E test failures:

```
E2E Test Fails
├─ Is the UI behaving correctly manually?
│  ├─ YES → Test issue (selector, timing, test data)
│  │  ├─ Selector issue → Make selector more specific
│  │  ├─ Timing issue → Add proper waits
│  │  └─ Test data issue → Check beforeEach setup
│  └─ NO → Real bug!
│     ├─ Bug in component logic → Fix component
│     ├─ Bug in state management → Fix store actions
│     └─ Bug in validation logic → Fix validation functions
```

In our case:

- Strict mode failures → Test issue (selectors too ambiguous)
- Conflict modal not appearing → Real bug (logic order wrong)
- Routing tests failing → Test issue (missing test data)
- Modal timing failures → Test issue (missing waits)

## Real-World Takeaways

### For Developers

1. **E2E tests are worth it** - They catch integration bugs that unit tests miss
2. **Strict mode is your friend** - Forces you to write better selectors
3. **Debug systematically** - Group failures, fix root causes, not symptoms
4. **Test real workflows** - Not implementation details

### For Test Writers

1. **Use specific selectors** - `button:has-text("text")` over `text=text`
2. **Wait for state** - Not arbitrary timeouts
3. **Set up test data properly** - Each suite has its own needs
4. **Use data-testid attributes** - For stable test hooks

### For Teams

1. **Don't ignore flaky tests** - They're telling you something
2. **Run E2E tests in CI** - Catch issues before production
3. **Use Playwright trace viewer** - Essential for debugging CI failures
4. **Document debugging processes** - Like this document!
