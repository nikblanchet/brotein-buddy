## Introduction

Deployment is where your carefully crafted application meets the real world. It's the difference between "it works on my machine" and "it works for everyone, everywhere." Phase 3.5 focused on getting BroteinBuddy from a local development environment to a publicly accessible URL with HTTPS, PWA functionality, and automatic deployments.

But here's the thing: deployment isn't just about getting code online. It's about:

- **Reproducible builds**: Ensuring production builds match local builds
- **Platform compatibility**: Handling OS-specific dependencies
- **Security**: HTTPS, proper headers, protecting against common vulnerabilities
- **Automation**: Zero-touch deployments from git pushes
- **Validation**: Verifying everything works in production before declaring success

### Why This Is Important

You can have the most elegant code, perfect test coverage, and beautiful UI design - but if you can't deploy reliably, your app is just an expensive hobby project. Deployment is where theory meets practice, and where many projects fail.

### Learning Objectives

By the end of this document, you'll understand:

- How to choose a hosting platform for static web apps
- Platform-specific build dependencies and how to handle them
- Vercel's deployment model and configuration
- Security headers and why they matter
- The difference between technical validation and portfolio-ready deployment
- Why deploying early reveals integration issues

### Prerequisites

- Understanding of build tools (Vite, Rollup)
- Basic knowledge of Node.js and npm
- Familiarity with git and GitHub
- Understanding of PWAs (see teaching doc 3.2)

## Why Vercel for Static Hosting

Choosing a hosting platform is one of those decisions that affects everything: your deployment workflow, your costs, your reliability, and how easy it is to iterate.

### The Options We Considered

**1. Vercel (Chosen)**

**Pros:**

- Zero-configuration Vite support (auto-detects framework)
- Automatic HTTPS with valid SSL certificates
- Built-in preview deployments for every PR
- Free tier suitable for portfolio projects
- Excellent global CDN performance
- GitHub integration for automatic deployments
- Native support for SPAs (single-page applications)

**Cons:**

- Vendor lock-in (mitigated by standard Vite build)
- Cold start times on free tier (acceptable for portfolio)
- Some configuration quirks (like Rollup binary issue)

**Why we chose it:** Best Vite integration, zero-config HTTPS, and preview deployments made this the clear winner for a PWA project.

**2. Netlify**

Very similar to Vercel - almost identical feature set. We chose Vercel purely because of slightly better Vite integration and familiarity.

**3. GitHub Pages**

**Pros:**

- Free for public repos
- Simple setup

**Cons:**

- No preview deployments (you can't test PRs before merging)
- Limited configuration for custom headers
- No easy way to handle SPA routing
- Manual workflow required

**Why we rejected it:** Lack of preview deployments is a dealbreaker for a project with CI/CD workflow.

**4. Railway, Render, Fly.io**

**Why we rejected them:** These platforms are designed for server-side applications. For a static PWA, they're overkill and more expensive. We don't need a server - just a CDN.

**5. AWS S3 + CloudFront**

**Pros:**

- Maximum control and scalability
- Extremely cost-effective at scale

**Cons:**

- Manual configuration nightmare
- No preview deployments without custom tooling
- SSL certificate management
- CloudFront distribution setup
- S3 bucket policies and CORS

**Why we rejected it:** Too much infrastructure management for a portfolio project. Vercel gives us 90% of the benefit with 5% of the complexity.

### The Vercel Model

Vercel's value proposition is simple: **git push = live deployment**. Here's what happens:

1. You push code to GitHub
2. GitHub Actions runs your CI tests
3. If tests pass and PR is merged, Vercel builds your app
4. Vercel deploys to their global CDN
5. Your app is live with HTTPS in ~30 seconds

For pull requests, Vercel creates preview deployments with unique URLs so you can test changes before merging. This is invaluable for catching integration issues.

## Understanding Platform-Specific Build Dependencies

This is where things got interesting. Our first deployment attempt failed with a cryptic error:

```
Error: Cannot find module '@rollup/rollup-linux-x64-gnu'
```

Wait, what? It worked fine locally on macOS. Welcome to cross-platform builds.

### The Problem: Native Binaries

Rollup (the bundler used by Vite) ships with platform-specific native binaries for performance. On macOS, it uses `@rollup/rollup-darwin-x64`. On Linux, it uses `@rollup/rollup-linux-x64-gnu`.

npm is supposed to automatically install the correct binary based on your platform using the `optionalDependencies` field. But Vercel's build environment apparently doesn't trigger this detection correctly.

### The Solution: Explicit Optional Dependencies

We forced npm to install the Linux binary by adding it explicitly:

```json
{
  "optionalDependencies": {
    "@rollup/rollup-linux-x64-gnu": "4.52.5"
  }
}
```

**Key points:**

1. **Version must match**: We used `4.52.5` because that's the exact Rollup version bundled with Vite 7.1.12
2. **Optional, not regular**: Marked as optional so it doesn't fail on macOS/Windows development machines
3. **Updated install command**: Changed Vercel's install command to `npm install --include=optional` to ensure it installs

### Why It's Optional

If we put this in `dependencies`, npm would try to install the Linux binary on every developer's machine, including macOS and Windows. Since it's optional, npm only installs it when running on Linux (or when explicitly told to with `--include=optional`).

Local development machines use their platform-specific binary automatically. Vercel's Linux servers now explicitly install the Linux binary. Everyone's happy.

### What We Learned

**Platform-specific dependencies are tricky.** When your build works locally but fails in CI/CD, look for:

1. Native binaries (Rollup, node-sass, sharp, etc.)
2. Platform-specific dependencies
3. Differences between development OS and production OS
4. npm/yarn/pnpm version differences

Always test your build in a Docker container matching your production environment before pushing to production.

## Vercel Configuration Deep Dive

Let's break down every piece of our `vercel.json` and why it matters.

### Build Configuration

```json
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "installCommand": "npm install --include=optional",
  "framework": "vite"
}
```

**buildCommand**: Explicitly tells Vercel how to build the app. Even though Vercel auto-detects Vite, being explicit prevents surprises.

**outputDirectory**: Where the built files live. Vite outputs to `dist/` by default.

**installCommand**: Critical - includes optional dependencies so Rollup's Linux binary installs.

**framework**: Hints to Vercel that this is a Vite project for optimized handling.

### SPA Routing

```json
{
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```

**Why this matters:** BroteinBuddy uses client-side routing (svelte-spa-router). When you navigate to `/inventory`, there's no `inventory.html` file - just `index.html` with JavaScript that handles routing.

Without this rewrite rule:

1. User visits `https://brotein-buddy.vercel.app/`
2. Vercel serves `index.html`
3. User clicks "Inventory" → URL changes to `/inventory`
4. User refreshes page
5. Vercel looks for `/inventory.html` → 404 error

With this rewrite rule:

1. User visits `https://brotein-buddy.vercel.app/inventory`
2. Vercel rewrites request to `/index.html`
3. `index.html` loads with JavaScript
4. JavaScript reads URL path (`/inventory`) and renders correct route

This is essential for SPAs. Every platform handles it differently:

- Vercel: `rewrites` in vercel.json
- Netlify: `_redirects` file or netlify.toml
- Apache: `.htaccess` with mod_rewrite
- Nginx: `try_files` directive

### Service Worker Caching

```json
{
  "source": "/service-worker.js",
  "headers": [
    {
      "key": "Cache-Control",
      "value": "public, max-age=0, must-revalidate"
    }
  ]
}
```

**The problem:** Service workers cache assets for offline functionality. But what happens when you deploy an update? Users' browsers keep serving the old cached service worker, never seeing your new code.

**The solution:** Force browsers to always check for service worker updates:

- `public`: Can be cached by browsers and CDN
- `max-age=0`: Cache expires immediately
- `must-revalidate`: Must check with server before using cached version

This ensures users get service worker updates on every deployment while still benefiting from cached app assets.

### Security Headers

```json
{
  "source": "/(.*)",
  "headers": [
    {
      "key": "X-Content-Type-Options",
      "value": "nosniff"
    },
    {
      "key": "X-Frame-Options",
      "value": "DENY"
    },
    {
      "key": "X-XSS-Protection",
      "value": "1; mode=block"
    }
  ]
}
```

These aren't strictly required, but they're security best practices:

**X-Content-Type-Options: nosniff**

Prevents browsers from "sniffing" content types and executing files as different types than declared. For example, prevents a `.txt` file from being executed as JavaScript if it contains code.

**X-Frame-Options: DENY**

Prevents your site from being embedded in an iframe. This protects against clickjacking attacks where a malicious site overlays invisible iframes over your UI to trick users into clicking things.

**X-XSS-Protection: 1; mode=block**

Enables the browser's built-in XSS (cross-site scripting) filter. If the browser detects a reflected XSS attack, it blocks the page instead of rendering it.

**Note:** These are defense-in-depth measures. Modern security relies on Content Security Policy (CSP), but these headers add extra protection for older browsers.

## The Two-Phase Deployment Strategy

Here's where our approach differed from the original plan. The plan said:

> **3.4 → 3.5**: Complete documentation and polish, then deploy.

We did:

> **3.5a → 3.4 → 3.5b**: Deploy infrastructure first, discover issues, fix them, then verify production.

### Why We Changed the Order

**Original assumption:** The app works perfectly in development, so deployment is just "put it online and verify."

**Reality:** Production environments reveal integration issues that don't surface locally:

1. **Drag-and-drop completely broken** - worked in dev, broken in production
2. **CRUD operations failing** - edge cases not caught by tests
3. **PWA standalone mode** - can't test without actual iOS device installation
4. **Visual issues** - different screen sizes, actual usage patterns
5. **UX problems** - only apparent when doing real workflows

### The Two-Phase Strategy

**Phase 3.5a: Infrastructure Deployment (COMPLETE)**

Goal: Get code deployed and technically functioning.

Deliverables:

- Vercel project configured
- Node.js 22 requirement specified
- Rollup Linux binary fix
- Production deployment successful
- HTTPS working
- PWA installable
- Known issues documented

**Phase 3.4: Bug Fixes and Polish (IN PROGRESS)**

Goal: Fix critical bugs discovered during production testing.

Deliverables:

- Fix 5 critical bugs (drag-and-drop, inventory CRUD, PWA navigation)
- Resolve 5 major UX issues (favorite flavor management, random selection UX)
- Polish 5 visual issues (contrast, styling, clarity)
- Write user documentation
- Add screenshots

**Phase 3.5b: Production Verification (BLOCKED)**

Goal: Verify portfolio-ready status.

Deliverables:

- All features working on production
- Lighthouse scores verified (95+/95+/90+/85+)
- Manual testing on iOS completed
- Repository marked as "ready for portfolio"

### What We Learned

**Deploy early, deploy often.** Waiting until everything is "perfect" means discovering integration issues late. Better to deploy infrastructure early, find problems in production, and fix them systematically.

This is the "shift left" philosophy applied to deployment: catch production issues earlier in the development cycle.

## How It Works Together

Let's walk through the complete deployment workflow from git push to live URL.

### Deployment Flow

**1. Developer pushes code to feature branch**

```bash
git push origin feature/some-feature
```

**2. GitHub Actions CI runs**

`.github/workflows/ci.yml` executes:

- Lint (ESLint)
- Format check (Prettier)
- Type check (TypeScript)
- Unit tests (Vitest)
- E2E tests (Playwright)
- Build verification

**3. Vercel creates preview deployment**

If PR is created:

- Vercel detects new PR
- Runs `npm install --include=optional`
- Runs `npm run build`
- Deploys to unique preview URL
- Comments on PR with preview link

**4. Developer reviews preview deployment**

Clicks preview link, tests changes in production-like environment.

**5. PR merged to main**

After approval and passing checks:

```bash
git checkout main
git merge --squash feature/some-feature
git push origin main
```

**6. Vercel deploys to production**

- Detects push to main branch
- Runs full build process
- Deploys to https://brotein-buddy.vercel.app
- Updates service worker for installed PWAs

**7. Service worker updates**

Users with installed PWA:

- Service worker checks for updates
- Downloads new version in background
- Prompts user to reload (or auto-reloads on next visit)

### What Happens During Build

Vercel build process (simplified):

1. **Clone repository** from GitHub
2. **Install Node.js 22** (specified in package.json engines)
3. **Run install command**: `npm install --include=optional`
   - Installs dependencies
   - Installs `@rollup/rollup-linux-x64-gnu` (our fix)
4. **Run build command**: `npm run build`
   - Vite builds production bundle
   - Rollup bundles code
   - vite-plugin-pwa generates service worker
   - Outputs to `dist/`
5. **Deploy to CDN**
   - Uploads `dist/` contents to Vercel's edge network
   - Configures rewrites and headers from vercel.json
   - Invalidates CDN cache

**Build time:** ~30 seconds

**Time to global propagation:** ~1 minute

## Design Trade-offs

Every deployment decision involves trade-offs. Here's what we optimized for and what we sacrificed.

### What We Optimized For

**1. Simplicity**

Chose Vercel over AWS because we wanted deployment to be:

- Zero-configuration for HTTPS
- Automatic for every PR
- Managed (no server maintenance)

**Trade-off:** Vendor lock-in to Vercel's platform.

**Why it's okay:** Standard Vite build means we can migrate to any static host. Vercel is just serving files.

**2. Fast Iteration**

Preview deployments for every PR means we can:

- Test changes in production environment before merging
- Share work-in-progress with others
- Catch integration issues early

**Trade-off:** More deployments = more build minutes consumed on free tier.

**Why it's okay:** Vercel's free tier is generous (100GB bandwidth, 100 build hours/month). Our builds are ~30 seconds each.

**3. Developer Experience**

Explicit configuration in `vercel.json` means:

- New developers can see exactly how deployment works
- No "magic" auto-detection surprises
- Reproducible across environments

**Trade-off:** More configuration files to maintain.

**Why it's okay:** Configuration is documented and rarely changes.

### What We Sacrificed

**1. Custom Server Logic**

Static hosting means we can't:

- Run server-side code
- Have API endpoints
- Do server-side rendering (SSR)

**Why it's okay:** BroteinBuddy is 100% client-side. We use LocalStorage for data, no backend needed.

**2. Deployment Control**

Using Vercel's managed platform means:

- Can't customize server configuration deeply
- Limited control over CDN behavior
- Dependent on Vercel's uptime

**Why it's okay:** For a portfolio project, managed hosting benefits outweigh control.

**3. Cost Predictability**

Free tier has limits:

- 100GB bandwidth/month
- 100 build hours/month
- No custom domains on free tier (must use vercel.app subdomain)

**Why it's okay:** Portfolio project traffic fits comfortably in free tier. If it somehow becomes popular enough to exceed limits, that's a good problem to have.

## Real-World Compromises

Let's talk about the less-than-ideal decisions we made and why they were acceptable.

### 1. Hardcoded Rollup Version

We hardcoded the Rollup Linux binary version:

```json
{
  "@rollup/rollup-linux-x64-gnu": "4.52.5"
}
```

**The problem:** If we update Vite (which bundles Rollup), we need to manually update this version to match.

**The ideal solution:** Script to detect Rollup version from Vite's dependencies and automatically update package.json.

**Why we didn't do it:** One-time configuration that rarely changes. Vite major versions are infrequent. The maintenance burden is minimal.

**The compromise:** Document it in ADR-009 so future maintainers know to check this when updating Vite.

### 2. Deploying With Known Bugs

We deployed to production knowing there were critical bugs (drag-and-drop broken, CRUD issues).

**The problem:** Production URL is public and could be viewed by potential employers.

**The ideal solution:** Fix all bugs in development, then deploy perfect code.

**Why we didn't do it:** Some bugs only surfaced in production environment. Deploying infrastructure first enabled:

- Testing on actual iOS devices
- Discovery of integration issues
- Validation of deployment configuration

**The compromise:** Added prominent status notice to README:

> Status: Technical validation deployment. Known issues being tracked for Phase 3.4. Not portfolio-ready yet.

This signals to visitors that this is a work-in-progress.

### 3. No Staging Environment

We deploy directly from main to production. No staging environment.

**The problem:** Changes go live immediately. No intermediate environment to test.

**The ideal solution:** Staging environment that mirrors production exactly.

**Why we didn't do it:** Preview deployments serve this purpose. Each PR gets a preview URL that's production-like. For a solo portfolio project, staging is overkill.

**The compromise:** Use preview deployments as staging. Test thoroughly on preview before merging to main.

### 4. Manual iOS Testing

We don't have automated tests for PWA installation on iOS.

**The problem:** Can't verify PWA functionality in CI/CD.

**The ideal solution:** Automated iOS testing using BrowserStack or similar.

**Why we didn't do it:** iOS PWA installation requires real device interaction (tap Share button, Add to Home Screen). Automation is expensive and complex for a portfolio project.

**The compromise:** Manual testing on iPhone after each deployment. Document testing procedure in DEVELOPING.md.

## What You Should Learn From This

Here are the key patterns and principles worth remembering from this deployment.

### 1. Configuration as Documentation

Our `vercel.json` is explicit:

```json
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",
  "installCommand": "npm install --include=optional",
  "framework": "vite"
}
```

Even though Vercel can auto-detect most of this, being explicit means:

- New team members see exactly how deployment works
- No surprises from platform updates
- Configuration is version-controlled and reviewable

**When to use it:** Always prefer explicit configuration over "magic" auto-detection for critical infrastructure.

**When to avoid it:** Don't over-configure. Only specify what matters for reproducibility.

### 2. Platform-Specific Dependencies Require Explicit Handling

If your build tool uses native binaries (Rollup, node-sass, sharp, etc.), test on the same platform as production.

**Pattern:**

1. Identify native dependencies (look for `@rollup/*`, `node-sass`, etc.)
2. Check if they're platform-specific
3. Test build on target platform (Docker, CI, etc.)
4. Add explicit optional dependencies if needed

**When to use it:** Anytime you're using build tools with native bindings.

### 3. Security Headers Are Defense-in-Depth

Our security headers (`X-Frame-Options`, `X-Content-Type-Options`, etc.) aren't required for the app to work, but they protect against classes of attacks.

**Pattern:**

- Always add security headers to production deployments
- Use CSP (Content Security Policy) for modern security
- Add traditional headers for older browser support
- Test with security tools (Mozilla Observatory, Security Headers)

**When to use it:** Every production deployment, no exceptions.

### 4. Deploy Infrastructure Before Perfection

We deployed with known bugs to validate infrastructure and discover integration issues.

**Pattern:**

1. Get minimal viable deployment working (Phase 3.5a)
2. Test in production environment
3. Document discovered issues
4. Fix issues systematically (Phase 3.4)
5. Verify portfolio-ready status (Phase 3.5b)

**When to use it:** For projects where production environment differs significantly from development (PWAs, mobile apps, complex integrations).

**When to avoid it:** For backend services handling sensitive data. Test thoroughly before deploying.

### 5. Preview Deployments Enable Fast Iteration

Every PR getting a preview URL means you can:

- Test changes before merging
- Share work with non-technical stakeholders
- Catch integration issues early

**Pattern:**

- Choose hosting platform with preview deployment support
- Share preview links in PR descriptions
- Test thoroughly on preview before merging
- Use preview deployments as lightweight staging

**When to use it:** Any project with CI/CD and collaboration.

## Common Deployment Pitfalls

Here are mistakes I've seen (and made) in production deployments.

### 1. Missing Environment Variables

**Problem:** App works locally but crashes in production because environment variables aren't set.

**Solution:**

- Document all required environment variables
- Use `.env.example` as template
- Configure on hosting platform
- Verify during deployment

**BroteinBuddy note:** We don't use environment variables (LocalStorage-only), but most real apps do.

### 2. Different Build Behavior Locally vs CI

**Problem:** Build succeeds locally but fails in CI or production.

**Common causes:**

- Different Node.js versions
- Different npm/yarn versions
- Missing dependencies in package.json (worked locally because globally installed)
- Platform-specific binaries (our Rollup issue)

**Solution:**

- Lock Node.js version in package.json (`engines` field)
- Use `package-lock.json` or `yarn.lock` (never gitignore these)
- Test build in Docker container matching production
- Run `npm ci` instead of `npm install` in CI (uses lock file strictly)

### 3. Forgetting SPA Routing Configuration

**Problem:** SPA works on home page, but refreshing `/about` gives 404.

**Solution:** Configure server to rewrite all routes to index.html (we did this in vercel.json).

**Platform-specific:**

- Vercel: `rewrites` in vercel.json
- Netlify: `_redirects` file
- Apache: `.htaccess` with mod_rewrite
- Nginx: `try_files $uri /index.html`

### 4. Service Worker Caching Issues

**Problem:** Deploy new code, but users still see old version.

**Causes:**

- Service worker not updating (aggressive caching)
- Service worker file itself cached by CDN/browser
- Cache-Control headers too aggressive

**Solution:**

- Set service worker Cache-Control to `max-age=0, must-revalidate` (we did this)
- Use vite-plugin-pwa which handles updates automatically
- Test service worker updates in private/incognito mode

### 5. HTTPS Mixed Content

**Problem:** Site is HTTPS but loads HTTP resources (images, fonts, scripts). Browser blocks them.

**Solution:**

- Use relative URLs (`/assets/image.png` instead of `http://example.com/assets/image.png`)
- Use protocol-relative URLs (`//example.com/assets/image.png`)
- Ensure all external resources are HTTPS
- Test on production HTTPS URL, not localhost

### 6. Ignoring Build Warnings

**Problem:** Build succeeds with warnings. Warnings turn into errors in production.

**Examples:**

- Large bundle sizes
- Deprecated dependencies
- Missing peer dependencies
- Sourcemap warnings

**Solution:**

- Treat warnings as errors in CI (`process.exit(1)` on warnings)
- Fix warnings immediately
- Monitor bundle size (we use rollup-plugin-visualizer)

## Summary

Deploying BroteinBuddy taught us that infrastructure deployment and application readiness are two separate concerns. We successfully deployed the technical infrastructure (Vercel, HTTPS, PWA) while discovering that the application itself needed significant bug fixes.

The key lessons:

1. **Deploy infrastructure early** to discover integration issues
2. **Platform-specific dependencies** require explicit handling
3. **Configuration should be explicit** and version-controlled
4. **Security headers** are cheap insurance
5. **Preview deployments** enable fast, safe iteration

Phase 3.5a achieved its goal: getting code deployed with proper configuration. Phase 3.4 will address the bugs discovered during production testing, and Phase 3.5b will verify portfolio-ready status.

Deployment isn't the end - it's the beginning of real-world validation.
