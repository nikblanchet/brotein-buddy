# CI/CD vs Local Testing: Why Continuous Integration Catches What You Miss

This document explains why CI/CD checks catch issues that local tests don't, using real examples from Phase 3.3 where CI/CD uncovered bugs that passed locally.

## What We Built

Phase 3.3 added 60+ accessibility tests to BroteinBuddy. This increased CI/CD run time from ~5 minutes to ~8-10 minutes, but also exposed critical differences between local testing and CI/CD environments.

**Key insight:** CI/CD caught bugs that passed locally, including:

- localStorage key mismatches (hardcoded vs constant)
- Platform-specific rendering differences (macOS vs Linux)
- Timing issues with sequential worker execution
- Environment-specific configuration bugs

The result: Higher confidence in our code, but also a deeper understanding of why CI/CD is NOT just "running the same tests again."

## Why CI/CD Catches Things Local Tests Don't

### The Problem: "It Works on My Machine"

You run tests locally. All green. You push to GitHub. CI/CD fails. What happened?

**The answer:** Your local environment is NOT the same as CI/CD. Subtle differences accumulate into real bugs.

### Key Differences Between Local and CI/CD

#### 1. Fresh Environment Every Time

**Local:**

- `node_modules/` cached from previous installs
- Build artifacts might be stale
- OS-level packages installed weeks ago
- Environment variables from previous runs

**CI/CD:**

- Fresh Ubuntu container on EVERY run
- `node_modules/` installed from scratch
- No cached build artifacts
- Clean environment variables

**Real Example from Phase 3.3:**

**Bug:** Tests used hardcoded string `'broteinbuddy-state'` for localStorage key instead of the `STORAGE_KEY` constant from `storage.ts`.

**Why it passed locally:**

- Previous test runs had populated localStorage with the correct key
- Even though tests used wrong key, data from previous runs was still there
- Tests read stale data and passed

**Why it failed in CI/CD:**

- Fresh container = empty localStorage
- Tests set data with wrong key: `'broteinbuddy-state'`
- App read with correct key: `'BROTEINBUDDY_APP_STATE'`
- App found no data → "No flavors configured" error
- 4 tests failed

**Fix:**

```typescript
// Before (hardcoded, fragile)
await context.addInitScript(() => {
  localStorage.setItem('broteinbuddy-state', JSON.stringify({ ... }));
});

// After (uses constant, robust)
import { STORAGE_KEY } from '../../src/lib/storage';

await context.addInitScript((key) => {
  localStorage.setItem(key, JSON.stringify({ ... }));
}, STORAGE_KEY);
```

**Lesson:** Constants exist for a reason. Use them EVERYWHERE, including tests.

#### 2. Different Operating Systems

**Local (macOS/Windows):**

- macOS file system (case-insensitive on APFS)
- macOS font rendering (subpixel antialiasing)
- macOS Safari/Chrome behavior
- Native dependencies compiled for macOS

**CI/CD (Linux):**

- Linux file system (case-sensitive)
- Linux font rendering (FreeType)
- Headless browsers (no GPU acceleration)
- Native dependencies compiled for Linux

**Potential Issues:**

- File paths that work on macOS fail on Linux (`src/Components/Button.svelte` vs `src/components/Button.svelte`)
- Font metrics differ (text might wrap differently)
- SVG rendering differences (stroke width, antialiasing)
- Native modules might behave differently

**Example (not from this PR, but common):**

```typescript
// This works on macOS (case-insensitive)
import Button from './Components/button.svelte';

// This fails on Linux (case-sensitive)
// Error: Cannot find module './Components/button.svelte'
```

**Best Practice:** Use lowercase for all file/directory names, or enforce strict casing in your linter.

#### 3. Worker Parallelization

**Local (8 workers on my M1 Mac):**

- Playwright runs 8 tests in parallel
- Tests complete in ~2 minutes
- Race conditions might not surface (tests finish before state conflicts)

**CI/CD (1 worker on GitHub Actions):**

- Playwright runs tests sequentially
- Tests complete in ~8 minutes
- Race conditions MORE likely to surface (longer test duration exposes timing bugs)

**Why Sequential Execution Exposes Bugs:**

Imagine two tests that share state (e.g., localStorage):

**Parallel execution (8 workers):**

```
Test A: ----[runs in 2s]----
Test B:     ----[runs in 2s]----
            ^ Both finish before interfering
```

**Sequential execution (1 worker):**

```
Test A: ----[runs in 2s]----
                            Test B: ----[runs in 2s]----
                                    ^ Test B sees leftover state from Test A
```

**Real Example from Phase 3.3:**

**Bug:** Random selection tests occasionally failed with timeout waiting for `/random/confirm` navigation.

**Why it sometimes passed locally:**

- Parallel execution → tests ran in isolation
- Fast machine → navigation completed before timeout

**Why it sometimes failed in CI/CD:**

- Sequential execution → exposed timing issues
- Slower container → navigation took longer
- Increased timeout from 10s → 30s to accommodate slower CI/CD environment

**Fix:**

```typescript
// Before (too aggressive for CI/CD)
await page.waitForURL('/#/random/confirm', { timeout: 10000 });

// After (accommodates slower environments)
await page.waitForURL('/#/random/confirm', { timeout: 30000 });
```

**Lesson:** Timeouts that work locally might be too aggressive for CI/CD. Be generous with timeouts in E2E tests (30s is reasonable).

#### 4. Environment Configuration

**Local (.env.local):**

- Custom port for worktree development: `VITE_PORT=5174`
- API keys for development
- Debug flags enabled
- Personal preferences

**CI/CD (no .env.local):**

- Default port: `5173`
- No API keys (uses mocked data)
- Production-like configuration
- Minimal environment variables

**Real Example from Phase 3.1:**

**Bug:** Tests failed in CI/CD because `vite.config.ts` didn't load `.env.local`.

**Why it passed locally:**

- `.env.local` existed with `VITE_PORT=5174`
- Vite loaded it automatically
- Tests connected to correct port

**Why it failed in CI/CD:**

- No `.env.local` in CI/CD
- Vite used default port, but config tried to read `process.env.VITE_PORT`
- `process.env.VITE_PORT` was `undefined` → parseInt(undefined) → NaN → Vite crashed

**Fix:**

```typescript
// Before (crashed if .env.local missing)
server: {
  port: parseInt(process.env.VITE_PORT),
}

// After (graceful fallback)
import dotenv from 'dotenv';
dotenv.config({ path: '.env.local' });

server: {
  port: parseInt(process.env.VITE_PORT || '5173'),
}
```

**Lesson:** Always provide fallback values for environment variables. CI/CD might not have your `.env.local`.

#### 5. Platform-Specific Font Rendering

**Local (macOS):**

- System fonts: SF Pro, Helvetica Neue
- Subpixel antialiasing
- Retina display rendering

**CI/CD (Linux):**

- System fonts: Liberation Sans, DejaVu Sans
- Standard antialiasing
- Headless browser rendering

**Potential Issues:**

- Text wrapping differs (different font metrics)
- Contrast calculations might vary slightly
- Snapshot tests might fail (pixel-perfect comparisons)

**Example (hypothetical):**

```css
/* This text might wrap on Linux but not macOS */
.button {
  width: 100px;
  font-family: system-ui, sans-serif; /* Different fonts on different platforms */
}
```

**Best Practice:** Use flexible layouts (`min-width`, `max-width`) instead of fixed widths for text.

## How to Minimize CI/CD Surprises

### 1. Run Full Test Suite Locally Before Pushing

**Command:**

```bash
# Run EVERYTHING that CI/CD runs
npm run lint && \
npm run format:check && \
npm run typecheck && \
npm run test:coverage && \
npm run test:e2e && \
npm run build
```

**Why:** Catches 80% of issues before they hit CI/CD.

**When to do this:**

- Before pushing to remote
- Before creating a PR
- After major refactors

**Trade-off:** Takes 5-8 minutes locally, but saves 30 minutes of CI/CD feedback loops.

### 2. Use Same Test Data Constants Everywhere

**Pattern:**

```typescript
// src/lib/storage.ts
export const STORAGE_KEY = 'BROTEINBUDDY_APP_STATE';

// tests/e2e/accessibility.spec.ts
import { STORAGE_KEY } from '../../src/lib/storage';

test.beforeEach(async ({ context }) => {
  await context.addInitScript((key) => {
    localStorage.setItem(key, JSON.stringify({ ... }));
  }, STORAGE_KEY);
});
```

**Why:** Eliminates hardcoded strings that drift out of sync.

**Anti-pattern:**

```typescript
// DON'T DO THIS (hardcoded strings)
localStorage.setItem('broteinbuddy-state', ...); // Wrong key!
localStorage.setItem('app-state', ...);          // Also wrong!
```

### 3. Test in Clean Environments Occasionally

**Pattern:**

```bash
# Clear everything and reinstall
rm -rf node_modules dist .vite
npm ci                    # Clean install (uses package-lock.json exactly)
npm run build
npm run test:e2e
```

**Why:** Simulates CI/CD fresh environment.

**When to do this:**

- Before major releases
- After adding/removing dependencies
- When "it works locally but fails in CI/CD"

### 4. Monitor CI/CD Output for Patterns

**Red flags in CI/CD logs:**

- Timeouts (need more generous timeouts)
- "Cannot find module" (case sensitivity issues)
- "localStorage is not defined" (environment setup issues)
- "fetch is not defined" (Node version differences)

**Pattern:**

```bash
# Download CI/CD logs and search for errors
gh run download <run-id>
grep -r "Error\|Failed\|Timeout" ./
```

### 5. Document Platform-Specific Behaviors

**Example from BroteinBuddy's DEVELOPING.md:**

```markdown
## Platform Differences

### localStorage Key

- Constant: `STORAGE_KEY` from `src/lib/storage.ts`
- Value: `'BROTEINBUDDY_APP_STATE'`
- Tests MUST use this constant, not hardcoded strings

### Font Rendering

- Local (macOS): SF Pro, Helvetica Neue
- CI/CD (Linux): Liberation Sans, DejaVu Sans
- Use flexible layouts to accommodate font metric differences
```

**Why:** New team members (or future you) won't repeat the same mistakes.

### 6. Use Generous Timeouts for E2E Tests

**Pattern:**

```typescript
// Generous timeout for slow CI/CD environments
await page.waitForURL('/#/random/confirm', { timeout: 30000 }); // 30s

// Even more generous for complex workflows
await page.waitForSelector('.loaded', { timeout: 60000 }); // 60s
```

**Why:**

- CI/CD containers are slower than local machines
- Network latency varies
- Parallel test execution can slow individual tests
- False negatives are worse than slow tests

**When to use shorter timeouts:**

- Unit tests (milliseconds)
- Integration tests (seconds)
- Operations that SHOULD be fast (button clicks)

**When to use longer timeouts:**

- E2E navigation (page loads)
- API calls (network requests)
- Animations (wait for transitions)

## Design Trade-offs

### What We Optimized For

1. **Comprehensive CI/CD**: Catch bugs before they reach users
2. **Fresh environment**: Prevent "works on my machine" syndrome
3. **Automated testing**: 290 tests (207 passing, 68 skipped, 15 integration disabled)
4. **Cross-platform consistency**: Works on macOS, Linux, Windows

### What We Sacrificed

1. **CI/CD speed**: 8-10 minutes (up from ~5 minutes)
2. **Local test speed**: Full suite takes 5-8 minutes
3. **Development velocity**: Accessibility tests add overhead

### When Trade-offs Make Sense

**Longer CI/CD is worth it when:**

- Shipping to production (users expect quality)
- Multiple contributors (prevent breaking each other's work)
- Complex app (lots of integration points)

**Faster CI/CD might be worth it when:**

- Solo developer (you can test locally)
- Early prototyping (move fast, fix bugs later)
- Infrequent deployments (weekly releases, not daily)

## Real-World Compromises

### CI/CD Time: 5 minutes vs 10 minutes

We chose to accept **8-10 minute CI/CD runs** to gain comprehensive accessibility testing.

**Alternative:** Skip accessibility tests in CI/CD, run them manually before releases.

**Why we didn't:**

- Accessibility regressions are HARD to catch manually
- "Run manually before releases" becomes "we forgot to run them"
- 3-5 minute increase is acceptable for quality

**When to optimize CI/CD:**

- Run time > 15 minutes (developer frustration)
- Frequent pushes (10+ per day)
- Large team (blocking others' work)

### Test Parallelization: 8 workers vs 1 worker

CI/CD runs with **1 worker** (sequential), local runs with **8 workers** (parallel).

**Why CI/CD is sequential:**

- GitHub Actions free tier: 1 concurrent job
- More reliable (no race conditions)
- Easier to debug (clear execution order)

**Why local is parallel:**

- Developer time is valuable (2 min vs 8 min)
- Modern machines have cores to spare
- Immediate feedback during development

**Trade-off:**

- Parallel execution might hide timing bugs
- Sequential execution exposes those bugs in CI/CD
- Mitigate with generous timeouts and isolation

### Skipping Tests: 68 skipped vs 0 skipped

We skipped **68 tests for advanced features** deferred to issue #68.

**Why we skipped instead of deleting:**

- Tests document future requirements
- Easy to re-enable when implementing features
- Maintains test coverage metrics

**When to skip tests:**

- Feature intentionally deferred
- Test is flaky and needs investigation
- Platform-specific behavior (skip on certain OS)

**When to delete tests:**

- Feature removed permanently
- Test is duplicated elsewhere
- Test no longer makes sense (requirements changed)

## What You Should Learn From This

### 1. CI/CD is Not "Just Running Tests Again"

**Pattern:** CI/CD runs in a fundamentally different environment.

**Why:** Fresh container, different OS, different resource constraints, different parallelization.

**Key differences:**

- No cached dependencies (`node_modules/` installed fresh)
- Different OS (Linux vs macOS/Windows)
- Different environment variables
- Different execution order (sequential vs parallel)

**Lesson:** Never say "the tests pass locally, CI/CD must be wrong." CI/CD found a real bug.

### 2. Use Constants, Not Magic Strings

**Pattern:**

```typescript
// Define once
export const STORAGE_KEY = 'BROTEINBUDDY_APP_STATE';

// Use everywhere
import { STORAGE_KEY } from './storage';
localStorage.setItem(STORAGE_KEY, data);
```

**Why:** Constants stay in sync. Magic strings drift.

**Common mistakes:**

- Hardcoding API endpoints
- Hardcoding localStorage keys
- Hardcoding route paths
- Hardcoding CSS class names

### 3. Fresh Install Before Major Milestones

**Pattern:**

```bash
# Simulate CI/CD locally
rm -rf node_modules dist
npm ci
npm run build
npm run test:e2e
```

**When to do this:**

- Before creating a PR
- Before releases
- After dependency changes
- When "it works locally but fails in CI/CD"

**Why:** Catches stale dependency issues, build artifact problems, environment drift.

### 4. Generous Timeouts for E2E Tests

**Pattern:**

```typescript
// Don't be stingy with E2E timeouts
await page.waitForURL('/#/page', { timeout: 30000 }); // 30s, not 3s
```

**Why:**

- CI/CD is slower than local
- Network latency varies
- Prevents flaky tests

**When to use short timeouts:**

- Unit tests (milliseconds)
- Operations that should be instant (synchronous functions)

**When to use long timeouts:**

- E2E navigation (30-60s)
- API calls (30-60s)
- Animations (5-10s)

### 5. Document Environment Assumptions

**Pattern:** Add a "Platform Differences" section to DEVELOPING.md.

**What to document:**

- Environment variables and fallbacks
- OS-specific behaviors
- Font rendering differences
- File system case sensitivity
- Any "this works on X but not Y" issues

**Why:** Prevent future developers (or future you) from repeating the same mistakes.

### 6. Monitor CI/CD Logs for Patterns

**Pattern:**

```bash
# Download logs and analyze
gh run download <run-id>
grep -r "Error\|Timeout\|Failed" ./
```

**Common patterns:**

- Timeouts → increase timeout values
- "Cannot find module" → case sensitivity or path issues
- "X is not defined" → environment setup issues
- Flaky tests → race conditions or timing bugs

**Why:** CI/CD logs reveal systemic issues, not just individual test failures.

## Questions to Think About

1. **When is it OK to skip CI/CD?** Are there scenarios where local testing is "good enough"? (Hint: Personal projects, prototypes, but NOT production apps.)

2. **How do you balance CI/CD speed with thoroughness?** If CI/CD takes 20 minutes, developers will skip it. How do you optimize without sacrificing quality?

3. **What's the cost of a bug in production vs CI/CD time?** If CI/CD saves 1 production bug per month, how much time is that worth? (Hint: Production bugs cost 10-100x more than CI/CD time.)

4. **How do you handle flaky tests?** Retry 3 times? Skip and investigate later? Fail the build? (Hint: Flaky tests erode trust in CI/CD. Fix them immediately.)

5. **Should E2E tests run on every commit?** Or only on PRs? Or only nightly? (Hint: Depends on team size, commit frequency, and test duration.)
