## Why This Document Exists

PR #96 is large. It rewrites the visual language of the whole app, replaces the
navigation model, restructures three screens, and — partway through — absorbs an
entire Supabase auth/sync backend that landed on `main` while this branch was in
flight. That last part is the interesting one.

Most teaching docs in this series teach a feature. This one teaches a
_situation_: what to do when your long-lived feature branch and the `main` you
forked from have both grown in different directions, and now they have to become
one tree again. That situation is uncomfortable, it's common, and it's where a
lot of real bugs are born. So we're going to spend the first and longest part of
this document on exactly that, and treat the design system and the responsive
shell — both genuinely worth learning — as the supporting acts.

If you're maintaining this codebase, here's the one-sentence version: **the
branch did not just merge `main` and move on; it merged `main`, then did the
unglamorous work of making the merged-in code look and behave like it was
designed here all along.** That second step is the lesson.

Three ADRs and two design docs back this work. Read them alongside this:

- [`docs/adr/014-cloud-dancer-token-system.md`](../adr/014-cloud-dancer-token-system.md) — the OKLCH token decision
- [`docs/adr/015-persistent-tab-navigation.md`](../adr/015-persistent-tab-navigation.md) — the three-tab shell decision
- [`docs/design/2026-ux-refresh/README.md`](../design/2026-ux-refresh/README.md) — the high-fidelity design handoff

## Part One — The Diverged-Branch Integration

### What "Diverged" Actually Means Here

When you branch off `main`, you and `main` share a common ancestor. As long as
only you commit, your branch is just "ahead." You can fast-forward back with no
drama.

"Diverged" means **both sides committed.** While `feature/ui-refresh-2026` was
rewriting the UI, somebody else shipped PR #95 (Supabase sync + magic-link auth)
and PR #97 (realtime sync + offline resilience) straight to `main`. Now the
common ancestor is in the past for _both_ branches, and the two histories have
genuinely different content. Git can't fast-forward anything. Somebody has to
decide how the two timelines reconcile.

Here's the part that makes it spicy, and it's worth saying plainly: the two
efforts were not independent. The sync work and the UI refresh **both touch the
UI.** Sync added `SyncStatusBadge`, `SyncAccountModal`, and
`ConflictResolutionModal`, and it wired the first two _into the Inventory screen_
— the exact screen the refresh was tearing apart and rebuilding. That overlap is
where the conflict lives.

A useful mental model: a merge conflict is not git failing. It's git
**escalating an editorial decision to a human** because two changes touched the
same lines and git has no opinion about which is correct. Your job at a conflict
is not "make git happy." It's "decide what the code should be."

### Merge vs. Rebase: The Decision

You have two ways to reconcile a diverged branch. Both end with your branch
containing `main`'s commits. They differ in _how the history reads afterward_.

**Rebase** replays each of your branch's commits, one at a time, on top of the
current `main`. The result is a straight line — it looks like you started your
work _after_ the sync PRs landed. It's clean. Bisecting is pleasant. But you
resolve conflicts **once per replayed commit that touches the contested files**,
and you're rewriting commits that, here, were already pushed and already part of
an open PR.

**Merge** creates one new commit (`5ac9d07`) with two parents — your branch tip
and `origin/main`. History stays truthful: it shows two lines of work that
genuinely happened in parallel and then joined. You resolve conflicts **once,
total**, in the merge commit.

This branch chose **merge**, and for a long-lived branch with an open PR that is
the right call. Walk the reasoning the way you would for any branch:

- _Is the branch shared / does it have an open PR?_ Yes — PR #96 exists, CI runs
  against it, a reviewer may already be looking. Rebasing rewrites every commit
  hash. Anyone who pulled the branch now has a fork in the road, and the PR's
  review history detaches from the commits it reviewed. **Rewriting public
  history is the cost rebase quietly charges, and it's a big one.**
- _How tangled is the overlap?_ The UI refresh rewrote `App.svelte` and
  `Inventory.svelte` across many commits. A rebase would stop and ask you to
  resolve the sync-vs-refresh conflict _again on every one of those commits_ —
  and the intermediate states are half-built, so you'd be resolving conflicts
  against code that doesn't even run yet. Painful and error-prone.
- _Does the parallelism matter?_ Yes. "The sync backend and the UI refresh were
  built at the same time and then integrated" is a true and useful fact. A merge
  commit records it. A rebase erases it and pretends the refresh came second.

The merge commit message, `5ac9d07`, is worth reading in full with `git show
5ac9d07`. It does the thing every good merge commit should do: it doesn't just
say "merged main," it **writes down every editorial decision** so the next
person doesn't have to reverse-engineer them from the diff.

> **The general rule.** Rebase private, not-yet-shared, still-messy local work to
> tidy it before anyone sees it. Merge when the branch is public, long-lived, or
> has an open PR. The deciding question is never "which history looks prettier" —
> it's "will rewriting these commit hashes hurt anyone, and does the parallel
> story deserve to be told." Here, both answers said merge.

### Why Only Two Files Truly Conflicted

The sync merge added or changed _27 files_ (`git show 5ac9d07 --stat`). Most of
them — `src/lib/supabase.ts`, `src/lib/auth.ts`, `src/lib/sync-coordinator.ts`,
the migrations, the unit tests — were **brand-new files**. A new file can't
conflict; there's nothing on your side to disagree with. Git just adds it.

Conflicts only happen where _both_ branches edited _the same region of the same
existing file._ Run the numbers and exactly two files qualify:

- **`src/App.svelte`** — sync needed to add `initializeSync()` to `onMount` and
  mount `<ConflictResolutionModal />`. The refresh had rewritten `App.svelte`
  top-to-bottom into the app-shell. Same file, overlapping regions: conflict.
- **`src/routes/Inventory.svelte`** — sync had wired its badge and modal into the
  old Inventory screen. The refresh had rewritten that screen into
  Active/Storage sections. Same file, heavily overlapping: conflict.

Everything else slotted in cleanly. This is a genuinely reassuring property to
internalize: **the conflict surface of a merge is not "how big is the other
PR" — it's "how much did both sides edit the same existing lines."** Two efforts
can each be enormous and still merge almost cleanly if they mostly touch
different files. A sync layer that lives in its own `src/lib/*.ts` modules is
_designed_ to merge cleanly into a UI refresh, and that's not luck — it's what
good module boundaries buy you.

### Resolving `App.svelte`: the Union-of-Imports Move

Run `git show 5ac9d07 -- src/App.svelte` and you can see the conflict resolution
inline. The merge diff (the `diff --cc` "combined diff" format) shows three
columns of context, and what happened is instructive.

The import block is the textbook case. The refresh side added:

```ts
import AppNav from './lib/components/AppNav.svelte';
import PickResultSheet from './lib/components/PickResultSheet.svelte';
import AddInventoryPanel from './lib/components/AddInventoryPanel.svelte';
import { addInventoryOpen } from './lib/panel-state';
```

The `main` side added:

```ts
import ConflictResolutionModal from './lib/components/ConflictResolutionModal.svelte';
import { initializeSync } from './lib/sync-coordinator';
```

The resolution: **keep both.** This is the _union of imports_, and it's the
single most common merge resolution you'll ever perform. The reasoning is dead
simple — these imports don't compete. They're not two answers to one question;
they're two unrelated additions that happened to land on adjacent lines. The
right answer to "A or B?" is sometimes "A and B," and recognizing when you're in
that case is half the skill.

The mount lifecycle is more interesting. The refresh's `onMount` and the sync's
`onMount` each added a line. Resolution — again — the union: keep the welcome-
modal check _and_ call `initializeSync()`. But notice the editorial judgment
hiding in there. The merge commit message says `ConflictResolutionModal`
"auto-merged into the mount lifecycle and template." That word _auto-merged_
matters: git itself could place that one because the surrounding lines were
similar enough. The human's job was the _imports_, where git saw two competing
edits to the same line and bailed.

> **The lesson.** When a conflict is "two parties each _added_ something," the
> default resolution is almost always "keep both, in a sensible order." A
> conflict is only a genuine _either/or_ when the two sides changed _the same
> thing to two different values_. Train yourself to ask, at every conflict
> marker: "is this an _addition_ collision or a _value_ collision?" Additions
> merge. Values need a decision.

### Resolving `Inventory.svelte`: Deleting Working Code on Purpose

`Inventory.svelte` is the hard one, and it's hard in a way that has nothing to do
with git mechanics.

On `main`, `Inventory.svelte` contained a working, tested, shipped Sync
button — plus the badge and modal wired right into the inventory header. That
code was _correct_. It passed review. It passed CI. Users were using it.

The refresh resolution **threw it away.** The merge commit says so, flatly:

> kept the refreshed version. main's inline Sync button/badge/modal are
> intentionally dropped here — the sync surface moves to the More tab and a
> global topbar badge in the follow-up integration commits.

Sit with how counterintuitive that is. The instinct at a merge conflict — a
strong, almost moral instinct — is _preserve everything_. Both sides worked
hard; losing either feels like waste; surely the safe move is to keep it all.

That instinct is wrong here, and understanding _why_ is the deepest lesson in
this whole document.

The refresh isn't a coat of paint. ADR-015 made a real _architectural_ decision:
sync is a secondary, occasional concern, so it belongs on the **More tab** and as
a slim **global topbar badge** — not bolted into the Inventory header competing
for attention with the boxes. The `main` version of the Sync button wasn't
"wrong code." It was **right code for a navigation model that no longer exists.**
The refresh deleted the button-grid Home, deleted the per-screen header pattern,
and introduced three persistent tabs. In that new world, an inline Inventory-
header Sync button isn't a feature to preserve — it's a _contradiction_ of the
design the branch exists to ship.

So the resolution drops it. But — and this is the part that makes it
_responsible_ rather than reckless — the merge commit makes a **promise**: "the
sync surface moves to the More tab and a global topbar badge **in the follow-up
integration commits.**" The functionality isn't deleted. It's _relocated_, and
the merge commit names where it's going so a reviewer can verify the promise was
kept.

It was kept. Read the commits right above the merge:

- `dd79be8 Add a Sync & sign-in row to the More screen`
- `804f574 Mount SyncStatusBadge in the global topbar`

The capability `main` put in the Inventory header is now reachable from More and
visible as a topbar badge — in the places ADR-015 says it belongs.

> **The lesson — and it's a big one.** At a merge conflict, "keep both" is the
> right _default_ but not a _law_. When one side made an architectural decision
> that genuinely supersedes the other side's code, the correct resolution is to
> **delete the superseded code and re-implement its capability inside the new
> architecture.** What makes that safe instead of destructive is rigor: (1) say
> _explicitly_ in the merge commit that you're dropping it and _why_, (2) name
> where the capability is being re-homed, and (3) actually do the re-homing in
> named follow-up commits a reviewer can check. Silent deletion is a bug.
> _Documented, promised, and delivered_ relocation is good engineering.

### The Discipline of Re-Styling Merged-In Features

Here's where most "merge `main` and move on" branches quietly fail, and where
this one earns its keep.

The merge made the code _compile_. It did not make the code _belong_. The merge
commit is candid about the loose end it leaves:

> The three sync UI components still reference old `--color-*` tokens; they get
> the Cloud Dancer makeover in the commits that follow.

Think about what that means concretely. After `5ac9d07`, the app builds and
runs. But `SyncStatusBadge`, `SyncAccountModal`, and `ConflictResolutionModal`
were authored against the _pre-2026_ design system — `--color-primary`,
`--radius-base`, the old hex-ish tokens. The refresh **deleted those token
names** (more on that in Part Two). So the sync components are now referencing
CSS custom properties that **no longer exist.** A `var(--color-primary)` with no
`--color-primary` defined doesn't crash — CSS just falls back to the property's
initial value or transparent. The components would render. They'd render
_wrong_: a centered modal with default-ish colors, visibly from a different app,
bolted onto the side of a freshly redesigned product.

A branch in a hurry stops at "it compiles." This branch did not. Look at the
integration commits as a _sequence_, because the sequence is the lesson:

1. **`1714c2c` — Add `--success` and `--info` semantic tokens.** The badge has
   genuine _synced / offline / error_ states. The new minimal palette had only
   `--danger`. Before you can restyle the badge you must first _give the design
   system the tokens the badge needs._ You don't hack hardcoded greens into a
   component — you extend the system.
2. **`1153ff5` — Migrate sync components to Cloud Dancer tokens.** Now remap all
   three components: dead `--color-*` → live `accent` / `--ink-*` / `--line-1` /
   `--surface-*` / the new semantic tokens. The commit message calls it "pure
   cosmetic; no logic change" — a deliberately _small, reviewable_ commit that
   does exactly one thing.
3. **`cf0b661` — Restructure `SyncAccountModal` into a responsive sheet/panel.**
   The deepest change. `main`'s `SyncAccountModal` was a centered `<Modal>`. But
   the refresh established a _house pattern_: overlays are **sheets** — bottom
   sheet on phone, right-side panel on laptop — exactly like `AddInventoryPanel`
   and `FlavorPickerSheet`. So the merged-in modal is rebuilt to that pattern. It
   now mounts once at the App level and is driven by a `syncSheetOpen` store
   (`src/lib/sync-ui-state.ts`), matching how every other sheet on the branch
   works.
4. **`dd79be8`, `804f574` — Re-home the entry points.** The More-screen row and
   the topbar badge — fulfilling the merge commit's promise.
5. **`78fb300` — Extract sync badge display logic into a tested util.** The badge
   collapses sync status + a pending flag into a label and a variant. The branch
   pulls that into a _pure_ `sync-status-badge-utils.ts` with its own unit tests
   — because that is the project's standard split (it's how `numberpad-utils`
   and `modal-utils` already work). The merged-in feature is held to the
   _project's_ testing conventions, not grandfathered in under its own.

That is what "first-class citizen" means in practice. After these commits the
sync UI doesn't _look_ merged-in. It looks like it was designed alongside the
refresh: same tokens, same sheet pattern, same store-driven open/close, same
pure-util-plus-test structure. A new maintainer reading `SyncAccountModal.svelte`
today cannot tell it arrived via a merge — and that is precisely the goal.

> **The lesson.** Integrating a diverged branch has _two_ phases, and the second
> is the one people skip. Phase one: make it compile (the merge). Phase two: make
> it _belong_ — re-token it, re-pattern it, re-home it, and hold it to the
> conventions of the branch it's joining. A feature that visibly looks bolted-on
> is a half-done integration. The tell is always the same: mismatched colors,
> a component using a pattern nothing else uses, logic that isn't tested the way
> the rest of the codebase tests logic. If you ever merge `main` into a branch
> with a different design language, budget Phase Two. It's not polish. It's the
> job.

### The Bug the Merge Quietly Created

Now the part that should make you a little paranoid in the best way.

A merge can compile, pass every existing test, and still introduce a _runtime_
bug — because the two sides each made an assumption that was true in isolation
and false once combined. There is no conflict marker for "your assumption no
longer holds." Git can't see assumptions.

Commit `994d620` is exactly this. Read its message:

> Fix InventoryBoxEdit discarding edits on a background store update
>
> The reseed `$effect` read the box through the reactive `$appState`, so every
> store mutation re-fired it and overwrote the working copy. Once a user is
> signed in to sync, the coordinator's `replaceAppState` pulls run in the
> background — a pull mid-edit silently discarded the user's changes.

Trace it, because the _shape_ of this bug recurs constantly.

`InventoryBoxEdit` is a classic preview-then-commit screen (the pattern teaching
doc 2.7 covers): it copies the box's `quantity` and `isOpen` into local working
state, lets you edit freely, and only writes back on Save. To re-seed that
working copy when you navigate to a _different_ box, it ran a `$effect`.

In the pre-sync world, that `$effect` was _fine_. The only thing that ever
mutated `$appState` was the user, on this device, deliberately. So "re-seed when
the store changes" was a perfectly safe proxy for "re-seed on navigation."

Sync **breaks that assumption.** The sync coordinator subscribes to `appState`,
and a realtime push from your _other_ device — or a pull on reconnect — calls
`replaceAppState` to apply server state. That mutates `$appState` **in the
background, while you're mid-edit.** The old `$effect` saw the mutation, re-fired,
and clobbered your half-typed quantity with the store's value. No error. No
conflict. Your edit just _vanished_ — and only on a signed-in device, only when
a sync happened to land during an edit. That is the worst class of bug: silent,
intermittent, and invisible to every test written before the merge.

The fix is small and worth memorizing:

```ts
import { untrack } from 'svelte';

$effect(() => {
  const id = boxId; // tracked dependency
  const current = untrack(() => $appState.boxes.find((b) => b.id === id));
  if (current) {
    quantity = current.quantity;
    isOpen = current.isOpen;
  }
});
```

`untrack()` tells Svelte 5: _run this code, but do not subscribe the effect to
anything you read inside it._ Now the effect's only tracked dependency is
`boxId`. It re-seeds the form when you navigate to a different box — which is
what we actually wanted all along — and it stays completely deaf to background
`$appState` churn from sync. The box _lookup_ still reads fresh store data; it
just doesn't _trigger_ on store changes.

The meta-lesson is bigger than `untrack`. **A merge is a hypothesis: "these two
bodies of work compose."** A green build only tests the hypothesis against
behaviors that were _already_ tested. The genuinely dangerous bugs live in the
interaction the merge _creates_ — here, "background state mutation" was a thing
that simply did not exist before sync and the UI refresh shared a tree. After
any non-trivial merge, the question to ask is not "do the tests pass?" It's
**"what is now _possible_ that wasn't possible on either branch alone?"** Then go
hunt for the code that quietly assumed it couldn't happen.

### The Specs the Refresh Quietly Broke

The flip side of the same coin. The merge didn't only let new bugs in — it
exposed that the refresh had **broken the e2e suite**, in a way that, again, no
conflict marker announced.

End-to-end tests drive the app the way a user does: click the thing labeled X,
assert the thing labeled Y appears. That makes them brutally sensitive to UI
change — which is the entire point of having them, and also why a UI refresh
detonates them. Three flavors of breakage showed up, and each teaches a distinct
e2e lesson.

**1. The flow no longer exists.** `5472410` deletes `home.spec.ts`,
`random-flow.spec.ts`, `manual-flow.spec.ts`, `favorite-flow.spec.ts` outright.
ADR-015 deleted the `Random` and `RandomConfirm` routes and replaced the Home
button-grid with the Pick screen. A spec for a deleted route isn't a _failing_
test — it's a _dead_ test. The right move is delete it and **re-establish its
coverage in a spec for the screen that replaced it** — here, a new
`pick.spec.ts` exercising the pool tap, the result sheet, the "Taking it"
decrement, and the favorite/manual paths. Coverage _migrates_; it isn't lost.

**2. The selector moved.** `701998b`, `689b3b3`, `0e1a9b8` repair specs that
still test a real flow but were reaching for it the old way. `0e1a9b8` is the
sharpest example — read its message:

> it opened the panel only via the FAB — hidden on laptop widths, where the
> topbar "+ Add inventory" button is the opener — so every test failed on the
> Desktop Chrome project

The refresh made Add Inventory's _opener_ responsive: a floating FAB on phone, a
topbar button on laptop. The spec only knew about the FAB, so it passed on Mobile
Safari and failed on Desktop Chrome. The fix is a _viewport-aware opener helper_
— the test learns the same responsive truth the app already knows.

**3. The assertion encodes a stale mental model.** This one is subtle and the
most worth absorbing. Several specs asserted `toBeHidden()` on a closed panel or
sheet. Under the refresh that assertion **can never be true** — and the
component is not buggy. The refresh's sheets _stay mounted_ and slide off-screen
via `transform: translateY(100%)` so they have a "from" position to animate from
(that's the fix in `b0ca42f`). A parked sheet is mounted, present in the DOM,
just translated out of view. `toBeHidden()` expects `display: none` or removal
from the DOM; it will wait, then fail. The repair switches the assertion to
check `aria-hidden` instead — which is _also_ the more correct accessibility
assertion. The old test wasn't just using a stale _selector_; it was asserting
against a stale _model of how "closed" works._

Notice the through-line. Two more post-merge commits — `b0ca42f` (sheet slides
instead of pops) and `e53fb47` (sheet dialogs need a grouping role and
Escape-to-close) — are _code-review blockers_, found by a human reviewing the
PR, not by a test. CI being green and a reviewer being satisfied are two
different bars, and a diverged-branch integration has to clear both. The e2e
repairs cleared CI; the reviewer fixes cleared review.

> **The lesson.** A UI refresh _will_ break your e2e suite, and that is the suite
> doing its job. The discipline is to triage each failure into one of three
> buckets: **(a) the flow is gone** — delete the spec, re-home its coverage in
> the replacement screen's spec; **(b) the selector moved** — update the spec to
> the new affordance, and if the affordance is now responsive, make the _test_
> responsive too; **(c) the assertion encodes a stale mental model** — the
> deepest case — fix the _assumption_, not just the selector. A test asserting
> `toBeHidden()` on something that is now "present but translated away" is
> wrong about the world, and updating the assertion to `aria-hidden` makes it
> both correct and more accessible. Never "fix" a failing e2e test by deleting
> the assertion. Figure out which bucket it's in.

## Part Two — The OKLCH Cloud Dancer Token System

With the integration story told, here's the design system the merged-in sync UI
had to be dragged onto. It's worth understanding in its own right — it's a small,
opinionated system with a few genuinely clever moves. The full rationale is in
[ADR-014](../adr/014-cloud-dancer-token-system.md); this is the mentor's tour.

### Why Perceptual Lightness Is the Whole Point

Start with the problem. The pre-2026 app rendered each flavor's box card by
hashing the flavor's ID into an HSL color: fixed saturation 65%, fixed lightness
55%, hue from the hash. Sounds principled. It isn't, and here's the exact reason.

**HSL's "L" is not perceptual.** `hsl(60, 65%, 55%)` (a yellow) and
`hsl(240, 65%, 55%)` (a blue) claim the _same_ 55% lightness. Your eye disagrees,
emphatically — the yellow looks far brighter than the blue. HSL lightness is a
number about the _color model's math_, not about _how bright the color looks to a
human._ So a hash-to-HSL palette produced exactly the failure ADR-014 names:
"some hues landed dark and busy, others washed-out and indistinguishable." Two
flavors could hash to colors that _looked the same_. For an app whose entire job
is "tell me which flavor this box is at a glance," that is a real defect.

**OKLCH fixes this at the color-space level.** OKLCH is `L` (lightness), `C`
(chroma / saturation), `H` (hue), and its `L` is _perceptually uniform_: two
OKLCH colors with the same `L` actually _look_ equally bright, whatever their
hue. That single property is the foundation everything else in the system stands
on. When the palette says "every flavor `fill` is at `L=0.92`," that is a real,
keepable promise — every flavored box reads at the same brightness against the
page, so they're a _coherent set of tints_, not a brightness lottery.

There's a second payoff, and it's the one that makes the system pleasant to
_maintain_. OKLCH's three axes are _independent_. "Same hue, slightly darker" is
literally one number: drop `L`, leave `C` and `H` alone. With hex you'd be doing
a color-space round-trip in your head or in a tool. That independence is why the
flavor palette can hand you a _coordinated triple_ per flavor — `fill`, `accent`,
`ink` — that are obviously the same hue at three lightness levels. They're three
`L` values on one `H`. Try expressing "the same family, three lightnesses" in
hex and you'll feel the difference immediately.

### The Surface / Ink / Line / Accent Architecture

Open [`src/styles/variables.css`](../../src/styles/variables.css) and read the
`:root` block. The system is deliberately small and grouped:

- **Surfaces** — four warm cream tones, themed on Pantone's 2026 Color of the
  Year, "Cloud Dancer." `--surface-app` (the page), `--surface-card` (cards, even
  softer than white), `--surface-sunk` (inset wells), `--surface-hover`. They
  share hue `85` and step only in lightness — the cream-to-milk-to-fog family.
- **Ink** — four warm near-blacks for text: `--ink-1` primary through `--ink-4`
  disabled. Critically _warm_ (hue 70), not pure gray, so text sits sympathetically
  on the cream rather than fighting it.
- **Lines** — two border weights, `--line-1` and `--line-2`.
- **Accent** — _one_ restrained bronze, in three tones: `--accent`, `--accent-soft`
  (a pale background wash), `--accent-ink` (a deeper variant for chips and active
  controls). The single-accent restraint is a deliberate design stance: the
  flavors bring the color; the chrome stays quiet.
- **Pool tints** — the Pick screen's two pool cards (caffeinated, caffeine-free)
  get their own parametrized token families so a future palette tweak doesn't
  mean touching the Pick component.
- **Semantic** — `--danger`, `--success`, `--info`, each with a `-soft`
  background. We'll return to why this set, and only this set, in a moment.

The thing to take away: this is a _system_, not a bag of colors. Every token is a
named _role_ ("primary text," "inset well," "soft accent wash"), and every
component references roles, never raw colors. That indirection is the entire
reason the yearly re-tune and a future dark mode are cheap — change the role's
value once, every consumer follows.

### The Curated 12-Tone Flavor Palette

The flavor color logic lives in
[`src/lib/utils/flavor-color.ts`](../../src/lib/utils/flavor-color.ts), and the
refresh changed both _what it returns_ and _how it's built_.

**What it returns.** The old `getFlavorColor(id)` returned a single HSL string.
The new `getFlavorTone(id)` returns a **triple**:

```ts
export type FlavorTone = {
  readonly fill: string; // box background — soft tinted cream
  readonly accent: string; // left accent strip + secondary text — darker hue
  readonly ink: string; // primary text on the fill — darkest hue
};
```

One lookup paints a whole box card: `fill` for the background, `accent` for the
4px left strip and secondary text, `ink` for the flavor name. ADR-014 rejected
the obvious alternative — three separate helpers, `getFlavorColor` /
`getFlavorAccentColor` / `getFlavorInkColor`, each with its own hash — and the
rejection reasoning is worth keeping: three independent hashes would _drift_ over
time, and nothing would guarantee the trio you got back was _coordinated_. One
function returning one curated triple guarantees coherence by construction.

**How it's built.** Not a hash-to-color formula anymore — a _hand-curated_
`PALETTE` constant: twelve `FlavorTone` triples, all `fill` at `L=0.92`, low
chroma (0.022–0.032), hues spaced evenly around the wheel. They're named in the
source — terracotta, clay, ochre, moss, sage, fern, mist, slate, periwinkle,
lavender, mauve, rose. The design handoff calls the intended feel "muted stained
paper" — sophisticated, not candy. Because every `fill` shares `L=0.92`, they're
a genuine _set_. Because the chroma is low, they're tints, not shouts. Twelve
hand-chosen colors a designer signed off on will _always_ beat a formula spraying
colors across a wheel and hoping.

`getFlavorTone` still _hashes_ — but only to _pick an index into the curated
palette_, never to _compute a color_:

```ts
export function getFlavorTone(flavorId: string): FlavorTone {
  let h = flavorId.length * 17;
  for (let i = 0; i < flavorId.length; i++) {
    h = (flavorId.charCodeAt(i) * 31 + (h << 5) - h) | 0;
  }
  return PALETTE[Math.abs(h) % PALETTE.length];
}
```

The hash is deterministic (same flavor → same tone, every render, no storage
needed) and seeds with `flavorId.length * 17` so that same-prefix names —
"Chocolate" vs. "Chocolate Wintermint" — start from different positions instead
of landing adjacent. The output space is now _closed_: twelve designer-approved
tones, never anything else. The hash chooses; it can no longer _create_.

### Why Hash Collisions Are a Feature, Not a Bug

This catches people, so let's be explicit. With ~11 flavors and 12 palette slots,
**two flavors will sometimes hash to the same tone.** The design handoff even
names a real case: "Chocolate Wintermint shares a lavender tint with Chocolate."

Your instinct says _collision = bug_. Here it genuinely is not, and the reasoning
is a small piece of wisdom worth carrying to other problems:

- **The tone was never an identifier.** It is a _visual aid_. The flavor _name_,
  printed right on the box, is the source of truth. Two boxes sharing a tint is
  no more broken than two people sharing a favorite color.
- **A collision-free palette would cost more than it's worth.** To guarantee
  uniqueness you'd need a perfect-hash scheme keyed to the exact flavor set,
  re-derived every time a flavor is added — real complexity, fragile, all to
  prevent a harmless visual coincidence.
- **Twelve curated tones beat N perfectly-unique ugly ones.** If you forced
  uniqueness by generating colors per-flavor, you'd be right back in the
  hash-to-HSL "some look bad" world. Twelve hand-tuned tones with rare
  collisions is the better trade.

ADR-014 states it plainly: "Hash collisions are accepted — the flavor name
remains the source of truth." The general principle: **before you engineer away
a 'collision,' ask whether the colliding thing was ever required to be unique.**
Often it wasn't, and the cheapest correct design is to let the collision happen
and lean on the thing that _is_ actually unique.

### The Yearly Pantone Re-Tune Procedure

This is the part future-you will be grateful for, so it's worth doing slowly.

Cloud Dancer is the _2026_ Color of the Year. Pantone names a new one annually,
and the design intends the app to track it. The crucial design property: that
yearly re-tune is **mechanical** — no component touches at all.

The procedure is documented right in the `variables.css` header comment and in
ADR-014. Here it is, with the _why_ attached:

1. **Change `--surface-app`** to the new Color of the Year's base lightness.
2. **Shift the other four... sorry, three** — the other three surface lightness
   values (`--surface-card`, `--surface-sunk`, `--surface-hover`) — _proportionally_,
   so the cream→milk→fog relationship is preserved against the new base.
3. **Shift the flavor palette's `fill` lightness** in `flavor-color.ts` to track
   `--surface-app`. Today every `fill` is `L=0.92` against an `L=0.955` page —
   keep that _delta_. If the new base is darker, the fills move down with it.
4. **That's it.** No component CSS changes. The `accent` and `ink` tones in the
   palette generally hold; only `fill` chases the surface.

_Why_ is this mechanical? Because of everything Part Two has already built.
Components reference _roles_ (`var(--surface-app)`, `getFlavorTone(id).fill`),
never literal colors — so re-pointing a role re-paints every consumer for free.
And because OKLCH lightness is perceptual and on its own axis, "shift everything
proportionally to keep the same brightness relationships" is _real arithmetic on
one number_, not guesswork. ADR-014's "yearly Pantone re-tune is mechanical" line
is not marketing — it's a direct, earned consequence of perceptual lightness plus
role-based tokens.

The exact same machinery powers the _designed-in_ dark mode. Look at the bottom
of `variables.css`: there's a `@media (prefers-color-scheme: dark)` block,
deliberately _empty today_, with a comment describing the flip — surfaces down to
`L≈0.18–0.22`, ink lifted above `0.7`, accent roughly stable, lines darker. Dark
mode, when someone wires it up, is a _lightness flip on the same `:root` tokens._
No component changes. That is the entire return on investment of building a token
_system_ instead of scattering colors.

### Why `--warning` Got Retired and `--success` / `--info` Got Born

A small story that ties Part One and Part Two together, because it's a perfect
miniature of "extend the system, don't hack the component."

The pre-2026 palette had a `--warning` token (an amber). The refresh **retired
it.** ADR-014's reasoning is bracingly simple: _nothing in the app consumes it._
A minimal design system "doesn't budget a hue on speculation." If no component
uses a token, the token is dead weight — delete it. The old OPEN-box badge that
once used `--color-success-*` now just takes the flavor's own `accent` inside the
box card, so that consumer is gone too.

But the refresh also _added_ two tokens: `--success` and `--info` (each with a
`-soft` background), in commit `1714c2c`. Why add tokens to a system whose whole
ethos is minimalism?

Because the merged-in `SyncStatusBadge` **genuinely needs them.** The badge has
distinct states — _synced_ (green, `--success`), _offline_ (blue, `--info`),
_error_ (red, `--danger`). ADR-014 spells out the reasoning: collapsing those
onto the single `--danger` accent "would erase the very distinction the badge
exists to communicate." A status badge whose whole job is to tell three states
apart cannot render all three in one color.

So watch the _order of operations_ one more time, because it is the entire moral:
the branch did **not** open `SyncStatusBadge.svelte` and paste in a hardcoded
green. It first **extended the design system** — added `--success` / `--info` as
proper tokens, each constructed exactly like `--danger` (text/border at `L≈0.55`,
soft background at `L≈0.95`) — _and then_ the badge consumed them. The system
stays coherent. The next component that needs a success color finds one already
named and waiting.

> **The lesson.** A minimal token system isn't a _frozen_ one. The rule is not
> "never add tokens" — it's "add a token only when a real component needs it, and
> when you add it, build it to the system's own construction rules." Retire
> `--warning` because nothing uses it. Add `--success` because the badge does.
> Both moves serve the same master: every token in the system is a _role a real
> consumer plays._ When a merged-in feature needs a color the system lacks, the
> correct fix is _grow the system_, never _hardcode the component._

## Part Three — The Container-Query Responsive Shell

The third body of work is the navigation shell — and it leans on a CSS feature,
_container queries_, that you may not have used yet. The full rationale is in
[ADR-015](../adr/015-persistent-tab-navigation.md).

### Container Queries vs. Media Queries

You almost certainly know media queries: `@media (min-width: 820px) { ... }`.
They ask one question — _how wide is the viewport?_ — and that question has been
the backbone of responsive CSS for over a decade.

**Container queries** ask a different question: _how wide is this element's
container?_ You declare an element a container (`container-type: inline-size`),
optionally name it (`container-name: app`), and then `@container app (min-width:
820px) { ... }` styles its descendants based on _that container's_ rendered
width — not the viewport's.

This refresh uses container queries for _every_ responsive switch, and the choice
is deliberate, not fashionable. ADR-014 and ADR-015 both give the same reason:

- **The design prototype is rendered inside a fixed-size frame.** A media query
  reads the _browser window_; inside a fixed frame the window and the app's real
  width disagree. A container query reads the frame. It's _right_ in a context
  where a media query is _wrong_.
- **The future iOS PWA / iPad split-screen.** Same story — the app may be smaller
  than the viewport. The layout should respond to _the space it was actually
  given_, not to the screen behind it.
- **It costs nothing extra.** The branch already needed JS-side breakpoint
  detection (the `isWide` flag, next section) for structural swaps CSS can't do.
  Making the _CSS_ portable too was free once that machinery existed.

> **The mental model.** A media query asks "how big is the _window_?" A container
> query asks "how big is _this box_?" Whenever a component might be rendered at a
> size that isn't the viewport size — inside a frame, a split-screen, a resizable
> panel, an embed — the container query is the _correct_ tool, and the media
> query is merely a _common_ one. This app might be embedded; it chose correct.

### The CSS-Grid App Shell and the Collapsing Topbar

`src/App.svelte` wraps the router outlet in a CSS-grid shell, `.app-shell`, with
three named grid areas: `topbar`, `main`, `nav`. The whole phone-vs-laptop layout
is _one container query_ re-pointing the grid template.

Phone (the default):

```css
.app-shell {
  grid-template-areas: 'topbar' 'main' 'nav';
  grid-template-rows: auto 1fr auto;
  grid-template-columns: 1fr;
}
```

Laptop, at container width ≥ 820px:

```css
@container app (min-width: 820px) {
  .app-shell {
    grid-template-areas: 'nav topbar' 'nav main';
    grid-template-rows: auto 1fr;
    grid-template-columns: 72px 1fr;
  }
}
```

On phone the nav is a row at the _bottom_ (iOS-native tab bar). On laptop the same
`nav` area becomes a 72px column on the _left_ (a rail). Look closely at what does
_not_ change: the HTML doesn't, and `AppNav.svelte` doesn't render two different
components. The _exact same_ `.nav` element is replaced into a different grid
slot, and one `@container` block inside `AppNav` flips its flex direction and
moves the active-tab indicator from a top edge bar to a left edge bar. ADR-015's
phrase is "same component, same content, two layouts." That is the design goal,
and grid template areas plus a container query are how it's reached with almost
no duplicated code.

The genuinely elegant detail is the **collapsing topbar.** The `topbar` grid row
is sized `auto`. CSS grid collapses an `auto` row to `0px` when nothing renders
into it. So screens that need no topbar — Pick, Box Edit, More — simply render
nothing there, the row vanishes, and `main` gets the full height. No
`display: none`, no per-screen conditional layout CSS, no special cases. The
refresh leans on this hard: only the laptop Inventory list mounts a topbar (for
its `+ Add inventory` button), and the topbar _also_ appears when sync is
configured and you're signed in (to host the status badge). Both conditions are
plain `$derived` booleans in `App.svelte` — `showInventoryTopbar`, `syncReady`,
combined into `showTopbar`. When both are false, the row is 0px and costs
nothing. "Let an `auto` grid row collapse itself" is a small trick, and a lovely
one.

### The `ResizeObserver` `$effect`: Mirroring CSS Into JS

Container queries handle everything CSS _can_ express. But some responsive
switches are _structural_ — they're not "style this differently," they're "render
a genuinely different component" — and CSS cannot do those. Two examples on this
branch:

- **Add Inventory** is a bottom _sheet_ on phone but a right side _panel_ on
  laptop. Different DOM, different mount, different animation.
- The Inventory **Add affordance** is a floating FAB on phone but a topbar button
  on laptop.

For these, JavaScript has to _know_ the breakpoint. So `App.svelte` keeps an
`isWide` boolean — and the way it stays in sync is the most copy-worthy pattern in
the file:

```ts
let appEl = $state<HTMLDivElement | undefined>(undefined);
let isWide = $state(false);

$effect(() => {
  if (!appEl) return;
  isWide = appEl.offsetWidth >= WIDE_BREAKPOINT_PX; // (1) seed synchronously
  const ro = new ResizeObserver(([entry]) => {
    // (2) then observe
    isWide = entry.contentRect.width >= WIDE_BREAKPOINT_PX;
  });
  ro.observe(appEl);
  return () => ro.disconnect(); // (3) clean up
});
```

Three things in this tiny block each earn their place:

1. **The synchronous seed.** Before attaching the observer, `isWide` is set
   straight from `appEl.offsetWidth`. This matters more than it looks. A
   `ResizeObserver` fires its _first_ callback asynchronously, after the next
   layout. Without the seed, the very first paint would render with
   `isWide = false` (the default) and then _flip_ once the observer caught up —
   a visible flash where, e.g., a laptop user sees the phone sheet for one frame.
   The seed makes the _first paint already correct._ ADR-015 calls this out by
   name: "no first-paint flash."
2. **The observer for everything after.** Once seeded, the `ResizeObserver`
   keeps `isWide` honest as the container resizes — a laptop window dragged
   across the 820px line, an iPad rotating. It watches the `.app` _element_, so
   it's measuring the same width the `@container` rules measure. CSS and JS now
   agree on the breakpoint because they're reading the _same ruler_.
3. **The cleanup return.** A Svelte 5 `$effect` may return a teardown function.
   Returning `() => ro.disconnect()` means the observer is torn down if the
   effect re-runs or the component unmounts. Skip this and you leak an observer
   holding a reference to a dead DOM node. The teardown is not optional politeness;
   it's the back half of the pattern.

Why is the JS breakpoint constant (`WIDE_BREAKPOINT_PX = 820`) _duplicated_ from
the CSS `--bp-app-wide: 820px` and the `@container` rules? Because CSS custom
properties and JS constants live in different worlds and there's no clean,
synchronous way for JS to read a container-query threshold. The honest move is to
duplicate the number and **comment loudly at both sites that they must stay in
lockstep** — which `App.svelte` and `variables.css` both do. A documented,
deliberate duplication beats a clever runtime bridge that's hard to follow. If
you ever change `820`, change it in all three places; the comments will tell you
where.

### Why the Sheets Mount Outside the Grid

One last detail, and it's the kind that costs an afternoon if you don't know it.

`App.svelte` mounts `PickResultSheet`, `AddInventoryPanel`, and `SyncAccountModal`
as **siblings of `.app-shell`**, not inside `.main`:

```svelte
<div class="app">
  <div class="app-shell">
    {#if showTopbar}<header class="topbar">...</header>{/if}
    <main class="main"><Router {routes} /></main>
    <AppNav />
  </div>

  <!-- sheets/overlays live OUT here, as siblings of .app-shell -->
  <PickResultSheet />
  <AddInventoryPanel />
  <SyncAccountModal />
</div>
```

Here's the trap. These sheets are _always mounted_ — recall `b0ca42f`: a sheet
must stay in the DOM and slide off-screen via `transform: translateY(100%)` so it
has a "from" position for its open animation. A _closed_ sheet, then, is a real
element parked off-screen by a translate.

Now — _where_ does `translateY(100%)` park it? `100%` of the sheet's own height,
relative to its **containing block**. If a sheet were a child of `.main`, "100%
down" would land it at the bottom of `.main` — which on phone sits _directly
above the bottom tab bar._ The parked, "closed" sheet would visibly overlap the
nav. By mounting the sheets as siblings of `.app-shell`, their containing block
is `.app` (the whole frame), so `translateY(100%)` pushes them fully off the
_bottom of the app_ — genuinely out of sight. The design handoff flags this as a
"critical layout note," and it earns the adjective.

The general principle is about _positioning context_. `position: absolute`,
`position: fixed`, and percentage transforms are all resolved against an
element's _containing block_, not against wherever you mentally picture it. When
an overlay must escape a layout — a grid, a scroll region, an `overflow: hidden`
ancestor — mount it high enough in the tree that its containing block is the
thing you actually want it positioned against. Mounting these sheets as siblings
of `.app-shell` is a deliberate choice to give them `.app` as their reference
frame.

## What You Should Learn From This

### On integrating a diverged branch (the headline)

1. **Merge for public/long-lived branches; rebase for private, unshared, still-messy
   work.** The deciding question is "will rewriting these commit hashes hurt
   anyone, and does the parallel story deserve telling" — not "which history is
   prettier."
2. **A merge conflict is an editorial decision escalated to a human.** At every
   conflict marker, ask: _addition collision_ (keep both — the union) or _value
   collision_ (genuinely pick one)? Most conflicts are additions.
3. **"Keep both" is the default, not a law.** When one side made an
   _architectural_ decision that supersedes the other side's code, delete the
   superseded code and re-implement its capability inside the new architecture —
   but only if you (a) say so explicitly in the merge commit, (b) name where the
   capability is being re-homed, and (c) actually deliver the re-homing in named
   follow-up commits.
4. **Integration has two phases, and people skip the second.** Phase one: make it
   compile. Phase two: make it _belong_ — re-token it, re-pattern it, re-home it,
   hold it to the joining branch's conventions. A feature that looks bolted-on is
   a half-done merge.
5. **A green build is not a clean merge.** After any non-trivial merge, ask "what
   is now _possible_ that wasn't possible on either branch alone?" — then hunt for
   the code that assumed it couldn't happen. (Here: background `$appState`
   mutation from sync, which silently clobbered `InventoryBoxEdit`.)
6. **A UI refresh will break your e2e suite — that's the suite working.** Triage
   each failure: flow gone (delete spec, re-home coverage) / selector moved
   (update spec, make it responsive if the affordance is) / assertion encodes a
   stale model (fix the _assumption_). Never delete an assertion to make a test
   pass.
7. **Write the merge commit like a letter to the next maintainer.** `5ac9d07`
   lists every resolution and every promise. That message is why this document
   could be written at all.

### On design systems

8. **Use a perceptually-uniform color space (OKLCH) when "same brightness across
   hues" is a real requirement.** HSL lightness lies; OKLCH lightness doesn't.
9. **Curate, don't compute, when a human will judge the result.** Twelve
   hand-tuned tones beat a hash spraying colors across a wheel. Let the hash
   _index into_ a curated set; never let it _create_ a color.
10. **Before engineering away a "collision," ask if the thing was ever required
    to be unique.** Flavor tones aren't IDs; the name is. The collision is free.
11. **Build tokens as _roles_, not colors, and a yearly re-tune / dark mode
    becomes a one-number change instead of a component sweep.**
12. **A minimal token system is not a frozen one.** Retire tokens nothing
    consumes (`--warning`); add tokens a real component needs (`--success`,
    `--info`) built to the system's own construction rules. Never hardcode a
    color into a component because the system lacked it — grow the system.

### On responsive layout

13. **Container queries when the component might not be viewport-sized** (frames,
    split-screens, embeds); media queries are merely the common default.
14. **Let CSS grid do the heavy lifting** — named areas plus one `@container`
    block flips an entire layout, and an `auto` row collapses itself to 0px when
    empty (the self-collapsing topbar).
15. **When JS needs the breakpoint, seed the flag synchronously, then observe.**
    The synchronous `offsetWidth` read kills the first-paint flash a bare
    `ResizeObserver` would cause; the observer keeps it honest after; the
    `$effect` teardown disconnects it.
16. **Positioning resolves against the containing block.** Mount escape-the-layout
    overlays high enough that their containing block is the frame you actually
    want them positioned against.

## Questions to Think About

1. The branch chose to **merge** `main` rather than rebase. Suppose this branch
   had been a _private, unpushed, three-commit_ spike instead of a long-lived PR.
   Would rebase have been the better call? What single fact flips the decision?
2. The merge dropped `main`'s inline Inventory Sync button and _promised_ to
   re-home it. Imagine the integration commits had stopped after the merge —
   build green, button gone, no follow-up. What exactly would a user lose, and
   why would _no existing test_ catch it?
3. `untrack()` fixed `InventoryBoxEdit` by making the reseed `$effect` deaf to
   background store changes. Are there _other_ preview-then-commit screens in the
   app whose working copy could be clobbered the same way once sync is on? How
   would you go looking for them, before a user reports a lost edit?
4. The flavor palette accepts hash collisions. Now suppose a future feature lets
   the user **assign** a color to a flavor by hand. Does the "collisions are
   fine" argument still hold? What changes about the requirement?
5. The yearly Pantone re-tune is "change `--surface-app`, shift the rest
   proportionally." Walk it concretely: if next year's color is _darker_ than
   Cloud Dancer, which exact tokens move, in which direction, and which provably
   don't move at all — and _why_ does the answer fall out of OKLCH for free?
6. `App.svelte` duplicates the `820` breakpoint across a JS constant, a CSS
   custom property, and `@container` rules, with comments tying them together.
   Sketch a design that removes the duplication entirely. Is your design
   genuinely _better_, or just _cleverer_? What does it cost a future reader?
7. The closed sheets stay mounted and slide off-screen. List the things that buys
   (animation, accessibility) and the things it costs (the parked sheet must be
   `inert` + `aria-hidden` + pointer-events-none — see `b0ca42f` and `e53fb47`).
   Was "stay mounted" the right call, and what's the alternative?
