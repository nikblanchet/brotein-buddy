## What We Cleaned Up

Most of this change is a few lines in a few files. The interesting part is
that almost every line is load-bearing for a different reason, and the
reasons are worth understanding even if you never touch a bare repo again.

Concretely, we did four things:

- Removed four tracked symlinks under `.claude/` whose target paths were
  off-by-one and broken on every machine.
- Slimmed `.gitignore` down to the rules that genuinely belong to every
  collaborator, and pushed per-clone rules into `.bare/info/exclude`.
- Taught `init-shared.sh` to populate that exclude file on a fresh clone
  and to resolve the repo root in a way that works _before_ any worktree
  exists.
- Rewrote the "first time setup" section of `DEVELOPING.md` so a future
  reader can bootstrap from zero without folklore.

None of that is exciting on its own. What's interesting is the small pile
of git concepts you trip over when you do this kind of cleanup, and the
patterns that fall out naturally once you understand them.

## The Bare-Repo + Worktrees Layout

Most git tutorials show you this layout:

```
my-project/
  .git/         <-- directory; contains everything git
  src/
  package.json
```

There's one working tree and one `.git` directory, joined at the hip.
Worktrees, when people use them at all, are usually a sibling directory or
a subdirectory.

This repo uses a different shape:

```
BroteinBuddy/             <-- parent container, not itself a worktree
  .bare/                  <-- the canonical repository (everything that
  .git                        normally lives in .git/, but no working tree)
  .shared/                <-- per-clone personal stuff (not tracked)
  main/                   <-- worktree for the main branch
    .git                  <-- file: gitdir: <abs path>/.bare/worktrees/main
    src/
    ...
  feature-xyz/            <-- worktree for a feature branch
    .git
    src/
    ...
```

A few details worth pinning down:

**`.bare/` is the repo.** It contains `HEAD`, `refs/`, `objects/`,
`config`, and friends. It has no working tree of its own. You can think
of it as the `.git` directory promoted to a first-class folder, sitting
beside the worktrees instead of inside one of them.

**The `.git` file at the parent level is a one-line pointer.** It contains
literally `gitdir: ./.bare`. When you run `git status` from `BroteinBuddy/`
itself, git reads that file, follows the pointer, and treats `.bare/` as
the repository. Most git tooling handles this transparently. (You'll
notice we cat-ed it earlier: `echo "gitdir: ./.bare" > .git`. That's the
whole file.)

**Each worktree has its own `.git` file too**, but pointing to a
per-worktree subdirectory inside the bare repo:

```
main/.git  →  gitdir: <abs path>/.bare/worktrees/main
```

That subdirectory holds the per-worktree `HEAD`, index, and other
things-that-differ-by-worktree. The bulk of the repo (objects, packed
refs, config) is shared.

**Why bother?** Compared to "main branch lives in the root, worktrees go
in a subdirectory like `wt/`," the bare layout has two practical wins:

1. **No special main.** Every worktree is just `BroteinBuddy/<name>/`.
   There's no "the project lives at the root, except sometimes it lives in
   a subdirectory." Tooling that walks up looking for `.git` finds the
   same thing in every worktree.

2. **A genuine container directory.** `.shared/`, `.bare/`, and the
   worktrees are all siblings. You can put a `CLAUDE_CONTEXT.md` symlink
   at the parent level and have every worktree's symlinks point to a
   single shared file via `../`.

Compared to "everything in `.git`, no worktrees at all," this layout
genuinely earns its complexity only when you do parallel development. The
0.1 teaching doc covers worktrees in depth; this doc is about the things
that fall out of the bare flavor of that pattern, not the pattern itself.

> **General principle:** A bare repo is just `.git` without a working
> tree, promoted to its own directory. Once you internalize that, every
> "but where does X live?" question has the same answer: in `.bare/`, the
> same place it would have lived inside `.git/`.

## Two Ignore Files, Two Audiences

Git has multiple places you can tell it "ignore this file." The two that
matter here are:

| File                 | Tracked in git? | Who sees it?       | What it's for                      |
| -------------------- | --------------- | ------------------ | ---------------------------------- |
| `.gitignore`         | Yes             | Every collaborator | Project-wide rules everyone needs  |
| `.bare/info/exclude` | No (per-clone)  | Just this clone    | Local rules specific to your setup |

(There's also `~/.config/git/ignore` for "user-wide across all repos." Not
relevant here.)

The rule of thumb:

- If _every_ collaborator should ignore this thing because of what it
  _is_ (build output, OS clutter, secret files), it belongs in
  `.gitignore`. That file is part of the project's contract.

- If _only this clone_ should ignore this thing because of _how this
  clone is laid out_ (the per-clone `.shared/` directory, the per-clone
  symlinks pointing into it, the bare-repo-specific scratch dirs), it
  belongs in `.bare/info/exclude`. That file is a local preference.

Before this cleanup, `.gitignore` had a bunch of stuff that wasn't really
project-wide:

```gitignore
# Worktrees directory
/wt/

# Shared directory - personal files not committed
/.shared/

# Planning and scratch (if symlinked to root)
.planning
.scratch

# Claude Code personal settings (symlinked in worktrees)
.claude/agents
.claude/settings.local.json
.claude/skills
```

None of that is wrong, exactly. But it's leaking the _structure of one
clone_ into the project's tracked file. A teammate cloning fresh without
the bare-repo layout would have a bunch of `.gitignore` rules referring to
directories they don't have. The right home for those rules is
`.bare/info/exclude`, where they only affect the clone that uses them.

So after the cleanup, `.gitignore` keeps the things that _are_ universal:

```gitignore
# Environment
.env
*.local

# CLAUDE_CONTEXT.md - confidential file kept here intentionally...
CLAUDE_CONTEXT.md

# Testing, build output, OS clutter, etc.
coverage/
.DS_Store
...
```

…and `.bare/info/exclude` holds the per-clone realities:

```gitignore
.shared/
.claude
.planning
.scratch
CLAUDE_CONTEXT.md

.claude/settings.local.json
.claude/skills
.claude/agents

node_modules/
wt/
```

Notice this is _additive_, not exclusive. Git unions both files. If
something appears in either, it's ignored. You don't have to pick a side;
you just have to put each rule in the side that "owns" it.

### Why `*.local` covers `.env.local`

A subtle thing: the old `.gitignore` listed `.env.local` _and_ `*.local`.
That's redundant — `*.local` already matches `.env.local`. We removed the
specific one and kept the glob.

That's not just tidiness. The principle is **single source of truth for
each rule**. If you have a glob and an instance of that glob, the instance
is dead code. The first time someone wonders "why is `.env.local` listed
twice?" they spend a few minutes confirming it's not. That few minutes is
the cost of the redundancy. Multiply by every reader, forever.

> **Pattern name:** This is sometimes called "rule normalization." When
> you have a class of things expressed by a pattern, don't also enumerate
> members of the class. It looks like extra safety. It's actually just
> extra reading.

## Defense-in-Depth for Confidential Files

Here's an exception to the "single source of truth" rule. `CLAUDE_CONTEXT.md`
appears in _both_ `.gitignore` and `.bare/info/exclude`. The duplication is
deliberate, and the reasoning is worth slowing down on.

`CLAUDE_CONTEXT.md` contains things you actively do not want in the git
history: API keys, internal notes, things that would be embarrassing or
worse if pushed. Leaking it once and amending the commit is not a fix.
Once it's pushed, it's on someone's screen, in a CI log, in someone's
fork. Git history is forever for our purposes.

The two ignore files cover different failure modes:

- **`.bare/info/exclude`** ignores it for _this_ clone, because the file
  lives at `BroteinBuddy/CLAUDE_CONTEXT.md` (as a symlink into
  `.shared/`). Local-only, never travels.

- **`.gitignore`** ignores it project-wide, because the file is tracked
  and shipped to every collaborator. Anyone who clones the repo without
  ever running `init-shared.sh` _still_ won't accidentally `git add` it.

Now, in steady state, `.bare/info/exclude` would be enough. The
`.gitignore` entry is redundant — every working clone has both files
populated, so either one catches it.

But consider a fresh clone on a brand-new machine. The sequence is:

1. `git clone --bare ...`
2. `echo "gitdir: ./.bare" > .git`
3. … nothing has populated `.bare/info/exclude` yet …
4. `git --git-dir=.bare show HEAD:init-shared.sh | bash`
5. Now `.bare/info/exclude` exists.

Between steps 2 and 5 there is a window — small, but nonzero — where the
clone exists but the per-clone exclude has not been written. If the user
opens the repo in an editor during that window, drops a
`CLAUDE_CONTEXT.md` into the root, and runs `git add .` to check status,
they could stage a confidential file by accident.

`.gitignore` is the safety net. It is shipped _in_ the commit, so it's
populated the moment the clone exists. The clone has _no window_ in which
git would let you accidentally stage `CLAUDE_CONTEXT.md`, even if the
per-clone bootstrap has not run.

> **General principle:** Single-source-of-truth is the right default, but
> _irreversibility_ changes the calculus. If a mistake cannot be undone
> (git history, deployment to prod, sending an email, deleting data),
> redundant guards are worth the readability cost. Document why the
> duplication exists at the duplication site, so a future cleanup-minded
> reader does not "fix" it back.

That's exactly what the comment in `.gitignore` does. It tells you the
line is duplicated, tells you _why_, and tells you not to remove it.
Without that comment, the duplication looks like a bug. With it, it's
obviously a feature.

> **Pattern name:** "Defense in depth." Borrowed from security. Each layer
> on its own is probably enough; together, they survive the failure of
> any single layer. Use it sparingly — it has a real readability cost —
> but use it without apology when the failure mode is irreversible.

## The Bootstrap Chicken-and-Egg

There's a subtle ordering problem in the bare-repo bootstrap. Let's stare
at it head-on.

To set up a new machine, you want `.bare/info/exclude` to exist before you
touch any files in the repo, so that `git status` doesn't get noisy or
risky. The thing that populates `.bare/info/exclude` is `init-shared.sh`.
The thing that contains `init-shared.sh` is the repo.

So you can't just clone, then `./init-shared.sh`, because there is no
working tree yet — you only have `.bare/`. And you can't `git checkout`
something because `git checkout` in a bare repo needs you to pick a
worktree, which means you've already started messing with the filesystem
before the exclude file exists.

The trick:

```bash
git --git-dir=.bare show HEAD:init-shared.sh | bash
```

This says: "Using `.bare` as the git directory, find the file
`init-shared.sh` at the tip of `HEAD`, dump its contents to stdout, and
pipe that into bash." No working tree required. No checkout. The script
runs from stdin, populates `.bare/info/exclude`, creates `.shared/`, sets
up symlinks — all the things that need to happen before there's a real
worktree to drop files into.

Once that's done, you `git worktree add main main` and you have a proper
worktree with proper symlinks and a clean `git status`.

Two things to appreciate here:

**1. `git show <ref>:<path>` is a content-only operation.** It does not
touch the filesystem, does not update the index, does not require a
worktree. It reads bytes out of the object database. You can pipe those
bytes anywhere. Other contexts where this is useful:

- Reading a tracked file's contents on a CI machine before a checkout.
- Inspecting an old version of a file without doing anything that touches
  your current working tree.
- Producing a tarball from a specific revision (`git archive` is the
  fancy form of this).

**2. The bootstrap script is _self-contained enough to run from stdin_.**
That's a real constraint. `init-shared.sh` cannot, for instance, assume
its own location on disk — it isn't on disk. It has to determine the repo
root from git itself, not from `$0` or `$(dirname "$0")`. That requirement
is what drives the path-resolution code in the next section.

> **General principle:** When you have a chicken-and-egg, look for a
> source of truth that exists _before_ either of the two. For
> bare-repo-aware bootstraps, that source is "git's own knowledge of its
> own directory." For other bootstraps, it might be the OS, an
> environment variable, or a user-supplied path.

## Path Resolution in a Multi-Context Script

`init-shared.sh` needs to know where the repo root is. The obvious answer
is:

```bash
REPO_ROOT="$(git rev-parse --show-toplevel)"
```

That's what the script used before. It works _inside a worktree_. It does
not work from the container directory during the initial bootstrap.

Let's walk through why.

`git rev-parse --show-toplevel` returns "the absolute path of the
top-level directory of the working tree." If you're in `main/src/`, it
returns `BroteinBuddy/main`. If you're in `main/`, same answer.

What about from `BroteinBuddy/` itself, where `.git` is a file pointing at
`./.bare`? There is no working tree _here_. `.bare/` is a bare repo. So
`--show-toplevel` either errors out or returns something unhelpful,
depending on git version.

That's a problem for the bootstrap, which runs from `BroteinBuddy/` — by
necessity, because there isn't a worktree yet to run from.

The right answer is:

```bash
GIT_COMMON_DIR="$(git rev-parse --git-common-dir 2>/dev/null)"
REPO_ROOT="$(cd "$GIT_COMMON_DIR/.." && pwd)"
```

`--git-common-dir` returns the path to the directory holding the
shared-across-worktrees git data. In our layout:

- From `BroteinBuddy/`, it returns `./.bare` (or its absolute form).
- From `BroteinBuddy/main/`, it returns `../.bare` or an equivalent —
  the worktree's `.git` file points into `.bare/worktrees/main`, and
  git's common-dir resolution walks up to `.bare`.
- From `BroteinBuddy/main/src/`, same as above.

In all three contexts, going one level up from `--git-common-dir` lands
you at `BroteinBuddy/`, which is what we want.

Compare to `--show-toplevel`:

| From                     | `--show-toplevel`   | `--git-common-dir`          |
| ------------------------ | ------------------- | --------------------------- |
| `BroteinBuddy/`          | error / nothing     | `./.bare` → up = container  |
| `BroteinBuddy/main/`     | `BroteinBuddy/main` | up from `.bare` = container |
| `BroteinBuddy/main/src/` | `BroteinBuddy/main` | up from `.bare` = container |

`--show-toplevel` returns the worktree root, which is _a_ valid answer
inside a worktree but not the same answer in every context. We want the
container, not the worktree. So we use the common-dir flag.

The error-handling clause is worth noting too:

```bash
if ! GIT_COMMON_DIR="$(git rev-parse --git-common-dir 2>/dev/null)"; then
    echo "Error: not inside a git repository or its bootstrap directory." >&2
    exit 1
fi
```

If you somehow run the script from `~/Desktop` or anywhere outside the
repo, you get a clear error instead of bash trying to `cd` to an empty
string. The `2>/dev/null` suppresses git's own error so we can replace it
with one that mentions the bootstrap directory specifically.

> **General principle:** Pick the `git rev-parse` flag that answers your
> _real_ question. `--show-toplevel` answers "where is the worktree
> root?" `--git-common-dir` answers "where is the shared git data?"
> `--git-dir` answers "where is the per-worktree git data?" If you're
> writing a tool that must work in multiple contexts, the common-dir
> answer is usually the most stable.

## Symlink Hazards: -f vs -fn

The last thing worth understanding is buried in two characters of an
`ln` flag.

`ln -s TARGET LINK` creates a symbolic link at `LINK` pointing to
`TARGET`. Fine.

What happens when `LINK` already exists?

```bash
ln -s newtarget existinglink
# ln: existinglink: File exists
```

So you reach for `-f` to force overwrite. And here's where it gets sharp.

`-f` ("force") means: if `LINK` exists, remove it first, then create the
new link. _Mostly._ The complication is when `LINK` is a symlink to a
_directory_. In that case, `-f` may follow the symlink and act on the
target rather than replacing the symlink itself. From `man ln`:

> -f If the target file already exists, then unlink it so that the
> link may occur.

That sounds safe enough, but the behavior across platforms (and across
GNU coreutils vs BSD `ln`) gets subtle when the target is a symlink to a
directory. On macOS / BSD specifically, `ln -sf TARGET LINK` where `LINK`
points to a directory can write `TARGET` _inside_ that directory rather
than replacing the symlink.

The fix is `-n`:

> -n With -f, if the target file is a symbolic link, do not follow it.
> This is most useful with the -f option to replace a symbolic link
> which may point to a directory.

So `ln -sfn TARGET LINK` says: "if LINK exists and is a symlink, do not
dereference it — just delete it and put a new symlink in its place."

In `init-shared.sh`, the relevant line is:

```bash
ln -sfn "$CENTRAL_SKILLS" "$SHARED_DIR/.claude/skills"
```

Without `-n`, on the second run of the script, this would dereference
`.shared/.claude/skills` (a symlink to `~/Code/repos/custom-claude-skills/`),
descend into the central skills repo, and create a new symlink _inside_
the skills repo named after the basename of `$CENTRAL_SKILLS`. The
self-referential result silently breaks every worktree that resolves
skills through that chain.

The bug is invisible until it isn't. `git status` doesn't notice. The
symlink "works" because the first level resolves. The damage is in the
shared store, which means every worktree on the machine sees it.

The same hazard applies to the per-worktree symlinks in `setup-worktree.py`
and to the manual `ln -sfn` commands in the new `DEVELOPING.md`. Anywhere
you're replacing a symlink that _might_ point at a directory: use `-sfn`,
not `-sf`. Treat `-sf` alone as a code smell unless you've proved the
target doesn't exist or isn't a directory link.

> **Pattern name:** I call this one "the symlink overwrite gotcha." It
> shows up in any script that's idempotent over symlinks, which is
> basically every dotfiles installer and every worktree bootstrap. The
> habit to build: when in doubt, `-n`. The cost of an unnecessary `-n` is
> zero. The cost of a missing one is debugging a self-referential
> filesystem at 11pm.

## Takeaways

Six ideas worth keeping past the next time you touch a bare repo:

1. **Bare-repo + worktrees is a layout, not a feature.** `.bare/` is just
   `.git/` with no working tree, promoted to a sibling of the worktrees.
   Once you see it that way, the rest is mechanical.

2. **`.gitignore` is the project contract; `.bare/info/exclude` is the
   local preference.** If every collaborator needs the rule, track it. If
   only this clone needs the rule, keep it untracked. Use both, union the
   effect.

3. **Redundancy is occasionally correct.** Single-source-of-truth is the
   default, but when the failure mode is irreversible (committing
   secrets, deploying to prod, deleting data), defense-in-depth earns its
   keep. Document the deliberate duplication so a future tidy-up doesn't
   "fix" it.

4. **`git show <ref>:<path>` is your bootstrap escape hatch.** When you
   need to run a script before any worktree exists, pipe it from the
   object database into bash. No checkout, no filesystem changes, no
   chicken, no egg.

5. **Pick the right `git rev-parse` flag.** `--show-toplevel` answers
   "worktree root." `--git-common-dir` answers "shared git data."
   `--git-dir` answers "per-worktree git data." When your script must
   work from multiple directories, the common-dir answer is usually the
   most stable anchor.

6. **`ln -sf` is dangerous around directory symlinks; reach for `-sfn`.**
   The cost of an unnecessary `-n` is zero. The cost of a missing one is
   a self-referential filesystem that silently corrupts shared state.

If you internalize one thing from this doc, internalize the meta-pattern:
**every one of these issues is invisible in normal operation and only
appears when you're setting up, recovering, or doing something unusual.**
That's exactly when you cannot afford for the tooling to be subtle. The
extra comments, the deliberate redundancy, the picky flag choice — they
exist for the worst moments, not the average ones.

## Questions to Think About

1. We unioned `.gitignore` and `.bare/info/exclude` for the
   `CLAUDE_CONTEXT.md` rule. What other failure modes would justify
   listing the same rule in two places? Where is the line between
   "principled defense in depth" and "anxious duplication"?

2. The bootstrap pipes `init-shared.sh` from stdin into bash. That means
   the script cannot reliably know its own filesystem path. What other
   constraints does "runs from stdin" impose? Could you write a Python
   bootstrap with the same property?

3. `--git-common-dir` is the right anchor for our case. Imagine a tool
   that needs to find _all_ worktrees of a given repo from any worktree.
   Which flag would you reach for, and why?

4. `ln -sfn` is safer than `ln -sf`. Is there ever a case where `-f`
   without `-n` is the correct choice? (Hint: think about non-directory
   symlinks where you _want_ to overwrite the target file, not the
   link.)

5. If you were starting BroteinBuddy from scratch today, would you pick
   the bare-repo + worktrees layout? At what team size or feature volume
   does the complexity pay for itself, and at what point would it be
   overkill?
