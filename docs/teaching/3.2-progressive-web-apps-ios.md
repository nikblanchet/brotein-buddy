## Introduction

Progressive Web Apps (PWAs) bridge the gap between web applications and native mobile apps. They provide an app-like experience through web technologies, enabling features like offline functionality, home screen installation, and full-screen display.

For BroteinBuddy, PWA functionality transforms a responsive website into an installable iOS app that works offline and feels native. This is particularly valuable for a utility app where users expect quick access and reliability.

### What Makes PWAs Special

PWAs combine the best of both worlds:

**Web benefits:**

- Single codebase for all platforms
- Instant updates (no app store approval)
- No installation friction (just visit the URL)
- Searchable and linkable

**Native app benefits:**

- Home screen icon
- Offline functionality
- Full-screen experience (no browser chrome)
- App-like performance

### Learning Objectives

By the end of this document, you'll understand:

- What PWAs are and how they work
- Service workers and their role in offline functionality
- Web app manifests and installation metadata
- iOS-specific PWA requirements and limitations
- Using vite-plugin-pwa for automated PWA setup
- Icon requirements and generation workflows
- Testing and debugging PWA features
- Real-world trade-offs in PWA implementation

- Understanding of Vite build system
- Basic knowledge of JavaScript promises

## Progressive Web Apps Fundamentals

### What is a PWA?

A Progressive Web App is a web application that uses modern web capabilities to deliver an app-like experience. The term "progressive" means the app progressively enhances based on browser capabilities.

**Core principles:**

1. **Progressive** - Works for all users, regardless of browser
2. **Responsive** - Fits any form factor (desktop, mobile, tablet)
3. **Connectivity independent** - Works offline or on low-quality networks
4. **App-like** - Feels like a native app with app-style interactions
5. **Fresh** - Always up-to-date thanks to service worker updates
6. **Safe** - Served via HTTPS to prevent tampering
7. **Discoverable** - Identifiable as an "application" via manifest
8. **Re-engageable** - Can re-engage users through features like push notifications
9. **Installable** - Users can add to home screen without app store
10. **Linkable** - Easily shared via URL

Not all principles apply to every PWA. BroteinBuddy focuses on: progressive, responsive, connectivity independent, app-like, fresh, safe, discoverable, installable, and linkable.

### The Three Pillars of PWAs

PWAs rely on three key technologies:

**1. HTTPS**

Required for security. Service workers can only run on HTTPS (or localhost for development).

```
Why: Service workers can intercept network requests. HTTPS prevents
man-in-the-middle attacks from injecting malicious code.
```

**2. Service Workers**

JavaScript that runs in the background, separate from web pages. Enables:

- Offline functionality (caching assets)
- Background sync
- Push notifications (not on iOS)
- Intercepting network requests

```javascript
// Service worker lifecycle
navigator.serviceWorker.register('/sw.js').then((registration) => {
  console.log('Service worker registered');
});
```

**3. Web App Manifest**

JSON file describing the app for installation:

- Name and icons
- Display mode (standalone, fullscreen, minimal-ui)
- Theme colors
- Start URL

```json
{
  "name": "BroteinBuddy",
  "short_name": "BroteinBuddy",
  "display": "standalone",
  "icons": [...]
}
```

### How PWAs Work

Here's what happens when a user visits a PWA:

**First visit:**

1. Browser loads HTML, CSS, JavaScript
2. Service worker registers and installs
3. Service worker caches specified assets
4. App renders normally using network
5. Browser may show "Add to Home Screen" prompt

**Subsequent visits:**

1. Service worker intercepts requests
2. Returns cached assets (instant load)
3. App works offline if fully cached
4. Service worker checks for updates

**Installation:**

1. User taps "Add to Home Screen" (iOS) or install prompt (Android)
2. Browser reads manifest for app metadata
3. Icon added to home screen
4. App launches in standalone mode (full-screen)

### PWA vs Native Apps

Let's compare:

| Feature            | PWA                                          | Native App         |
| ------------------ | -------------------------------------------- | ------------------ |
| Installation       | Direct from URL                              | App Store required |
| Updates            | Instant (on page load)                       | User must update   |
| Storage            | 5-10MB (localStorage), unlimited (IndexedDB) | Unlimited          |
| Offline            | Yes (service worker)                         | Yes (built-in)     |
| Performance        | Near-native                                  | Native             |
| Platform APIs      | Limited (web APIs only)                      | Full access        |
| Distribution       | URL (shareable)                              | App Store          |
| Development        | One codebase                                 | Platform-specific  |
| Push notifications | Yes (not iOS)                                | Yes                |
| Background sync    | Limited (not iOS)                            | Yes                |

For BroteinBuddy, PWA advantages outweigh limitations:

- No need for platform-specific APIs
- LocalStorage sufficient for data
- Instant updates beneficial
- Single codebase reduces complexity
- URL sharing enables easy adoption

## Why vite-plugin-pwa Over Manual Implementation

When implementing PWA functionality, you have three main options:

1. Manual service worker with hand-written manifest
2. Workbox CLI (separate build tool)
3. vite-plugin-pwa (Vite integration)

We chose vite-plugin-pwa. Here's why.

### The Manual Approach

Writing a service worker from scratch:

```javascript
// sw.js - Manual service worker
const CACHE_NAME = 'broteinbuddy-v1';
const urlsToCache = [
  '/',
  '/index.html',
  '/assets/index.js',
  // ... list every asset manually
];

self.addEventListener('install', (event) => {
  event.waitUntil(caches.open(CACHE_NAME).then((cache) => cache.addAll(urlsToCache)));
});

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((response) => response || fetch(event.request))
  );
});
```

**Problems with manual approach:**

1. **Asset list maintenance** - Must manually update every time assets change
2. **Cache invalidation** - Manually manage cache versions
3. **No fingerprinting integration** - Vite adds hashes to filenames (`index-abc123.js`), but you'd need to dynamically generate the list
4. **Manifest creation** - Hand-write JSON with correct icon paths
5. **Update mechanism** - Implement update detection and notification
6. **Testing** - No built-in testing helpers
7. **Error-prone** - Easy to forget assets or use wrong paths

**When to use manual:**

- Learning exercise
- Very simple app with few assets
- Need complete control over caching logic
- Building a custom framework

### The Workbox CLI Approach

Workbox provides CLI tools for generating service workers:

```bash
workbox generateSW workbox-config.js
```

```javascript
// workbox-config.js
module.exports = {
  globDirectory: 'dist/',
  globPatterns: ['**/*.{html,js,css}'],
  swDest: 'dist/sw.js',
};
```

**Better than manual, but:**

1. **Separate build step** - Run workbox command after Vite build
2. **No manifest generation** - Still write manifest.json manually
3. **Integration complexity** - Coordinate two build tools
4. **Icon management** - Manual PNG generation and manifest updates
5. **Configuration duplication** - Asset patterns defined separately from Vite

**When to use Workbox CLI:**

- Non-Vite projects
- Custom build pipeline
- Need Workbox features not in vite-plugin-pwa

### The vite-plugin-pwa Approach

This is what we chose. A Vite plugin that integrates Workbox:

```typescript
// vite.config.ts
import { VitePWA } from 'vite-plugin-pwa';

export default defineConfig({
  plugins: [
    svelte(),
    VitePWA({
      registerType: 'autoUpdate',
      manifest: {
        name: 'BroteinBuddy',
        icons: [
          /* icon definitions */
        ],
      },
      workbox: {
        globPatterns: ['**/*.{js,css,html,svg,png}'],
      },
    }),
  ],
});
```

**Advantages:**

1. **Single configuration** - Everything in vite.config.ts
2. **Auto-generates manifest** - From configuration object
3. **Integrates with Vite build** - Automatically handles fingerprinted assets
4. **Auto-update by default** - Service worker updates automatically
5. **Development mode support** - Disabled in dev, enabled in build
6. **TypeScript support** - Full type checking for config
7. **Icon generation helpers** - Integrates with asset pipeline

**How it works:**

1. During development: Plugin is inactive (Vite serves files directly)
2. During build: Plugin runs after Vite build completes
3. Scans `dist/` directory for assets
4. Generates manifest.webmanifest from config
5. Creates service worker with Workbox
6. Generates precache manifest listing all assets
7. Injects registration code into index.html

**Our configuration:**

```typescript
VitePWA({
  registerType: 'autoUpdate', // Auto-update on new version
  includeAssets: ['favicon.svg', 'icon-512.svg'],
  manifest: {
    name: 'BroteinBuddy',
    short_name: 'BroteinBuddy',
    theme_color: '#4F46E5',
    icons: [
      /* 192x192 and 512x512 variants */
    ],
  },
  workbox: {
    globPatterns: ['**/*.{js,css,html,svg,png,ico,txt,woff2}'],
    runtimeCaching: [
      {
        urlPattern: /^https:\/\/fonts\.googleapis\.com\/.*/i,
        handler: 'CacheFirst',
        options: {
          cacheName: 'google-fonts-cache',
          expiration: {
            maxEntries: 10,
            maxAgeSeconds: 60 * 60 * 24 * 365, // 1 year
          },
        },
      },
    ],
  },
});
```

This configuration:

- Precaches all app assets (js, css, html, svg, png)
- Caches Google Fonts with 1-year expiration
- Auto-updates service worker on deployments
- Generates manifest with correct icon references

### Real-World Comparison

Let's see what each approach requires:

**Task: Add a new asset (e.g., new icon)**

_Manual:_

1. Create icon file
2. Edit sw.js to add icon to urlsToCache array
3. Increment CACHE_NAME version
4. Test cache invalidation
5. Update manifest.json with icon reference

_Workbox CLI:_

1. Create icon file
2. Update glob pattern if needed
3. Regenerate service worker
4. Update manifest.json with icon reference
5. Test

_vite-plugin-pwa:_

1. Create icon file in public/
2. Update manifest.icons array in vite.config.ts
3. Build (automatic regeneration)

**Task: Deploy update**

_Manual:_

1. Increment cache version
2. Update asset list with new hashes
3. Deploy
4. Users get update on next visit
5. Hope you didn't miss any assets

_Workbox CLI:_

1. Regenerate service worker
2. Deploy
3. Users get update

_vite-plugin-pwa:_

1. Deploy (plugin handles everything)
2. Users auto-update on next visit

The plugin approach wins for maintainability and developer experience. You sacrifice some control, but gain reliability and simplicity.

## Service Workers and Caching Strategies

Service workers are the backbone of PWA offline functionality. Let's understand how they work and how vite-plugin-pwa uses Workbox to manage them.

### What is a Service Worker?

A service worker is a JavaScript file that runs in the background, separate from your web page. It can't access the DOM, but it can:

- Intercept network requests
- Cache responses
- Respond to requests from cache
- Run even when the app isn't open (for push notifications, background sync)

Think of it as a programmable proxy between your app and the network.

### Service Worker Lifecycle

Service workers have a specific lifecycle:

**1. Registration**

Your app registers the service worker:

```javascript
// Generated by vite-plugin-pwa in index.html
if ('serviceWorker' in navigator) {
  navigator.serviceWorker
    .register('/sw.js')
    .then((registration) => {
      console.log('SW registered:', registration);
    })
    .catch((error) => {
      console.log('SW registration failed:', error);
    });
}
```

**2. Installation**

Service worker downloads and installs:

```javascript
// Inside sw.js (generated by Workbox)
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('precache-v1').then((cache) =>
      cache.addAll([
        '/',
        '/index.html',
        '/assets/index-abc123.js',
        // ... all assets
      ])
    )
  );
  self.skipWaiting(); // Activate immediately
});
```

**3. Activation**

Service worker activates and takes control:

```javascript
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((cacheNames) => {
      // Delete old caches
      return Promise.all(
        cacheNames.filter((name) => name !== 'precache-v1').map((name) => caches.delete(name))
      );
    })
  );
  self.clients.claim(); // Control all tabs immediately
});
```

**4. Fetch Interception**

Service worker intercepts network requests:

```javascript
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((response) => {
      // Return cached response if found
      return response || fetch(event.request);
    })
  );
});
```

**5. Update**

When a new service worker is detected:

1. New service worker downloads and installs in parallel
2. Old service worker remains active
3. When all tabs close, new service worker activates
4. Next visit uses new service worker

With `skipWaiting()` and `clients.claim()`, the new service worker activates immediately.

### Caching Strategies

Workbox provides several caching strategies. vite-plugin-pwa uses them automatically:

**1. Precache (Install-Time Caching)**

Cache assets during installation. Used for app shell:

```javascript
// vite-plugin-pwa generates this automatically
workbox.precaching.precacheAndRoute([
  { url: '/index.html', revision: 'abc123' },
  { url: '/assets/index.js', revision: 'def456' },
  // ... all assets with revision hashes
]);
```

BroteinBuddy precaches:

- HTML entry point
- All JavaScript bundles (Vite chunks)
- All CSS files
- Icons and SVGs
- Fonts

Total: 21 entries, 432.55 KB

**2. CacheFirst (Cache, Falling Back to Network)**

Check cache first, use network if not found:

```javascript
// Good for: fonts, images, assets that rarely change
workbox.routing.registerRoute(
  /^https:\/\/fonts\.googleapis\.com\/.*/i,
  new workbox.strategies.CacheFirst({
    cacheName: 'google-fonts-cache',
    expiration: {
      maxEntries: 10,
      maxAgeSeconds: 60 * 60 * 24 * 365, // 1 year
    },
  })
);
```

**Flow:**

1. Request intercepted
2. Check cache
3. If found: return cached response (fast!)
4. If not found: fetch from network, cache, return

**3. NetworkFirst (Network, Falling Back to Cache)**

Try network first, use cache if offline:

```javascript
// Good for: API requests, dynamic content
new workbox.strategies.NetworkFirst({
  cacheName: 'api-cache',
  networkTimeoutSeconds: 3,
});
```

**Flow:**

1. Try network with timeout
2. If success: update cache, return response
3. If timeout or offline: return cached response
4. If no cache: fail

**4. StaleWhileRevalidate (Cache + Background Update)**

Return cache immediately, update in background:

```javascript
// Good for: frequently updated content where staleness is ok
new workbox.strategies.StaleWhileRevalidate({
  cacheName: 'content-cache',
});
```

**Flow:**

1. Return cached response immediately (fast!)
2. Fetch from network in background
3. Update cache for next time

### Our Configuration

BroteinBuddy uses two strategies:

**Precache strategy (for app assets):**

```typescript
workbox: {
  globPatterns: ['**/*.{js,css,html,svg,png,ico,txt,woff2}'],
}
```

This precaches everything in `dist/` matching the pattern. On first visit, all assets download and cache. Subsequent visits load from cache (instant).

**CacheFirst strategy (for Google Fonts):**

```typescript
runtimeCaching: [
  {
    urlPattern: /^https:\/\/fonts\.googleapis\.com\/.*/i,
    handler: 'CacheFirst',
    options: {
      cacheName: 'google-fonts-cache',
      expiration: {
        maxEntries: 10,
        maxAgeSeconds: 60 * 60 * 24 * 365,
      },
    },
  },
];
```

If we ever add Google Fonts, they'll cache for 1 year.

### Why This Works for BroteinBuddy

Our caching strategy is simple because our app is simple:

1. **Static app shell** - HTML, JS, CSS never change between versions
2. **No API calls** - All data in LocalStorage
3. **No dynamic content** - Everything precached
4. **Small bundle** - 432 KB total (fits easily in cache)

This means:

- Offline works perfectly (no network needed after first visit)
- Updates are simple (replace entire cache)
- No cache invalidation complexity
- No stale data issues

More complex apps would need:

- NetworkFirst for API requests
- StaleWhileRevalidate for dynamic content
- Cache versioning strategies
- Partial cache updates

## The Web App Manifest

The web app manifest is a JSON file that tells the browser how to install and display your PWA.

### What is a Manifest?

A manifest is metadata about your app:

```json
{
  "name": "BroteinBuddy",
  "short_name": "BroteinBuddy",
  "description": "Track your protein shake inventory",
  "theme_color": "#4F46E5",
  "background_color": "#FFFFFF",
  "display": "standalone",
  "orientation": "portrait",
  "scope": "/",
  "start_url": "/",
  "icons": [
    {
      "src": "/icon-192.png",
      "sizes": "192x192",
      "type": "image/png"
    }
  ]
}
```

### Manifest Fields Explained

**name** (required)

Full app name shown during installation:

```json
"name": "BroteinBuddy"
```

Shown in:

- Installation prompts
- App switcher
- Splash screens

**short_name** (optional but recommended)

Shorter name for home screen (iOS 12-character limit):

```json
"short_name": "BroteinBuddy"
```

Used when space is limited:

- Home screen icon label
- Notification headers

**description** (optional)

Brief description of app:

```json
"description": "Track your protein shake inventory by flavor and location with weighted random selection"
```

Shown in:

- Installation dialogs
- App directories
- Search results

**theme_color** (recommended)

Color for browser chrome and status bar:

```json
"theme_color": "#4F46E5"
```

We use indigo-600 from our design system (ADR-005). This colors:

- Address bar on Android
- Status bar on iOS (via meta tag)
- Splash screen theme

**background_color** (recommended)

Background color for splash screen:

```json
"background_color": "#FFFFFF"
```

White background matches our app's default background.

**display** (important)

How the app displays when launched:

```json
"display": "standalone"
```

Options:

- `fullscreen` - Full screen, no browser UI (games)
- `standalone` - Like a native app, no browser UI ← We use this
- `minimal-ui` - Minimal browser UI (back/forward)
- `browser` - Normal browser tab

Standalone gives app-like feel without browser chrome.

**orientation** (optional)

Lock orientation:

```json
"orientation": "portrait"
```

Options: `portrait`, `landscape`, `any`

We lock to portrait because BroteinBuddy is a mobile utility app.

**scope** (recommended)

Which URLs belong to this app:

```json
"scope": "/"
```

URLs starting with `/` are considered part of the app. Navigate outside scope and browser chrome reappears.

**start_url** (required)

URL to load when app launches:

```json
"start_url": "/"
```

Add query params for analytics:

```json
"start_url": "/?source=homescreen"
```

**icons** (required)

Array of icon objects:

```json
"icons": [
  {
    "src": "/icon-192.png",
    "sizes": "192x192",
    "type": "image/png",
    "purpose": "any"
  },
  {
    "src": "/icon-192-maskable.png",
    "sizes": "192x192",
    "type": "image/png",
    "purpose": "maskable"
  },
  {
    "src": "/icon-512.png",
    "sizes": "512x512",
    "type": "image/png",
    "purpose": "any"
  },
  {
    "src": "/icon-512-maskable.png",
    "sizes": "512x512",
    "type": "image/png",
    "purpose": "maskable"
  }
]
```

Icon requirements:

- At least 192x192 and 512x512 sizes
- PNG format (widely supported)
- `purpose: "any"` - Standard icons
- `purpose: "maskable"` - Adaptive icons (Android)

## iOS-Specific PWA Considerations

iOS has unique PWA behavior and limitations. Understanding these is critical for a good iOS user experience.

### How PWAs Work on iOS

iOS Safari supports PWAs, but differently than Android Chrome:

**Installation:**

- No automatic install prompt
- User must manually tap Share → Add to Home Screen
- Icon appears on home screen

**Standalone mode:**

- Launches in separate Safari process
- No address bar or browser chrome
- Looks like a native app

**Limitations:**

- No push notifications (Safari restriction)
- No background sync
- LocalStorage shared with Safari (not isolated)
- Service worker restrictions
- No install banner

### iOS Meta Tags

iOS requires specific meta tags for proper PWA behavior. These go in `index.html`:

**1. apple-mobile-web-app-capable**

Enables standalone mode:

```html
<meta name="apple-mobile-web-app-capable" content="yes" />
```

When user adds to home screen, app launches full-screen without Safari UI.

Without this tag: App opens as a Safari bookmark (address bar visible).

**2. apple-mobile-web-app-status-bar-style**

Controls status bar appearance:

```html
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
```

Options:

### iOS PWA Lifecycle

Understanding how iOS handles PWA lifecycle:

**First visit:**

1. User visits URL in Safari
2. Service worker registers
3. Assets cache in background
4. User taps Share → Add to Home Screen
5. Icon appears on home screen

**Launching installed app:**

1. User taps home screen icon
2. Splash screen displays (generated from manifest)
3. App loads in standalone Safari process
4. Service worker serves cached assets
5. App renders

**Closing app:**

1. User swipes up to close
2. Service worker continues running briefly
3. iOS suspends process to save battery

**Returning to app:**

1. If process still in memory: instant resume
2. If process killed: relaunch from cache

### iOS Limitations and Workarounds

iOS imposes restrictions on PWAs. Here's how we handle them:

**Limitation 1: No Push Notifications**

iOS Safari doesn't support push notifications for PWAs.

**Our workaround:** Not needed for BroteinBuddy (local-only app).

**Limitation 2: No Background Sync**

Service workers can't sync data in background on iOS.

**Our workaround:** All data in LocalStorage (no sync needed).

**Limitation 3: No Install Prompt**

iOS doesn't show automatic install prompts.

**Our workaround:** Add instructions in README and potentially in-app hint.

**Limitation 4: Storage Limits**

LocalStorage limited to 5-10 MB depending on iOS version.

**Our workaround:** BroteinBuddy data is tiny (< 1 MB). See teaching doc 1.2 for quota handling.

**Limitation 5: Service Worker Eviction**

iOS may evict service workers if not used for ~2 weeks.

**Our workaround:** First visit after eviction re-registers service worker. Transparent to user.

**Limitation 6: No Share Target API**

Can't register as share target like Android.

**Our workaround:** Not needed for our use case.

Icons are the visual identity of your PWA. They must look good at multiple sizes and on different platforms.

- Simple, recognizable shape
- Works at small sizes

**favicon.svg** - Simplified favicon:

Features:

### Maskable Icons

Android adaptive icons use "maskable" format. The icon is placed within a safe zone, and Android applies various masks (circle, squircle, rounded square).

**Safe zone:**

- Icon must fit within circle inscribed in square
- Content outside circle may be cropped
- Diameter = 80% of total size

```
┌─────────────────┐
│     ┌─────┐     │ ← Minimum safe zone (80%)
│   ┌─┴─────┴─┐   │
│   │  ICON   │   │
│   │ CONTENT │   │
│   └─────────┘   │
└─────────────────┘
```

**Our approach:**

We use the same icon for `any` and `maskable` purposes because our design fits comfortably within the safe zone. The protein shaker bottle is centered and doesn't extend to edges.

More complex icons might need separate maskable variants with extra padding.

## How It All Works Together

Let's trace the complete flow from visiting the app to offline functionality.

### First Visit: Installation and Caching

**1. User visits https://broteinbuddy.vercel.app**

Browser requests `index.html`:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta name="theme-color" content="#4F46E5" />
    <meta name="apple-mobile-web-app-capable" content="yes" />
    <link rel="manifest" href="/manifest.webmanifest" />
    <link rel="apple-touch-icon" href="/apple-icon-180.png" />
  </head>
  <body>
    <div id="app"></div>
    <script type="module" src="/src/main.ts"></script>
  </body>
</html>
```

**2. Browser parses HTML**

- Loads CSS and JavaScript
- Reads manifest.webmanifest
- Discovers service worker registration code (injected by vite-plugin-pwa)

**3. Service worker registers**

```javascript
// Auto-injected by vite-plugin-pwa
if ('serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js', { scope: '/' }).then((registration) => {
      console.log('SW registered:', registration.scope);
    });
  });
}
```

**4. Service worker installs**

```javascript
// Inside generated sw.js
self.addEventListener('install', (event) => {
  event.waitUntil(
    self.caches.open('workbox-precache-v1').then((cache) =>
      cache.addAll([
        '/index.html',
        '/assets/index-abc123.js',
        '/assets/index-def456.css',
        '/icon-192.png',
        '/icon-512.png',
        // ... all 21 assets
      ])
    )
  );
  self.skipWaiting();
});
```

Browser downloads and caches all 21 assets (432.55 KB total).

**5. Service worker activates**

```javascript
self.addEventListener('activate', (event) => {
  event.waitUntil(self.clients.claim());
});
```

Service worker takes control of the page.

**6. App renders**

Svelte app initializes:

- Loads state from LocalStorage
- Renders UI
- User interacts with app

### Second Visit: Offline-First Experience

**1. User returns (even offline)**

Browser checks for service worker.

**2. Service worker intercepts requests**

```javascript
self.addEventListener('fetch', (event) => {
  const { request } = event;

  // Check if request matches precached asset
  const cached = caches.match(request);

  if (cached) {
    // Return from cache immediately (fast!)
    event.respondWith(cached);
  } else {
    // Not in cache, fetch from network
    event.respondWith(fetch(request));
  }
});
```

**3. All assets served from cache**

- `index.html` from cache
- `index-abc123.js` from cache
- `index-def456.css` from cache
- Icons from cache

No network requests needed. App loads instantly, even offline.

**4. App loads from LocalStorage**

```javascript
// src/lib/storage.ts
export function loadState(): AppState {
  const stored = localStorage.getItem(STORAGE_KEY);
  // ... parse and validate
  return parsed;
}
```

LocalStorage is separate from service worker cache. Data persists.

**5. User sees their data**

App renders with boxes, flavors, settings - all from LocalStorage.

### Deployment Update Flow

**1. New version deployed**

Developer runs:

```bash
npm run build
git push
```

Vercel deploys new version with updated assets:

- `index-xyz789.js` (new hash)
- Updated `sw.js` with new precache manifest

**2. User visits app**

Browser checks for service worker updates:

```javascript
navigator.serviceWorker.register('/sw.js').then((registration) => {
  registration.addEventListener('updatefound', () => {
    const newWorker = registration.installing;

    newWorker.addEventListener('statechange', () => {
      if (newWorker.state === 'activated') {
        // New service worker activated
        console.log('New version available!');
      }
    });
  });
});
```

**3. New service worker installs**

```javascript
// New sw.js
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches
      .open('workbox-precache-v2') // New cache version
      .then((cache) =>
        cache.addAll([
          '/index.html',
          '/assets/index-xyz789.js', // New hash
          '/assets/index-ghi012.css', // New hash
          // ... updated assets
        ])
      )
  );
  self.skipWaiting(); // Activate immediately
});
```

**4. New service worker activates**

```javascript
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((cacheNames) => {
      // Delete old cache
      return Promise.all(
        cacheNames
          .filter((name) => name.startsWith('workbox-precache'))
          .filter((name) => name !== 'workbox-precache-v2')
          .map((name) => caches.delete(name))
      );
    })
  );
  self.clients.claim();
});
```

Old cache deleted, new assets cached.

**5. User gets new version**

Next page load serves new assets from updated cache. Seamless update.

### The Complete Architecture

```
┌─────────────────────────────────────────────────┐
│                   Browser                       │
│                                                 │
│  ┌──────────────┐         ┌─────────────────┐  │
│  │   Svelte     │         │  LocalStorage   │  │
│  │     App      │◄───────►│  (AppState)     │  │
│  └──────────────┘         └─────────────────┘  │
│         ▲                                       │
│         │                                       │
│         ▼                                       │
│  ┌──────────────────────────────────────────┐  │
│  │         Service Worker                   │  │
│  │                                          │  │
│  │  ┌────────────────────────────────────┐ │  │
│  │  │    Cache Storage                   │ │  │
│  │  │                                    │ │  │
│  │  │  workbox-precache-v1:             │ │  │
│  │  │    - /index.html                  │ │  │
│  │  │    - /assets/index-abc123.js      │ │  │
│  │  │    - /assets/index-def456.css     │ │  │
│  │  │    - /icon-192.png                │ │  │
│  │  │    - ... (21 entries, 432 KB)     │ │  │
│  │  │                                    │ │  │
│  │  │  google-fonts-cache:              │ │  │
│  │  │    - (fonts if used)              │ │  │
│  │  └────────────────────────────────────┘ │  │
│  └──────────────────────────────────────────┘  │
│         ▲                                       │
│         │ fetch()                               │
│         ▼                                       │
│  ┌──────────────┐                              │
│  │   Network    │                              │
│  └──────────────┘                              │
└─────────────────────────────────────────────────┘
           │
           │ HTTPS
           ▼
    ┌──────────────┐
    │    Vercel    │
    │  (CDN Host)  │
    └──────────────┘
```

**Data flow:**

1. **First visit:** Network → Service Worker → Cache → App
2. **Offline visit:** Cache → App
3. **Update:** Network → New Service Worker → New Cache → App
4. **Data persistence:** App ↔ LocalStorage (independent of cache)

## Design Trade-offs

Every technical decision involves trade-offs. Here's what we optimized for and what we sacrificed.

### What We Optimized For

**1. Developer Experience**

Choice: vite-plugin-pwa over manual service worker

Benefit:

- Single configuration file
- Auto-generated manifest and service worker
- Integrated with Vite build
- Less boilerplate
- Fewer bugs

Trade-off: Less control over caching logic, dependency on plugin updates

**2. Offline Reliability**

Choice: Precache all assets during installation

Benefit:

- App works 100% offline after first visit
- No network dependency for app shell
- Instant loads from cache
- Guaranteed consistency

Trade-off: Larger initial download (432 KB), all-or-nothing caching

**3. Simplicity**

Choice: LocalStorage instead of IndexedDB

Benefit:

- Simpler API
- Synchronous (no async complexity)
- Sufficient for our data size
- Works perfectly offline

Trade-off: Storage limits (5-10 MB), no advanced query capabilities

**4. Auto-Updates**

Choice: `registerType: 'autoUpdate'` with `skipWaiting()`

Benefit:

- Users always get latest version
- No manual update prompts
- Seamless update experience
- No stale code

Trade-off: Can't defer updates, potential mid-session disruption (mitigated by page load timing)

**5. iOS Compatibility**

Choice: iOS-specific meta tags and 180x180 icon

Benefit:

- Works on iOS Safari
- Looks native when installed
- Proper status bar styling
- Home screen icon quality

Trade-off: Extra configuration, manual testing required

### What We Sacrificed

**1. Fine-Grained Control**

We can't:

- Customize cache invalidation logic beyond Workbox strategies
- Implement custom service worker features easily
- Control exact update timing per user

Why it's okay: Workbox strategies cover 95% of use cases. Custom logic adds complexity we don't need.

**2. Partial Updates**

All-or-nothing caching:

- New version caches all assets
- Can't update individual files
- No incremental updates

Why it's okay: Bundle is small (432 KB). Users have fast internet. Full cache replacement is simple and reliable.

**3. Advanced PWA Features**

No support for:

- Push notifications (iOS limitation anyway)
- Background sync (iOS limitation)
- Periodic background sync
- Web Share Target

Why it's okay: BroteinBuddy doesn't need these. Local-only app, no server communication.

**4. Native App Features**

Can't access:

- Native file system
- Device sensors (mostly)
- Deep OS integration
- Siri shortcuts

Why it's okay: Utility app needs basic features. Web APIs sufficient.

**5. App Store Presence**

No listing in:

- iOS App Store
- Google Play Store
- Discoverability through stores

Why it's okay: Personal project, URL distribution works. No need for store presence.

### Real-World Compromises

**Compromise 1: Icon Generation**

Ideal: Automated icon generation in build pipeline
Reality: Manual PNG generation with pwa-asset-generator CLI

Why: vite-plugin-pwa doesn't generate PNGs from SVG automatically. Adding build step increases complexity. Manual generation once is acceptable.

Impact: Must remember to regenerate icons if design changes.

Future: Could add build script if icons change frequently.

**Compromise 2: iOS Installation UX**

Ideal: Automatic install prompt like Android
Reality: Manual "Add to Home Screen" with multi-step process

Why: iOS Safari doesn't support install prompts. Apple design decision.

Impact: Users must know to use Share → Add to Home Screen. Reduced discoverability.

Mitigation: Add installation instructions in README (Phase 3.4), potentially in-app hint.

**Compromise 3: Service Worker Debugging**

Ideal: Service worker debugger in dev mode
Reality: Must build and preview to test

Why: Service workers disabled in Vite dev mode (for good reasons - hot reload conflicts with caching).

Impact: Slower iteration when testing offline features.

Mitigation: Use preview mode, DevTools testing, automated tests.

**Compromise 4: Update Strategy**

Ideal: Prompt user "Update available, reload?"
Reality: Auto-update on page load

Why: `skipWaiting()` activates immediately. Adding update prompts requires custom UI and state management.

Impact: Users might miss update notes. Mid-session updates could be jarring (though unlikely - updates happen on page load).

Mitigation: Keep updates small and non-breaking. Add changelog in future if needed.

**Compromise 5: Bundle Size**

Ideal: < 100 KB total
Reality: 432 KB total

Why: Svelte framework, routing library, drag-and-drop library, service worker overhead.

Impact: Slower first load on slow connections (2-5 seconds on 3G).

Mitigation: Code splitting (Phase 3.3), tree shaking, lazy loading. 432 KB is reasonable for modern PWAs.

### Lessons Learned

**1. Start with Plugin, Not Manual**

Initial plan considered manual service worker. Using vite-plugin-pwa saved hours of boilerplate.

Lesson: Use well-maintained plugins for standard functionality. Save custom code for unique requirements.

**2. Test on Real Devices Early**

iOS Simulator doesn't accurately reflect PWA behavior. Real iPhone testing revealed issues with status bar and icons.

Lesson: Deploy early, test on target devices. Emulators insufficient for PWAs.

**3. Document iOS Installation**

"Add to Home Screen" isn't discoverable. Users won't find it without instructions.

Lesson: User education critical for iOS PWAs. Plan for installation documentation.

**4. Keep Bundle Small**

432 KB is manageable, but every KB matters for mobile users.

Lesson: Monitor bundle size. Tree shake aggressively. Code split in Phase 3.3.

**5. Offline-First from Start**

Building offline support into Phase 3.2 was right. Retrofitting would be harder.

Lesson: PWA features should be planned early, not bolted on later.

## Common Pitfalls and How to Avoid Them

Learning from others' mistakes.

### Pitfall 1: Forgetting HTTPS Requirement

**Problem:**

Service workers require HTTPS. Deploying to HTTP breaks PWA.

**Symptoms:**

- Service worker fails to register
- Console error: "SecurityError: Service Worker registration failed"
- Manifest doesn't load

**Solution:**

Always use HTTPS for production. Localhost is exempt.

```
Development: http://localhost:5173 ✓ (exempt)
Production: https://yourapp.com ✓ (required)
Production: http://yourapp.com ✗ (fails)
```

Vercel provides HTTPS by default. No configuration needed.

### Pitfall 2: Caching index.html Incorrectly

**Problem:**

Aggressive caching of `index.html` prevents updates.

**Symptoms:**

- New deployments don't appear
- Users stuck on old version
- Hard reload required to see changes

**Solution:**

vite-plugin-pwa handles this correctly by:

1. Using revision hashes in precache manifest
2. Checking for updates on page load
3. Re-caching index.html when service worker updates

Don't manually cache index.html with long expiration.

### Pitfall 3: Large Bundle in Precache

**Problem:**

Precaching 10+ MB of assets on first visit.

**Symptoms:**

- Slow first load
- QuotaExceededError on some devices
- Poor user experience

**Solution:**

Keep precache small:

- Code split non-critical routes (Phase 3.3)
- Lazy load large dependencies
- Use runtime caching for optional assets
- Monitor bundle size

Our 432 KB is acceptable. Aim for < 1 MB.

### Pitfall 4: Missing Icon Sizes

**Problem:**

Only providing one icon size.

**Symptoms:**

- Icons blurry on high-DPI displays
- Install prompt doesn't appear
- Lighthouse PWA audit fails

**Solution:**

Provide at minimum:

- 192x192 PNG
- 512x512 PNG
- 180x180 PNG (iOS)
- Maskable variants

Use pwa-asset-generator to generate all sizes from SVG.

### Pitfall 5: Wrong Display Mode

**Problem:**

Using `display: "browser"` instead of `"standalone"`.

**Symptoms:**

- App opens in browser tab
- Safari UI visible
- Doesn't feel like native app

**Solution:**

Set `display: "standalone"` in manifest:

```json
{
  "display": "standalone"
}
```

Test on device to verify.

### Pitfall 6: Ignoring iOS Specifics

**Problem:**

Only testing on Chrome/Android, not iOS.

**Symptoms:**

- App doesn't install correctly on iOS
- Icon missing or wrong size
- Status bar looks wrong
- Users confused about installation

**Solution:**

Add iOS meta tags:

```html
<meta name="apple-mobile-web-app-capable" content="yes" />
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent" />
<link rel="apple-touch-icon" href="/apple-icon-180.png" />
```

Test on real iPhone.

### Pitfall 7: Service Worker Scope Issues

**Problem:**

Service worker registered with wrong scope.

**Symptoms:**

- Service worker only controls some routes
- Offline mode partially works
- Manifest loaded from wrong path

**Solution:**

Set scope to `/`:

```javascript
navigator.serviceWorker.register('/sw.js', { scope: '/' });
```

vite-plugin-pwa does this automatically.

### Pitfall 8: Not Handling Updates

**Problem:**

Old service worker never replaced by new one.

**Symptoms:**

- Users stuck on old version forever
- Must manually clear cache
- Deployment updates invisible

**Solution:**

Use `skipWaiting()` and `clients.claim()`:

```javascript
self.addEventListener('install', () => {
  self.skipWaiting();
});

self.addEventListener('activate', () => {
  self.clients.claim();
});
```

Or use vite-plugin-pwa's `registerType: 'autoUpdate'`.

### Pitfall 9: LocalStorage Quota Exceeded

**Problem:**

Assuming unlimited localStorage.

**Symptoms:**

- QuotaExceededError thrown
- Data fails to save
- App breaks on save

**Solution:**

Catch quota errors:

```typescript
try {
  localStorage.setItem(key, value);
} catch (error) {
  if (error.name === 'QuotaExceededError') {
    // Handle quota exceeded
    alert('Storage full. Please delete old data.');
  }
}
```

See teaching doc 1.2 for full error handling.

### Pitfall 10: Testing Only in Dev Mode

**Problem:**

Running `npm run dev` to test PWA features.

**Symptoms:**

- Service worker doesn't register
- Manifest not found
- Offline mode doesn't work

**Solution:**

Always test with production build:

```bash
npm run build
npm run preview
```

Dev mode intentionally disables service workers for hot reload.

## Conclusion

Progressive Web Apps bridge the gap between web and native applications. By implementing PWA functionality in BroteinBuddy, we've created an app that:

- Installs to the iOS home screen
- Works completely offline after first visit
- Feels like a native app in standalone mode
- Updates automatically on new deployments
- Loads instantly from cache

The key technologies - service workers, web app manifest, and Workbox caching - work together to provide a seamless offline-first experience. Using vite-plugin-pwa simplified implementation while maintaining flexibility.

iOS-specific considerations required extra attention: meta tags, apple-touch-icon, and manual installation process. Testing on real devices proved essential for catching iOS-specific issues.

The result is a fully installable, offline-capable web app that rivals native apps in user experience, all from a single codebase deployed as a static site.

**Next steps (Phase 3.3):** Optimize performance, bundle size, and accessibility to ensure the PWA meets production quality standards.
