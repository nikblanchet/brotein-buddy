## Three Gaps, Three Fixes

PR 2 (ADR-012, teaching doc 1.7) shipped a working push/pull coordinator with
magic-link auth, RLS-protected tables, and a conflict modal. Read in
isolation, it looked complete. ADR-013's context section lists three gaps
that, in combination, would have been a quietly catastrophic experience for
exactly one of the users this app is built for — me, in the desert.

**Gap 1: no realtime propagation.** A push from Device A only reached Device
B on Device B's next manual reload. For a single-user app with two devices
(phone in pocket, iPad in the kitchen), that's a usability paper-cut, not a
disaster. But the schema and infra were already in place to do better, and
the cost of leaving it as paper-cut was negative because the next gap is
worse.

**Gap 2: no retry on failure.** PR 2's `runPush` looked like this:

```ts
async function runPush(state: AppState): Promise<void> {
  if (!currentSession) return;
  try {
    await pushFullState(state);
    markSynced();
  } catch (err) {
    recordError(err);
  }
}
```

`recordError` set `status='error'`. That was the entire failure handling.
If the next mutation didn't fire (because the user put the phone down), the
edit lived on the device forever — until the next launch's `INITIAL_SESSION`
pull, which leads us directly to Gap 3.

**Gap 3: the Burning Man footgun.** PR 2's `INITIAL_SESSION` handler did
exactly this (the old code, paraphrased from PR 2's
`silentPullIfPresent`):

```ts
if (event === 'INITIAL_SESSION') {
  const pulled = await pullFullState();
  if (pulled) {
    applyServerState(pulled);
  }
}
```

Trace the scenario. Sign in at home before leaving for the desert. Open the
app on the playa, no signal. Spend 10 days logging shakes — 30 to 50 events
accumulate in LocalStorage. The auto-save subscription is happily writing
to `BROTEINBUDDY_APP_STATE` on every mutation, exactly as designed. Day 8,
the iPad needs a restart. The browser reloads the SPA. supabase-js sees a
cached session in LocalStorage, fires `INITIAL_SESSION`. The coordinator
pulls the server's 10-day-stale snapshot and calls `applyServerState`. The
auto-save subscription writes that stale snapshot back to LocalStorage. Ten
days of offline edits are gone, with no error, no warning, no recovery.

That's the bug PR 3 has to close. The other two fixes (realtime + retry)
are also real, but Gap 3 is the one that would have been a felt loss. The
dirty bit (next major section) is the load-bearing fix.

The three gaps motivated three new pieces:

1. A Realtime subscription module (`src/lib/realtime.ts`), so changes from
   another device propagate without a reload.
2. Persistent sync metadata (`src/lib/sync-meta.ts`) — specifically, the
   `dirty` flag — and a meta-aware `reconcileSync` function that knows when
   pulling would destroy work.
3. Push retry with exponential backoff and an "offline" status that
   suppresses the per-mutation push debounce so the app doesn't drain the
   battery retrying every keystroke.

Plus an always-visible status badge in the Inventory header
(`src/lib/components/SyncStatusBadge.svelte`) so the user can see, at a
glance, whether their last edit reached the server.

The rest of this document is the elaboration of why each piece looks the
way it does. ADR-013 is the "what was decided"; this is the "why."

## Supabase Realtime Is a Postgres Publication

Before talking about the client code, it's worth a paragraph on what
"Supabase Realtime" actually is, because it's not magic, and the migration
makes a lot more sense once you see it.

Postgres has a feature called **logical replication**. The idea: instead of
streaming raw on-disk bytes (physical replication), Postgres can stream a
decoded sequence of logical change events ("row X was inserted into table T
with these column values"). The primary publishes events; subscribers
consume them. The set of tables that participate is defined by a
**publication** — a named, ALTER-able collection of tables. By default,
nothing is in any publication.

Supabase ships a publication called `supabase_realtime`. The Supabase
Realtime service is a long-running process that connects to Postgres as a
replication subscriber for that publication and rebroadcasts the decoded
changes over WebSocket. The client library
(`@supabase/supabase-js`) exposes a friendlier wrapper:
`supabase.channel(...).on('postgres_changes', ...)`. Under the hood it's a
WebSocket multiplexed by topic, with auth piggybacking on the same JWT
that gates RLS.

For a table to be visible at all, it has to be in the publication. The
migration is two lines (`supabase/migrations/20260514120000_enable_realtime.sql:18-19`):

```sql
alter publication supabase_realtime add table public.events;
alter publication supabase_realtime add table public.app_states;
```

A few properties worth being explicit about:

- **RLS still applies.** Realtime is a separate transport from regular
  queries, but the same RLS policies gate which rows reach a subscriber.
  The `app_states owner select` policy from PR 2's migration (`auth.uid()
= user_id`) is consulted for every broadcast row. A subscriber with no
  JWT, or the wrong user's JWT, never sees the row. We don't need a
  parallel auth model for Realtime — RLS is one body of policy that
  governs both.
- **The `user_id=eq.<id>` filter in `realtime.ts` is an optimisation, not
  a guard.** Without it, Supabase still wouldn't deliver other users' rows
  (RLS), but the server would consider each one for delivery and drop it.
  With the filter, the broadcast layer skips them entirely. Defence in
  depth and a perf win.
- **We pick INSERT for `events` and UPDATE for `app_states`.** Events are
  append-only (PR 2's RLS policy has no update/delete branch), so INSERT
  is the only thing that ever happens. `app_states` is one row per user,
  upserted on every push — UPDATE catches every change after the initial
  insert.

The `app_states` UPDATE channel is what catches "manual edits that don't
emit a timeline event" — the +/- quantity buttons in the Inventory page
mutate `boxes` via `updateBoxQuantity` (`src/lib/stores.ts:219-247`)
without writing an event row. Without the `app_states` channel, those
edits would only propagate on the next reload. The migration's inline
comment calls this out specifically — worth reading the SQL once for
the explanation.

## Option A vs Option B: The Pedantic Professor and the Google Architect

This is the single most important design decision in PR 3 and it's worth
spending real words on. When I scoped the realtime work I asked Claude
explicitly: "What's the correct way for the client to react to a remote
event broadcast?" The two answers were a fork.

**Option A.** When a remote event fires, ignore the payload entirely and
re-run the existing reconcile path — peek the server, compare to local
meta, pull if the server is fresher. The realtime broadcast is just a
_wake-up signal_; the actual decision and apply logic is the same code
that runs on `INITIAL_SESSION` and `SIGNED_IN`.

**Option B.** When a remote event fires, the broadcast already carries
the row payload. Run a local reducer (`applyEvent(state, event) →
state'`) to derive the new local state directly. No extra round-trip.
Lower latency. The cross-device feel is instant.

The pedantic-professor answer is **Option B**. It's strictly more
efficient. It's how a "real" distributed system would do it. CRDTs,
operational transforms, the whole literature on collaborative editing
points this direction.

The senior-Google-architect answer, for _this workload_, is **Option A**.
The reasoning:

- **Option A is one path.** `reconcileSync` already exists for auth events.
  Routing the realtime callback through the same function means the
  realtime case is a free side-effect of code that's already being
  written, debugged, and unit-tested. No new logic, no new test surface.
- **Option B is a parallel apply path.** A reducer for every event type
  (`box_received`, `box_opened`, `box_removed`, `shake_taken`,
  `shake_rejected`, `selection_cancelled`) — and the reducer has to
  handle all the invariants the server-side push would have enforced.
  `shake_taken` decrements `box.quantity`. What if the box doesn't exist
  locally yet (because we missed an earlier `box_received` broadcast due
  to a flaky connection)? What if it's already at zero? What if the
  remote event's payload has fields the local reducer doesn't know about
  (older client, newer server schema)?
- **Option B's bugs are user-visible "my data is wrong."** Option A's
  worst case is a 200 ms latency hit on a peek that didn't find new data.
  The asymmetry of failure modes is the dealbreaker. A wrong number in
  the inventory is a felt loss; 200 ms of staleness is not.
- **The workload doesn't justify the cost.** One user. Two or three
  devices. Maybe ten events on a heavy day. A spike of two simultaneous
  edits across devices is rare enough that the round-trip latency
  basically never manifests as "I waited for it."

I chose Option A. It's the right call for this workload. It would be the
wrong call for a multi-user collaborative editor.

The piece worth holding onto: **we deliberately isolated the apply
boundary in `src/lib/realtime.ts`** so a future swap to Option B is a
one-module change. Look at the realtime module's exported callback
signature (`src/lib/realtime.ts:31-32`):

```ts
/** Reason the coordinator was woken up. Surfaced for logging/testing. */
export type RemoteChangeReason = 'event-insert' | 'snapshot-update';
```

The callback receives a _reason_, not a _payload_. The realtime module
sees the payload (it has to — Supabase passes it to the handler) and
deliberately throws it away before talking to the coordinator. That
constraint forced the coordinator to be payload-agnostic from day one. If
we ever decide Option B is worth it:

1. Change the callback signature to pass the row payload.
2. Add an `applyEvent` reducer somewhere in `src/lib/`.
3. The coordinator's realtime handler calls the reducer instead of
   `reconcileSync`.

The change touches `realtime.ts`, the new reducer file, and the four-line
realtime handler in the coordinator (`src/lib/sync-coordinator.ts:249-258`).
Nothing else. Reconcile stays as the fallback for "first connection,
significant gap, suspicious meta" — Option B accelerates the steady state;
Option A remains the safety net.

> **General principle:** When you have a fast-but-fragile path and a
> slow-but-correct path, build the slow path first and isolate the
> boundary where the fast path _would_ plug in. The slow path is your
> safety net forever; the fast path is YAGNI until it isn't.

## The Dirty-Bit Invariant

This is the load-bearing concept of PR 3. Read this section twice.

The sync metadata module (`src/lib/sync-meta.ts`) is 87 lines of
TypeScript that stores three fields under
`BROTEINBUDDY_SYNC_META`:

```ts
export interface SyncMeta {
  dirty: boolean;
  lastServerUpdatedAt: string | null;
  lastSyncedAt: string | null;
}
```

(`src/lib/sync-meta.ts:20-39`)

`dirty` is the bit that closes the Burning Man footgun. Its invariant,
which I want you to be able to recite without looking, is this:

> **Anything that changes local state sets `dirty = true`. Only a
> successful push or pull clears it.**

That's it. Two clauses. Walk through them once concretely.

**Setter.** The `appState.subscribe` callback in the coordinator
(`src/lib/sync-coordinator.ts:103-112`):

```ts
appState.subscribe((state) => {
  if (suppressNextChange) {
    suppressNextChange = false;
    return;
  }
  markDirty();
  if (!currentSession) return;
  if (get(pendingConflictStore) !== null) return;
  schedulePush(state);
});
```

`markDirty()` runs **before** any of the early returns. Even if the user
is signed out, even if a conflict is pending, the bit gets set. The bit
is about local truth — has local diverged from "the server view at last
sync?" — and that question is answered by whether local has changed,
period, regardless of whether we're online or signed in.

The `suppressNextChange` guard is the one exception, and it's a _correct_
exception: that flag is set inside `applyServerState` immediately before
`replaceAppState`, so the very next subscriber call is a known-internal
pull-driven write. Skipping `markDirty` there is the whole point —
pulled-from-server state is by definition synced, not dirty.

**Clearer.** `persistAfterSync` (`src/lib/sync-coordinator.ts:336-344`):

```ts
function persistAfterSync(serverUpdatedAt: string | null): void {
  const meta: SyncMeta = {
    dirty: false,
    lastServerUpdatedAt: serverUpdatedAt,
    lastSyncedAt: new Date().toISOString(),
  };
  saveSyncMeta(meta);
  pendingChangesStore.set(false);
}
```

The only callers of `persistAfterSync` are `pushAndPersist` (after a
successful `pushFullState`) and the pull branch of `reconcileSync` (after
a successful `applyServerState`). Failed pushes never reach this code —
`runPush` (`src/lib/sync-coordinator.ts:317-328`) routes the catch to
`enterOfflineMode` instead.

**The Burning Man trace, with the dirty bit.** Same scenario as before:

1. Day 0, home wifi, sign in. Pull happens, meta written with
   `dirty: false`, `lastServerUpdatedAt: <today>`, `lastSyncedAt: <today>`.
2. Days 1–8, no signal, 40 mutations happen. Each one triggers
   `markDirty()`. The first one rewrites meta to `dirty: true`; subsequent
   ones short-circuit (`markDirty` checks `meta.dirty` and returns early
   if already dirty — `src/lib/sync-coordinator.ts:346-351`).
3. Day 8, tab reload. supabase-js fires `INITIAL_SESSION`.
4. The coordinator calls `reconcileSync({ treatLocalAsDirty: false })`.
   It peeks the server (`peekRemoteState`), loads meta, sees
   `meta.dirty === true`, sees `remote.updated_at === meta.lastServerUpdatedAt`
   (server hasn't changed since day 0).
5. Branch: `localDirty && !remoteFresher` → push. Push succeeds, server
   gets 40 days of accumulated events, meta cleared.

The bit is the difference between "silently overwrite 10 days of work"
and "push 10 days of work." That's the whole game.

### Alternatives that would have required a schema change

I considered three other shapes for this bookkeeping before landing on a
single bit.

**Event count delta.** Persist `lastSyncedEventCount` and compare to
`state.events.length`. Greater means dirty. Pro: zero per-mutation
write cost. Con: doesn't catch snapshot-only edits (the Inventory
+/- quantity buttons don't emit events). To make this complete you'd
need event count plus snapshot hash, which is two compares and a hash
computation.

**Hash of `AppState`.** On every load, hash local; compare to the last
synced hash. Pro: total. Con: hashing serializes the entire state on
every check; for a 700 KB state that's not free, and it pushes the
"work" from "occasional mark" to "every reconcile."

**Per-field dirty flags.** `boxesDirty`, `flavorsDirty`, `eventsDirty`.
Pro: lets a future field-level merge know what to send. Con: not
needed — push always sends everything — and three flags is just a
fancier bit.

The plain bit wins on every axis: it's correct, it costs one LocalStorage
write on the first mutation per sync cycle, it doesn't need a schema
version bump (the meta lives in its own key — `src/lib/sync-meta.ts:17`),
and it composes trivially with the timestamp-based "remote fresher"
check.

> **General principle:** Bookkeeping state belongs in its own key, not in
> the user-data schema. Otherwise every change to "did we sync yet"
> becomes a migration.

## `reconcileSync` as an Honest State Machine

The function that mediates every push/pull decision is
`reconcileSync(opts)` (`src/lib/sync-coordinator.ts:196-247`). It has
exactly five terminal branches and one parameter — `treatLocalAsDirty`.
Walk through it once.

```ts
async function reconcileSync(opts: { treatLocalAsDirty: boolean }): Promise<void> {
  statusStore.set('syncing');
  try {
    const remote = await peekRemoteState();
    const local = get(appState);
    const meta = loadSyncMeta();

    const localHasData = !isLocallyEmpty(local);
    const localDirty = opts.treatLocalAsDirty
      ? localHasData
      : meta.dirty || (localHasData && meta.lastSyncedAt === null);
    const remoteFresher =
      remote.exists &&
      (meta.lastServerUpdatedAt === null ||
        (remote.updatedAt !== null && remote.updatedAt > meta.lastServerUpdatedAt));

    if (!remote.exists) {
      await pushAndPersist(local);
      return;
    }

    if (localDirty && remoteFresher) {
      conflictLocalSnapshot = local;
      pendingConflictStore.set(remote);
      statusStore.set('conflict-pending');
      return;
    }

    if (localDirty) {
      await pushAndPersist(local);
      return;
    }

    if (remoteFresher) {
      const pulled = await pullFullState();
      if (pulled) {
        applyServerState(pulled);
        persistAfterSync(remote.updatedAt);
      }
      markSynced();
      return;
    }

    markSynced();
  } catch (err) {
    recordError(err);
    enterOfflineMode();
  }
}
```

Five branches:

1. **No remote row.** First sign-in ever. Push local up to seed the
   server. Empty pushes are fine — the resulting row has zero boxes /
   flavors / events but a real `user_id` and `updated_at`.
2. **Both dirty (local _and_ remote fresher than our last sync).** Real
   conflict. Surface the modal; do not auto-resolve.
3. **Local dirty, remote not fresher.** Push. This is the Burning Man
   path — local has accumulated edits, server hasn't moved.
4. **Remote fresher, local clean.** Pull. This is the "edited on the
   other device, opened here" path.
5. **Neither.** No-op. This is the common case after the first reconcile:
   we're already in sync.

### Why `treatLocalAsDirty` exists

The function takes one boolean parameter, and the two callers pass
different values:

- `INITIAL_SESSION` calls with `{ treatLocalAsDirty: false }`.
- `SIGNED_IN` calls with `{ treatLocalAsDirty: true }`.

The reason is subtle and worth dwelling on. On `INITIAL_SESSION`, the
local store and the meta were both written by the _same user in the same
browser_. The meta is authoritative — if `meta.dirty === false`, it's
genuinely false. If true, true. The local state belongs to this user.

On `SIGNED_IN`, the local store might have been written _by a different
user_. Concrete scenario: dad signs in on the kitchen iPad, uses the app,
signs out. Dad's edits are still in `BROTEINBUDDY_APP_STATE`. Son signs
in. Without `treatLocalAsDirty: true`, the coordinator would consult meta
(`dirty: false`, written by dad), decide local is clean, and silently
either pull or no-op — both of which leave dad's data accessible to son's
session. With `treatLocalAsDirty: true`, any non-empty local state forces
the conflict path. The modal pops up: "the server has X boxes, this
device has Y boxes, which do you want?" Son picks `keep-server` and gets
a clean slate.

This is a small example of a recurring shape in this codebase: **the same
function with two callers, parameterised by a property the callers know
and the function doesn't**. Same shape as `migrateState` running through
the chain of versions regardless of starting point (PR 1, teaching doc
1.6) — the function doesn't need to know "is this from a backup file or
from LocalStorage?", it just needs the data and a flag for the rare
case where source matters.

> **General principle:** When two callers of the same function differ
> only in their _suspicion of the input_, encode that suspicion as a
> parameter on the function. Don't fork into two parallel functions; the
> rest of the logic is identical and the duplication will rot.

## Loopback Prevention Without a Filter

When we push to the server, the Realtime broadcast for our own write
comes back to us. The naive worry is "infinite loop": push triggers
broadcast triggers reconcile triggers push triggers...

It doesn't, and the way it doesn't is worth understanding because it's
how Option A pays for itself.

After a successful push, `persistAfterSync` writes
`meta.lastServerUpdatedAt = <server's new updated_at>`. The Realtime
broadcast fires. The coordinator's realtime handler is one line, give or
take (`src/lib/sync-coordinator.ts:249-258`):

```ts
async function ensureRealtime(session: Session): Promise<void> {
  if (realtimeSub) return;
  realtimeSub = subscribeToRemoteChanges(session.user.id, () => {
    if (get(pendingConflictStore) !== null) return;
    void reconcileSync({ treatLocalAsDirty: false });
  });
}
```

The reconcile peeks. `remote.updatedAt` equals `meta.lastServerUpdatedAt`
(we just wrote it). The `remoteFresher` test
(`remote.updatedAt > meta.lastServerUpdatedAt`) is false. The
`localDirty` test is also false — we just pushed, `dirty` was cleared in
`persistAfterSync`. Both flags false → fifth branch → `markSynced` →
no-op. One extra peek round-trip per push, then quiet.

### Why not a timestamp filter in the realtime callback?

The naive alternative: in the realtime handler, remember our last push
timestamp, ignore broadcasts whose `commit_timestamp` matches. Faster —
no peek, no compare.

Worse in three ways:

1. **It would couple the realtime module to the push lifecycle.** The
   realtime module would need to know about pushes. The whole point of
   isolating it was that it doesn't.
2. **It's a fragile equality check on a server-assigned timestamp.** The
   broadcast carries `commit_timestamp` (when Postgres committed the
   row). The peek returns `updated_at` (when the row's column was
   updated, set by a trigger). They're related but not necessarily the
   same value at byte-equality. Comparing them is asking for a flaky
   "sometimes our own pushes echo through" bug.
3. **It's solving a problem we don't have.** The peek-and-compare is
   one round-trip. It's not zero, but it's not on the critical path of
   user input — the user already saw the optimistic local update before
   we even started pushing. One extra peek that almost always returns
   "no-op" is fine.

The chosen approach has the property I look for in this kind of code:
**the broadcast handler is dumb on purpose**. It doesn't know whether
"this might be our own write." It just says "something changed, ask the
reconciler." The reconciler is the single decision-maker. Single
decision-makers are easy to reason about; multiple decision-makers with
shared invariants are how distributed systems eat their owners.

> **General principle:** Prefer one expensive-but-correct check at a
> central decision point over many cheap-but-fragile filters scattered
> across event sources. Round-trips are cheap. Distributed correctness
> bugs are not.

## `navigator.onLine` Is a Liar (Especially on the Playa)

The web platform exposes two things relevant to offline detection:

- `navigator.onLine` (boolean): is the browser currently connected to a
  network?
- The `online` / `offline` events on `window`: fired when that boolean
  flips.

Both have a well-known flaw: they tell you about _network association_,
not _internet reachability_. On a captive-portal wifi (hotel lobby,
coffee shop, Burning Man's spotty mesh), `navigator.onLine === true`
even though the only thing you can reach is the captive-portal login
page. DNS lookups to api.supabase.co will fail or hang. To the browser,
you're "online." To Supabase, you're not.

The shape that follows from accepting the lie:

> **The `online` event is a signal to try, not proof of success. The
> only real online check is "did a push succeed?"**

The implementation (`src/lib/sync-coordinator.ts:114-129`):

```ts
if (typeof window !== 'undefined') {
  onlineHandler = () => {
    if (!currentSession) return;
    if (backoffTimer) {
      clearTimeout(backoffTimer);
      backoffTimer = null;
    }
    retryAttempt = 0;
    isKnownOffline = false;
    void runPush(get(appState));
  };
  window.addEventListener('online', onlineHandler);
}
```

When `online` fires, we cancel the backoff timer, reset the attempt
counter, clear the "known offline" flag, and try a push _immediately_.
If the push succeeds, great — we're back online for real, the dirty bit
clears, the badge goes from "Offline" to "Saved." If it fails (captive
portal lying to us), `runPush`'s catch routes us back through
`enterOfflineMode`, which sets `isKnownOffline = true` and schedules a
new backoff. The retry counter started over at zero, so the next backoff
is 1 second — meaning a real connection recovery typically detects fast.

**The Burning Man recovery trace.** Phone is in airplane mode for days.
Toggle wifi on. The wifi associates with whatever's available — call it
"BRC-Mesh", which is half-dead but technically associated. `online` event
fires. Coordinator cancels backoff, tries `runPush`. The request hangs
for the supabase-js default timeout, then errors. `recordError` →
`enterOfflineMode`, which sets `isKnownOffline = true` and
`scheduleBackoffRetry()` with `retryAttempt = 0` → delay = 1 second.
One second later, retry. Fails again, `retryAttempt = 1`, delay = 2s.
Then 4s, 8s, 16s, 32s, 60s (capped). At 60-second intervals it pings
until something works. The moment the captive portal actually routes,
the push succeeds. `runPush` calls `exitOfflineMode` which resets
`retryAttempt = 0`, calls `markSynced`, and the 50-event log is now on
the server.

The user sees, in order: the offline badge (blue, "Offline"), no
intervention required, eventually the saved badge (green, "Saved"). No
prompt, no "retry?" button, no choice to make. The right thing happens
on its own.

## Why Offline Mode Refuses to Reset the Push Debounce

This is a small piece of code and a deliberately subtle correctness call.
`schedulePush` (`src/lib/sync-coordinator.ts:301-315`):

```ts
function schedulePush(state: AppState): void {
  if (isKnownOffline) {
    statusStore.set('offline');
    return;
  }
  if (pushTimer) clearTimeout(pushTimer);
  pushTimer = setTimeout(() => {
    pushTimer = null;
    void runPush(state);
  }, pushDelayMs);
  statusStore.set('syncing');
}
```

The first three lines are the load-bearing part. While `isKnownOffline`
is true, `schedulePush` does _not_ schedule a new timer. It just sets the
status to "offline" and returns.

Walk through what would happen without the guard. User is on the playa,
typing edits. First edit fails to push → `enterOfflineMode`. Second edit
fires `schedulePush` → schedules a 2.5 s timer → fires → `runPush`
fails → `enterOfflineMode` again. Third edit, same thing. Every keystroke
queues a 2.5-second timer that will fire a failed network request. The
backoff schedule (which is what's _supposed_ to control retry pacing)
gets stomped on by the per-mutation timers. Battery dies in an hour.

With the guard, the only two legitimate retry triggers are:

1. The exponential backoff timer (`scheduleBackoffRetry`).
2. The `online` event (`onlineHandler` above).

The dirty bit is still set by every keystroke (`markDirty` runs before
the schedule check). Local persistence still happens (the auto-save
subscriber writes synchronously, unaffected by this code). The user
loses no data. They just don't burn battery retrying.

The "exit offline mode" path is symmetric — `runPush`'s successful branch
calls `exitOfflineMode` (`src/lib/sync-coordinator.ts:359-363`):

```ts
function exitOfflineMode(): void {
  isKnownOffline = false;
  retryAttempt = 0;
  cancelBackoff();
}
```

Once we're back online, `schedulePush` resumes scheduling normally on the
next mutation. The system has no permanent state — every push attempt
either lands us in "offline + backoff pending" or "online + idle."

> **General principle:** When you have a retry mechanism with its own
> pacing logic, prevent the _normal_ trigger from racing it. The normal
> trigger is for the happy path; the retry trigger is for the failed
> path. Mixing them is how you end up with retry storms.

## The Backoff Math, and Why It Doesn't Need Jitter

The backoff scheduler (`src/lib/sync-coordinator.ts:365-373`):

```ts
function scheduleBackoffRetry(): void {
  if (backoffTimer) return; // already pending
  const delay = Math.min(MAX_BACKOFF_MS, 1000 * 2 ** retryAttempt);
  retryAttempt += 1;
  backoffTimer = setTimeout(() => {
    backoffTimer = null;
    void runPush(get(appState));
  }, delay);
}
```

`MAX_BACKOFF_MS` is 60 seconds (`src/lib/sync-coordinator.ts:77`).
Attempt 0 → 1s, 1 → 2s, 2 → 4s, 3 → 8s, 4 → 16s, 5 → 32s, 6+ → 60s
forever. The `online` event resets `retryAttempt` to 0, so a connection
recovery starts the schedule over.

A few small decisions worth being explicit about.

**Why double instead of fibonacci or linear?** Exponential doubling is
the standard literature answer. It hits "back off enough to be polite"
within a small number of attempts (six attempts to reach the cap) while
still being quick to recover on transient blips (1 second on the first
retry). Fibonacci would be similar but with a slightly slower ramp;
linear (10s, 20s, 30s) takes longer to back off and stays artificially
short for too long.

**Why cap at 60 seconds?** Sole-device, one-user workload. The cap
controls "how long after a real connection recovery do we wait to
notice." 60 seconds is the worst case. The `online` event handles
the common case much faster (immediate cancel + retry). Capping higher
(5 minutes, say) buys nothing because there's no fleet of clients to
thunder-herd a server with.

**Why no jitter?** Jitter (a small randomization added to each delay) is
the right call when you have many clients backing off against a single
shared resource — you don't want a thundering herd where every client
retries at the same moment. We have one client. No herd. No jitter
required. If this app ever became a multi-tenant SaaS with many devices
on the same backend, jitter would be a one-line addition; we'd add it
then. For now it's noise.

**`if (backoffTimer) return;` is important.** Without that guard, you
could end up with multiple overlapping timers (because `enterOfflineMode`
gets called on every push failure, including failures from previously
scheduled retries). The guard says "if there's already a timer pending,
let it run; don't pile up more." `retryAttempt` only increments inside
the unguarded path, so the attempt counter accurately reflects the
number of _distinct_ attempt cycles, not the number of failures.

> **General principle:** Exponential backoff exists to be polite to the
> server and patient with the network. The cap exists to bound user-visible
> recovery latency. Jitter exists to break herds. Pick the features that
> match your workload; don't cargo-cult the whole RFC just because it
> exists.

## Idempotent Push Is What Lets the Rest Be Simple

Teaching doc 1.7 already covered this in depth, but it's worth restating
because PR 3's design only works if PR 2's `pushFullState` is idempotent.

The push (`src/lib/sync.ts:201-242`) does two things:

1. Upsert the `app_states` row by `user_id`. Same primary key = same row
   = last write wins.
2. Upsert the `events` rows by `id` with `ignoreDuplicates: true`. The
   client-generated `ev_<uuid>` from `lib/events.ts` is the PK, so
   re-inserting an event the server already has is a no-op (ON CONFLICT
   DO NOTHING).

Three properties fall out:

- **Re-pushing the same payload is safe.** The retry chain in PR 3
  (`scheduleBackoffRetry`) can fire `runPush` with the same `state.events`
  array over and over. Either the events are new (insert), or they
  already exist (no-op). The snapshot row is upserted to the same
  contents. The world doesn't drift.
- **The "offline queue" is the existing `state.events` array.** ADR-013's
  "Alternative 4" considered a separate LocalStorage push queue. It would
  be redundant: every event that ever existed locally is already in
  `state.events` (PR 1's design — see teaching doc 1.6), and the server
  dedupes by id. There's nothing to queue that isn't already queued.
- **The dirty bit suffices for "has anything unsynced happened?"** The
  push includes everything every time. We don't need to track "which
  events specifically are unsynced." A single bit + the existing events
  array is strictly simpler than a watermark / cursor approach.

If `pushFullState` were _not_ idempotent — if event IDs were
server-assigned, say — every one of these properties would break. Retries
would double-insert. The dirty bit would need to be a list of un-acked
event IDs. The push payload would need to be a delta. Idempotency at the
storage layer is what lets everything above it stay this small.

The one change to push in PR 3 is its return type. PR 2's signature was
`async function pushFullState(state: AppState): Promise<void>`. PR 3 made
it return the server's new `updated_at`:

```ts
export async function pushFullState(state: AppState): Promise<string> {
```

(`src/lib/sync.ts:201`)

That returned timestamp is what the coordinator persists as
`meta.lastServerUpdatedAt`. Without it, the next reconcile's
`remoteFresher` check would always be `false` (or always `true` — both
are wrong) because we'd have no idea what the server's "current" state
was. That single value, captured at the moment of successful push, is
how loopback prevention works (previous section) and how Burning Man
recovery works (the dirty-bit section). It's a tiny API change with
outsized leverage.

## What We Deliberately Did NOT Do

Each of these was considered. Listing them so future-me doesn't wonder
if they were missed.

- **CRDT-based merge.** The pedantic-correct answer. Rejected for this
  workload (one user, ~3 devices, ~10 events/day). Documented in
  ADR-013's "Alternative 2" for when the workload changes.
- **Local event reducer (Option B).** Lower-latency cross-device feel.
  Rejected for code-simplicity reasons. The apply boundary is isolated
  in `src/lib/realtime.ts` so a future swap is a one-module change.
- **Separate offline event queue.** ADR-013's "Alternative 4". Redundant
  with `state.events` + idempotent push. The dirty bit _is_ the queue.
- **Field-level merge in the conflict modal.** The current modal still
  offers `keep-local` / `keep-server` / `cancel` (PR 2). A "merge:
  combine boxes from both" option was considered and rejected because
  it makes the user think harder than necessary for the rare conflict
  case. If conflicts become common, revisit; for now, picking a side is
  the honest call.
- **Per-tab session tokens for loopback filtering.** A common pattern in
  multi-tab apps: tag each tab with a UUID, ignore broadcasts originating
  from your own tab. We don't need it — the peek-and-compare in
  reconcile is a more general solution that works across tabs _and_
  devices.
- **`beforeunload` flush on close.** Same conclusion as PR 2 (teaching
  doc 1.7) — `fetch` inside `beforeunload` is unreliable, `sendBeacon`
  doesn't fit our payload, partial reliability is worse than honest
  absence. The dirty bit + reconnect-and-push on next session is the
  proper fix and works correctly.
- **Throttling realtime callbacks.** A burst of remote events would each
  trigger a `reconcileSync`. We don't coalesce them — the realtime
  handler is "fire and forget." If chatter becomes an issue, a 200 ms
  debounce on the realtime handler would coalesce bursts; trivial
  addition.
- **Pretending Realtime is reliable.** It mostly is, but channels can
  drop, retries can fail, broadcast queues can lag. The Option A
  reconcile-on-broadcast is also our backstop: even if a broadcast is
  missed, the next auth event (token refresh on the hour, signing back
  in) re-reconciles and catches up. We don't need a "fall back to
  polling" loop because reconcile already runs on enough other triggers
  to keep us honest.

## The Test-Isolation Bug and `__resetForTests`

This deserves its own section because the bug was real, the fix is ugly
on purpose, and there's a generalizable lesson about Node's timer model.

### The bug

The test file `tests/unit/sync-coordinator.test.ts` calls
`vi.resetModules()` in `beforeEach`. The intent is sensible: each test
gets a fresh import of the coordinator with a fresh internal state. The
mocks for `pushFullState`, `pullFullState`, etc. are re-created.

The bug: the coordinator's `setTimeout` calls (the push debounce, the
backoff retry) are _not_ per-module. They live in Node's event loop
forever, indexed by their return value. `vi.resetModules()` blows away
the coordinator module reference, but the timers it scheduled are still
ticking. When they fire, they call into closures that captured the _old_
module's mocks. Except those mocks have been `mockClear`-ed and
`mockResolvedValue`-d by the new test, so the stale callback ends up
counting against the new test's call expectations.

In practice this manifested as flaky tests with "expected pushFullState
called 1 time, got 2 times" errors that disappeared if you ran the
specific test in isolation.

### The fix

A test-only export, `__resetForTests`
(`src/lib/sync-coordinator.ts:142-151`):

```ts
export function __resetForTests(): void {
  if (pushTimer) clearTimeout(pushTimer);
  pushTimer = null;
  if (backoffTimer) clearTimeout(backoffTimer);
  backoffTimer = null;
  if (typeof window !== 'undefined' && onlineHandler) {
    window.removeEventListener('online', onlineHandler);
    onlineHandler = null;
  }
}
```

And the corresponding `afterEach` hook in the test file
(`tests/unit/sync-coordinator.test.ts:102-108`):

```ts
afterEach(() => {
  coordinator?.__resetForTests?.();
});
```

The name is deliberately ugly. `__resetForTests` with a double underscore
is the universal "do not import this in production" signal — Python uses
the same convention, JavaScript convention is consistent. If you're ever
tempted to call this from production code, the name is screaming at you
to reconsider.

### The lesson

Three pieces worth carrying forward.

1. **`setTimeout` is not module-scoped.** `vi.resetModules()` resets
   _module exports_, not _the JavaScript runtime's timer queue_. If a
   module schedules timers, those timers outlive the module reference.
   The same applies to event listeners on global objects (`window`,
   `document`), pending Promises, and any reference captured by Node's
   event loop. Test isolation requires cleaning these up explicitly.
2. **Tests that fail flakily across files but pass in isolation are
   almost always a leak.** A leaked timer, a leaked listener, a leaked
   Promise. The fix is to identify the leak source and add explicit
   cleanup, not to add retries.
3. **Test-only exports should look like test-only exports.** I made the
   name ugly on purpose. A future contributor who sees `__resetForTests`
   in autocomplete will pause. A future contributor who sees a normal
   `reset()` export might think it's part of the public API and call it
   from a production code path.

This is also a small example of why the coordinator is at module scope
(not a class). A class instance would solve this problem implicitly —
each test gets a new instance, the old instance's timers and listeners
die when it's garbage-collected (provided they captured `this`). The
module-scope design pays in simplicity (no DI, no instance threading)
and pays a cost in test isolation. The `__resetForTests` export is the
explicit price. I think it's worth it for the simplicity of the rest of
the code; reasonable people could disagree.

> **General principle:** Module-scope mutable state buys simplicity at
> the cost of test-isolation work. If your tests start flaking across
> files, look for leaked timers, listeners, and promises _before_ you
> reach for retries. Make the cleanup explicit and name it loudly.
