# The localStorage E2E Testing Pattern: Constants in Browser Context

## What This Document Teaches

This is a focused deep-dive on ONE specific pattern from PR #55: how to use exported constants in Playwright's `addInitScript()` when setting up localStorage for E2E tests.

This pattern appears 16 times in our E2E test suite. It's subtle, non-obvious, and if you get it wrong, you'll waste hours debugging why your imports don't work in browser context.

## The Problem: Hardcoded Magic Strings

When we first wrote E2E tests, we hardcoded the localStorage key everywhere:

```typescript
// tests/e2e/home.spec.ts
test('displays favorite flavor', async ({ page, context }) => {
  await context.addInitScript(() => {
    const state = {
      /* ... */
    };
    localStorage.setItem('BROTEINBUDDY_APP_STATE', JSON.stringify(state));
    //                    ^^^^^^^^^^^^^^^^^^^^^^^^
    //                    Hardcoded magic string
  });
});

// tests/e2e/random-flow.spec.ts
test('selects random flavor', async ({ page, context }) => {
  await context.addInitScript(() => {
    const state = {
      /* ... */
    };
    localStorage.setItem('BROTEINBUDDY_APP_STATE', JSON.stringify(state));
    //                    ^^^^^^^^^^^^^^^^^^^^^^^^
    //                    Same hardcoded string
  });
});

// ... 14 more times across 4 test files
```

**16 instances of `'BROTEINBUDDY_APP_STATE'` hardcoded as string literals.**

This is fragile. If we ever change the storage key in production code, we have to update 16 places in tests. And if we miss one? Tests break in mysterious ways.

## The Naive Fix: Just Import the Constant

Our production code exports the constant:

```typescript
// src/lib/storage.ts
export const STORAGE_KEY = 'BROTEINBUDDY_APP_STATE';
```

So the obvious fix is to import it in tests:

```typescript
// tests/e2e/home.spec.ts
import { STORAGE_KEY } from '../../src/lib/storage';

test('displays favorite flavor', async ({ page, context }) => {
  await context.addInitScript(() => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(state));
    //                    ^^^^^^^^^^^
    //                    Use the imported constant
  });
});
```

This looks right. TypeScript compiles it. ESLint doesn't complain.

**But it doesn't work.**

When you run the test, you get:

```
ReferenceError: STORAGE_KEY is not defined
```

Wait, what? We imported it right there at the top!

## Understanding Browser Context

The issue is that `addInitScript()` runs in the **browser context**, not your Node.js test context.

Here's what happens:

1. Your test runs in Node.js (using Playwright)
2. Playwright launches a browser (Chromium, Firefox, WebKit)
3. The function you pass to `addInitScript()` gets **serialized** and sent to the browser
4. The browser executes the function in its own JavaScript context
5. The browser context has NO ACCESS to your Node.js imports

Think of it like this:

```typescript
// This runs in Node.js
import { STORAGE_KEY } from '../../src/lib/storage';

test('my test', async ({ page, context }) => {
  // This ALSO runs in Node.js
  await context.addInitScript(() => {
    // But THIS runs in the BROWSER
    // The browser doesn't have access to STORAGE_KEY
    localStorage.setItem(STORAGE_KEY, JSON.stringify(state)); // ERROR!
  });
});
```

The function gets serialized to something like:

```javascript
// In the browser:
(function () {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(state));
  // What is STORAGE_KEY? Not defined in this context!
})();
```

## The Correct Solution: Pass Constants as Arguments

The way to get values into browser context is to pass them as **arguments**:

```typescript
import { STORAGE_KEY } from '../../src/lib/storage';

test('displays favorite flavor', async ({ page, context }) => {
  await context.addInitScript((key) => {
    //                           ^^^^ Function parameter
    const state = {
      /* ... */
    };
    localStorage.setItem(key, JSON.stringify(state));
    //                   ^^^ Use the parameter
  }, STORAGE_KEY); // Pass the constant as an argument
  // ^^^^^^^^^^^
});
```

Now when Playwright serializes the function, it also serializes the arguments:

```javascript
// In the browser:
(function (key) {
  // key = 'BROTEINBUDDY_APP_STATE' (passed as argument)
  localStorage.setItem(key, JSON.stringify(state));
})('BROTEINBUDDY_APP_STATE'); // Argument is serialized too
```

**This works because the VALUE is passed, not the reference.**

## How This Works in Practice

Let's look at a real example from our E2E tests:

```typescript
// tests/e2e/home.spec.ts
import { test, expect } from '@playwright/test';
import { STORAGE_KEY } from '../../src/lib/storage';
//       ^^^^^^^^^^^
// Import the constant from production code

test('displays favorite flavor when configured', async ({ page, context }) => {
  // Set up localStorage BEFORE navigating to the page
  await context.addInitScript((key) => {
    //                           ^^^ Parameter receives the constant value
    const state = {
      version: 1,
      boxes: [],
      flavors: [{ id: 'choc_001', name: 'Chocolate', excludeFromRandom: false }],
      favoriteFlavorId: 'choc_001',
      settings: {},
    };
    localStorage.setItem(key, JSON.stringify(state));
    //                   ^^^ Use the parameter, not STORAGE_KEY directly
  }, STORAGE_KEY); // Pass the constant as an argument
  // ^^^^^^^^^^^

  // NOW navigate to the page
  await page.goto('/#/');

  // Favorite button should display the flavor name
  const favoriteButton = page.getByTestId('favorite-button');
  await expect(favoriteButton).toContainText('Chocolate');
});
```

**What happens step by step:**

1. Test imports `STORAGE_KEY` from production code
2. `addInitScript()` receives a function and `STORAGE_KEY` as an argument
3. Playwright serializes both to send to the browser
4. Browser executes: `(function(key) { ... })('BROTEINBUDDY_APP_STATE')`
5. The function receives `'BROTEINBUDDY_APP_STATE'` as the `key` parameter
6. localStorage gets set correctly
7. Page navigation happens AFTER localStorage is ready
8. App loads state from localStorage on mount
9. Test passes

This pattern appears **16 times** in our E2E test suite:

Every test that sets up localStorage state uses this pattern.

**Benefits:**

1. **Single source of truth**: Change `STORAGE_KEY` in one place, all tests update
2. **Type safety**: TypeScript ensures we pass a string
3. **No magic strings**: No hardcoded `'BROTEINBUDDY_APP_STATE'` literals
4. **Refactoring safety**: Renaming the constant automatically updates all usages
5. **Maintainability**: Future developers know where the key is defined

**Without this pattern, we'd have 16 places to update if we changed the storage key.**

## Common Mistakes

### Mistake 1: Trying to Use the Import Directly

```typescript
// WRONG: This won't work
import { STORAGE_KEY } from '../../src/lib/storage';

await context.addInitScript(() => {
  localStorage.setItem(STORAGE_KEY, data); // ReferenceError!
});
```

**Error:** `ReferenceError: STORAGE_KEY is not defined`

**Why:** Browser context doesn't have access to Node.js imports.

### Mistake 2: Hardcoding the Value

```typescript
// WRONG: This works but defeats the purpose
await context.addInitScript(() => {
  localStorage.setItem('BROTEINBUDDY_APP_STATE', data); // Magic string!
});
```

**Problem:** Now you have magic strings scattered across tests again.

### Mistake 3: Passing Multiple Arguments Without Destructuring

```typescript
// WRONG: Function only receives first argument as single value
await context.addInitScript(
  (key, value) => {
    localStorage.setItem(key, value);
  },
  STORAGE_KEY,
  jsonData
);

// addInitScript passes [STORAGE_KEY, jsonData] as ARRAY to first parameter
// so key = [STORAGE_KEY, jsonData], value = undefined
```

**Fix:** Pass an object and destructure, or pass a single argument and build data inside:

```typescript
// CORRECT: Pass object
await context.addInitScript(
  ({ key, data }) => {
    localStorage.setItem(key, data);
  },
  { key: STORAGE_KEY, data: jsonData }
);

// ALSO CORRECT: Build data inside (our approach)
await context.addInitScript((key) => {
  const state = {
    /* ... */
  }; // Built here
  localStorage.setItem(key, JSON.stringify(state));
}, STORAGE_KEY);
```

We use the second approach because test data is easier to read when it's built inline.

## Timing Considerations

An important detail: `addInitScript()` must be called BEFORE `page.goto()`.

### Wrong Order (Race Condition)

```typescript
// WRONG: localStorage set too late
test('my test', async ({ page, context }) => {
  await page.goto('/#/'); // Page loads HERE

  await context.addInitScript((key) => {
    // Too late!
    localStorage.setItem(key, data);
  }, STORAGE_KEY);

  // Test will fail because app already loaded without the data
});
```

The app mounts and tries to load state from localStorage, but it's empty because `addInitScript()` hasn't run yet.

### Correct Order

```typescript
// CORRECT: localStorage set before navigation
test('my test', async ({ page, context }) => {
  await context.addInitScript((key) => {
    // Set FIRST
    localStorage.setItem(key, data);
  }, STORAGE_KEY);

  await page.goto('/#/'); // Navigate AFTER

  // Test passes because state was ready before page loaded
});
```

This is why our tests that set localStorage have moved `addInitScript()` into individual test bodies instead of `beforeEach` hooks - we need precise control over timing.

## The Production Code Side

For completeness, here's what the production code looks like:

```typescript
// src/lib/storage.ts

/**
 * LocalStorage key for storing application state.
 * Namespaced to avoid conflicts with other applications.
 * Exported for use in E2E tests to ensure consistency.
 */
export const STORAGE_KEY = 'BROTEINBUDDY_APP_STATE';
//     ^^^^^^
// Exported so tests can import it

/**
 * Loads application state from localStorage.
 */
export function loadState(): AppState {
  try {
    const stored = localStorage.getItem(STORAGE_KEY);
    //                                   ^^^^^^^^^^^
    // Used internally in production code

    if (!stored) {
      return createDefaultAppState();
    }

    const parsed = JSON.parse(stored);

    if (!isAppState(parsed)) {
      console.warn('Invalid state in localStorage, using default');
      return createDefaultAppState();
    }

    return parsed;
  } catch (error) {
    console.warn('Failed to load state from localStorage:', error);
    return createDefaultAppState();
  }
}

/**
 * Saves application state to localStorage.
 */
export function saveState(state: AppState): void {
  try {
    if (!isAppState(state)) {
      throw new Error('Invalid AppState: failed type guard validation');
    }

    localStorage.setItem(STORAGE_KEY, JSON.stringify(state));
    //                   ^^^^^^^^^^^
    // Same constant used throughout
  } catch (error) {
    if (error instanceof DOMException && error.name === 'QuotaExceededError') {
      throw error; // Let UI handle quota errors
    }
    throw error;
  }
}
```

**Why export the constant?**

The JSDoc says it clearly:

> Exported for use in E2E tests to ensure consistency.

This is the entire reason. Production code doesn't need it exported - all storage operations are encapsulated in `loadState()` and `saveState()`. But tests need to set up localStorage directly (bypassing our abstractions) to test various scenarios.

## When to Use This Pattern

Use this pattern whenever you need to:

1. **Set up browser state before page load** (localStorage, sessionStorage, cookies)
2. **Mock browser APIs** (window.matchMedia, navigator.userAgent)
3. **Inject test fixtures** (override Date.now, Math.random for deterministic tests)

Examples:

```typescript
// localStorage
await context.addInitScript((key) => {
  localStorage.setItem(key, data);
}, STORAGE_KEY);

// sessionStorage
await context.addInitScript(
  ({ key, value }) => {
    sessionStorage.setItem(key, value);
  },
  { key: 'SESSION_KEY', value: 'test-session' }
);

// Mock window.matchMedia
await context.addInitScript((query) => {
  window.matchMedia = (q) => ({
    matches: q === query,
    media: q,
    // ... rest of MediaQueryList interface
  });
}, '(prefers-color-scheme: dark)');

// Override Date for deterministic tests
await context.addInitScript((timestamp) => {
  const OriginalDate = Date;
  Date.now = () => timestamp;
}, 1609459200000); // Jan 1, 2021
```

## Related Patterns

This pattern is part of a broader category: **passing data across execution contexts**.

Similar challenges appear in:

- **Web Workers**: `postMessage()` serializes data to send to worker
- **iframes**: `contentWindow.postMessage()` crosses frame boundaries
- **Service Workers**: Messages serialized between main thread and SW
- **React Server Components**: Data serialized from server to client

In all cases, you can't pass references - only serializable values.

**The Bottom Line:**

The localStorage constant pattern is a small detail, but it demonstrates a crucial principle: **execution contexts matter**. Code that runs in Node.js can't directly access browser context, and vice versa.

Understanding this principle will save you hours of debugging when writing E2E tests, working with Web Workers, or building any architecture that crosses execution boundaries.

**The pattern: Import constants in Node.js context, pass them as arguments to functions that run in browser context.**

Simple once you know it. Non-obvious until you do.
