# Phase 3.1: Component Integration and Cross-Route Navigation Patterns

## What We Built

Phase 3.1 completed the integration of BroteinBuddy's navigation flows by implementing two critical user journeys that were previously placeholders: **manual flavor selection** and **favorite flavor quick-pick**. Both features allow users to bypass the random selection algorithm and navigate directly to the confirmation screen with their chosen flavor.

On the surface, this seems straightforward - just add a modal with flavor buttons and wire up the favorite button, right? But here's the thing: we're building a **single-page application with client-side routing** where navigation between routes requires passing state. Unlike server-side frameworks where you can send data in POST requests or query parameters, SPAs need a strategy for sharing data between components that live on different routes.

This phase solved that challenge while also fixing critical infrastructure issues that were blocking parallel worktree development. The result is a complete, tested navigation system with three distinct paths to flavor selection: random, manual, and favorite quick-pick.

## Why This Approach

### The Problem We Solved

After Phase 2, we had a working home screen with four buttons, but two of them were placeholders:

1. **Random Pick** - Fully implemented, navigates to /random which performs selection
2. **Favorite Quick-Pick** - Button existed but just navigated to /random (no different than Random Pick)
3. **Manual Selection** - Button navigated to /inventory as a placeholder
4. **Inventory Management** - Fully implemented

The acceptance criteria for Phase 3.1 required:

- **Manual Selection**: Open a modal showing all flavors, allow user to pick one, navigate to confirmation with that flavor selected
- **Favorite Quick-Pick**: Skip the random selection algorithm entirely and navigate directly to confirmation with the user's pre-configured favorite flavor
- **Full E2E Testing**: Comprehensive tests covering all navigation flows, edge cases, and error states
- **Infrastructure Fixes**: Enable parallel worktree development by fixing the Vite configuration

The challenge? How do you pass the selected flavor from the Home screen (route `/#/`) to the Confirmation screen (route `/#/random/confirm`) when routing libraries like svelte-spa-router don't support navigation state out of the box?

### Options We Considered

#### Option 1: URL Query Parameters

**What it looks like:**

```typescript
// Home.svelte
push(`/random/confirm?flavorId=${flavor.id}`);

// RandomConfirm.svelte
const params = new URLSearchParams(window.location.hash.split('?')[1]);
const flavorId = params.get('flavorId');
```

**Pros:**

- Standard web pattern, visible in URL
- Shareable URLs with state baked in
- Browser refresh preserves state
- Works with browser back/forward

**Cons:**

- **Visible in URL** - User can see and modify the flavorId parameter
- **Hash routing complications** - With `/#/random/confirm?flavorId=choc_123`, parsing gets messy
- **No type safety** - Query params are always strings, need manual parsing
- **URL pollution** - Every navigation adds visible cruft to address bar

**Why we didn't choose it:**
For a utility PWA where URLs aren't shared externally, adding query parameters felt like overkill. Users don't need to bookmark "chocolate shake confirmation" pages. The visible state in the URL doesn't provide value and adds parsing complexity with hash-based routing.

#### Option 2: Svelte Store for Navigation State

**What it looks like:**

```typescript
// navigationStore.ts
export const selectedFlavor = writable<Flavor | null>(null);

// Home.svelte
selectedFlavor.set(flavor);
push('/random/confirm');

// RandomConfirm.svelte
$: currentFlavor = $selectedFlavor;
```

**Pros:**

- Type-safe
- Clean URLs
- Reactive updates if state changes mid-navigation
- Fits well with existing Svelte store pattern

**Cons:**

- **State persists too long** - What happens if user navigates away then returns? Stale flavor is still in store
- **No browser refresh survival** - Stores reset on refresh, lose navigation context
- **Manual cleanup required** - Need to clear store after confirmation or navigation away
- **Tab-level isolation** - Multiple tabs would share store state in some cases (not with per-instance stores, but still a footgun)

**Why we didn't choose it:**
The biggest issue is state lifecycle management. When should we clear the selected flavor? After confirmation? What if user hits back button? What if they navigate to inventory then return? The store persists longer than the navigation intent, creating potential for stale data bugs.

#### Option 3: sessionStorage with Navigation State Pattern ← **We chose this**

**What it looks like:**

```typescript
// Home.svelte - Set state before navigation
function handleFlavorSelect(flavor: Flavor) {
  sessionStorage.setItem('selectedFlavorId', flavor.id);
  push(ROUTES.RANDOM_CONFIRM);
}

// RandomConfirm.svelte - Retrieve and validate state
onMount(() => {
  const flavorId = sessionStorage.getItem('selectedFlavorId');
  sessionStorage.removeItem('selectedFlavorId'); // Clean up immediately

  if (!flavorId) {
    // Handle missing state - show error or redirect
    return;
  }

  const flavor = $appState.flavors.find((f) => f.id === flavorId);
  if (!flavor) {
    // Flavor was deleted since navigation started
    return;
  }

  // Proceed with confirmation flow
});
```

**Pros:**

- **Clean URLs** - No query parameters cluttering the address bar
- **Browser refresh survival** - sessionStorage persists across page reloads
- **Automatic cleanup** - Clears when tab closes (sessionStorage lifecycle)
- **Minimal data storage** - Only store IDs, retrieve full objects from appState store
- **Tab-isolated** - Each browser tab has separate sessionStorage
- **Type-safe after retrieval** - Validate against current app state

**Cons:**

- **Not standard routing pattern** - Some developers expect query params or router state
- **Manual cleanup required** - Must remember to remove item after reading
- **No reactivity** - If state changes between set/get, need manual checks
- **Edge case handling** - What if flavor was deleted between set/get?

**Why we chose it:**
sessionStorage strikes the perfect balance for a PWA. It provides:

1. **State that survives refresh** - User reloads the page mid-confirmation? State is still there
2. **Automatic session cleanup** - Close the tab, sessionStorage clears automatically (no stale data across sessions)
3. **Tab isolation** - Multiple tabs can navigate independently without state conflicts
4. **Clean URLs** - Navigation is invisible in the address bar
5. **Minimal storage** - We only store IDs (strings), not entire flavor objects

The key insight: **sessionStorage is perfect for "navigation intent" data** that should last longer than a component lifecycle but shorter than the app session. It's the Goldilocks solution - not too ephemeral (like router state we don't have), not too persistent (like localStorage), just right for cross-route data passing.

### Real-World Compromises

In a larger application with SvelteKit or Next.js, we'd use **server-side navigation state** or **built-in router state management**. For example, SvelteKit's load functions can pass data between routes server-side, and Next.js router.push() accepts a state object.

But here's the thing: we chose svelte-spa-router for its simplicity and tiny bundle size (6KB). It doesn't support navigation state because it's focused on doing one thing well: client-side route matching. Adding state management would bloat the library.

So we worked with the tools we have. sessionStorage is a web platform API - it's been around since IE8, works everywhere, and requires zero dependencies. Sometimes the "boring" solution is the right solution.

The compromise? **Manual state lifecycle management**. We have to remember to:

- Set the state before navigation
- Retrieve the state in the destination component
- Immediately clean up after reading
- Handle edge cases (missing state, deleted flavor, no boxes)

Is this more work than a framework's built-in state management? Yes. But it's also explicit, debuggable, and understandable. Six months from now, any developer can read `sessionStorage.setItem('selectedFlavorId', flavor.id)` and know exactly what's happening.

#### 2. Favorite Quick-Pick Button Enhancement

```svelte
<!-- Home.svelte -->

/**
 * Reactive: Get the user's favorite flavor (if configured)
 * Returns null if no favorite is set or flavor not found
 */
let favoriteFlavor = $derived(maybeGetFlavor($appState.favoriteFlavorId, $appState.flavors));

/**
 * Reactive: Determine the favorite button label
 * Shows flavor name if configured, "Set Favorite" otherwise
 */
let favoriteButtonLabel = $derived(
  favoriteFlavor ? `❤️ ${favoriteFlavor.name}` : '❤️ Set Favorite'
);

/**
 * Navigate to favorite flavor quick-pick
 * Navigates directly to confirmation with favorite flavor pre-selected
 *
 * Uses sessionStorage for cross-route state passing because:
 * - svelte-spa-router doesn't support navigation state in push()
 * - Preserves state across browser refresh (better UX)
 * - sessionStorage auto-clears when tab closes (no long-term storage)
 *
 * Pattern: Store minimal data (just ID) → navigate → destination retrieves and validates
 */
function handleFavoriteClick() {
  if (favoriteFlavor) {
    sessionStorage.setItem('selectedFlavorId', favoriteFlavor.id);
    push(ROUTES.RANDOM_CONFIRM);
  }
}

<Button
  variant="primary"
  size="lg"
  fullWidth={true}
  disabled={!favoriteFlavor}
  onclick={handleFavoriteClick}
  testId="favorite-button"
>
  {favoriteButtonLabel}
</Button>
```

**Why this implementation?**

- **Svelte 5 runes** - Uses `$derived` for reactive computed values (favoriteFlavor, favoriteButtonLabel)
- **Defensive programming** - `maybeGetFlavor()` utility handles null favoriteFlavorId gracefully
- **Disabled state** - Button visually disabled when no favorite configured (better UX than hiding it)
- **Dynamic label** - Shows actual flavor name when configured, "Set Favorite" prompt otherwise
- **Direct navigation** - Skips /random route entirely, goes straight to confirmation

The `maybeGetFlavor()` utility function is a reusable helper we created in Phase 2.3:

```typescript
// src/lib/utils/flavor.ts
export function maybeGetFlavor(flavorId: string | null, flavors: Flavor[]): Flavor | null {
  if (!flavorId) return null;
  return flavors.find((f) => f.id === flavorId) ?? null;
}
```

This pattern appears throughout the app - prefix utility functions with `maybe` when they can return null to make the null handling explicit.

#### 3. sessionStorage Navigation Pattern

```typescript
// Home.svelte - Sender
function handleFlavorSelect(flavor: Flavor) {
  sessionStorage.setItem('selectedFlavorId', flavor.id);
  showFlavorPicker = false;
  push(ROUTES.RANDOM_CONFIRM);
}

// RandomConfirm.svelte - Receiver
onMount(() => {
  const selectedFlavorId = sessionStorage.getItem('selectedFlavorId');

  // Clean up immediately after reading
  sessionStorage.removeItem('selectedFlavorId');

  // If no flavorId, check if we came from /random route
  if (!selectedFlavorId) {
    // Try loading from random selection...
    return;
  }

  // Validate flavor still exists
  const flavor = $appState.flavors.find((f) => f.id === selectedFlavorId);
  if (!flavor) {
    errorMessage = 'Selected flavor no longer exists';
    return;
  }

  // Proceed with confirmation flow
  selectedFlavor = flavor;
  selectedBox = selectPriorityBox($appState.boxes, flavor.id);
  // ...
});
```

**Critical details:**

1. **Store only IDs, not objects** - Keeps sessionStorage minimal and avoids serialization issues
2. **Immediate cleanup** - Remove item right after reading to prevent stale data
3. **Validation after retrieval** - Flavor might have been deleted between set/get
4. **Fallback handling** - If no sessionStorage data, fall back to other selection methods
5. **Error states** - Show user-friendly error if flavor missing or no boxes available

This pattern is **documented with comprehensive JSDoc comments** in the code explaining the rationale. Future developers can understand why we're using sessionStorage instead of query params or stores.

#### 4. Infrastructure Fix: Parallel Worktree Development

Phase 3.1 uncovered a critical bug: Vite's `loadEnv` function doesn't work with Playwright's webServer auto-start because loadEnv is only called during config parsing, but Playwright spawns the dev server in a child process where the config has already been evaluated.

**Problem:**

```typescript
// vite.config.ts - BROKEN
import { loadEnv } from 'vite';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');
  return {
    server: {
      port: parseInt(env.VITE_PORT || '5173'),
    },
  };
});
```

Playwright would timeout trying to start the dev server because the config function wasn't properly loading `.env.local`.

**Solution:**

```typescript
// vite.config.ts - FIXED
import dotenv from 'dotenv';

// Load .env.local if it exists (for worktree-specific port configuration)
dotenv.config({ path: '.env.local' });

export default defineConfig({
  plugins: [svelte()],
  server: {
    port: parseInt(process.env.VITE_PORT || '5173'),
  },
});
```

**Why dotenv package?**

- **Runs at import time** - dotenv.config() executes immediately when the module loads
- **Process environment** - Sets process.env variables before config object is created
- **Playwright compatible** - Works with webServer auto-start in playwright.config.ts
- **Standard pattern** - Many Node.js projects use dotenv for environment variables

This fix enables **parallel worktree development**: each worktree can have its own `.env.local` with `VITE_PORT=20297` (or any unique port), and both dev servers and E2E tests respect those ports.

## Design Trade-offs

### What We Optimized For

**1. User Experience Consistency**

All three selection paths (random, manual, favorite) converge on the **same confirmation screen**. This means:

- Users learn one confirmation flow, applies to all selection methods
- UI components are reused (confirmation screen doesn't care how flavor was selected)
- Testing is simplified (test confirmation once, works for all paths)

**2. State Durability**

sessionStorage survives page refreshes but not tab closes. This is perfect for:

- **Mid-navigation reloads** - User accidentally refreshes during selection? State persists
- **Session isolation** - Close tab, open new tab, clean slate (no stale "selected chocolate" from yesterday)
- **Browser back/forward** - State survives navigation history changes

**3. Code Maintainability**

The sessionStorage pattern is:

- **Explicit** - Every state transfer is visible in code: setItem → navigate → getItem → removeItem
- **Debuggable** - Open DevTools → Application → Session Storage, see exactly what's stored
- **Self-documenting** - JSDoc comments explain why we chose this approach

**4. Infrastructure Reliability**

The dotenv fix ensures:

- **Parallel development** - Multiple developers (or worktrees) can run dev servers simultaneously
- **E2E test stability** - Playwright can reliably start webServer on correct port
- **Zero configuration** - Just create `.env.local` with `VITE_PORT=12345`, everything works

### What We Sacrificed

**1. Routing Library Features**

By choosing svelte-spa-router (6KB, simple API), we gave up:

- Built-in navigation state (Next.js router.push(url, state))
- Layout nesting (SvelteKit +layout.svelte)
- Route guards (authentication checks)

**Trade-off:** For a client-side-only PWA, these features would add bundle weight and complexity we don't need. Our sessionStorage pattern is more explicit and easier to debug than router "magic".

**2. URL-Based State Sharing**

By avoiding query parameters, we gave up:

- Shareable URLs with pre-selected flavors
- Bookmarkable confirmation screens
- Back/forward URL history showing state

**Trade-off:** BroteinBuddy is a personal utility PWA, not a multi-user content platform. Users don't need to share "here's the chocolate confirmation URL" with anyone. Clean URLs matter more than shareable state.

**3. Reactive State Management**

By using sessionStorage instead of Svelte stores for navigation state, we gave up:

- Automatic reactivity if state changes mid-navigation
- Store devtools integration
- Type-safe store subscriptions

**Trade-off:** Navigation state is **transient by nature**. A store that lives longer than the navigation intent creates more bugs than it solves. sessionStorage's explicit lifecycle (set → navigate → get → remove) matches the mental model of "I'm passing data to the next screen".

**4. Framework Conventions**

By implementing a custom navigation state pattern, we gave up:

- Following standard routing patterns (query params, router state)
- Framework documentation examples we can copy-paste
- Community conventions other developers expect

**Trade-off:** The JSDoc comments explaining the pattern take 10 lines. The alternative (switching to a heavier routing library or SvelteKit) would add megabytes to the bundle and require restructuring the entire app. Documentation is cheaper than dependency weight.

## Key Lessons Learned

### 1. sessionStorage for Navigation State is Underrated

We almost went with query parameters because "that's what URLs are for", but sessionStorage turned out to be perfect for PWA navigation state:

- **Tab-isolated** - Multiple tabs don't interfere with each other
- **Session-scoped** - Closes with tab, doesn't clutter localStorage
- **Refresh-safe** - Survives page reloads during development
- **Debuggable** - Visible in DevTools → Application → Session Storage

**When to use sessionStorage:**

- Cross-route data passing in SPAs without router state support
- Temporary form data (survives refresh, clears on tab close)
- User's current navigation intent (selected item, filter state)

**When NOT to use sessionStorage:**

- Data that should persist across sessions → use localStorage
- Data shared between tabs → use localStorage + storage event listener
- Large data sets → use IndexedDB
- Sensitive data → minimize storage, clear aggressively

### 2. Infrastructure Issues Hide Until E2E Tests

The Vite `loadEnv` bug didn't show up until we ran Playwright tests with webServer auto-start. Running `npm run dev` manually worked fine because we were running from a shell where `.env.local` was already loaded.

**Takeaway:** E2E tests that auto-start the dev server catch configuration issues that manual testing misses.

### 3. Parallel Worktree Development Requires Port Isolation

Having `.env.local` files with unique `VITE_PORT` per worktree enables:

- Multiple dev servers running simultaneously
- E2E tests in one worktree not conflicting with dev server in another
- CI/CD environments with dynamic port assignment

**Pattern for parallel development:**

```bash
# wt/main/.env.local
VITE_PORT=5173

# wt/phase-3.1-component-integration/.env.local
VITE_PORT=20297

# wt/feature-something-else/.env.local
VITE_PORT=20298
```

Each worktree is isolated and doesn't conflict.

### 4. Document Non-Standard Patterns Aggressively

The sessionStorage navigation pattern isn't a standard routing convention. Most developers expect:

- Query parameters for state in URLs
- Router state objects (Next.js, SvelteKit)
- Stores for cross-component state

**We chose sessionStorage for good reasons**, but those reasons won't be obvious to someone reading the code in six months. That's why we added comprehensive JSDoc comments explaining:

- Why sessionStorage instead of query params
- Why sessionStorage instead of stores
- What the lifecycle is (set → navigate → get → remove)
- What edge cases we handle (deleted flavor, browser refresh)

**Principle:** The more your code deviates from conventions, the more documentation it needs.

### 5. Test Edge Cases Explicitly

The favorite quick-pick tests include scenarios that might seem "obvious":

- Favorite flavor that no longer exists
- Favorite flavor with no boxes
- Disabled button when no favorite configured

These aren't edge cases that "probably won't happen" - they're **realistic user scenarios**:

- User sets favorite to Chocolate, then deletes all Chocolate boxes (out of stock)
- User sets favorite, then deletes the Chocolate flavor entirely (decided they hate it)
- New user opens app for first time (no favorite configured yet)

**Principle:** If users can reach a state through normal app usage, test that state explicitly.

## Going Deeper

### Related Concepts

**sessionStorage vs localStorage:**

- Both are key-value stores with string values only
- sessionStorage: scoped to browser tab, clears when tab closes
- localStorage: scoped to origin, persists across sessions
- Both: 5-10MB limit per origin, synchronous API

**Hash routing vs History API:**

- Hash routing: URLs like `/#/inventory`, no server configuration needed
- History API: URLs like `/inventory`, requires server fallback configuration
- Hash routing: fragments (#) not sent to server, not crawled by search engines
- History API: cleaner URLs, better SEO, needs server rewrites

**Client-side state management patterns:**

- Component props: pass data down component tree
- Stores (Svelte stores, Redux): reactive global state
- Context API: pass data without prop drilling
- URL state: query params, route params
- Web Storage: localStorage, sessionStorage, IndexedDB
- Server state: fetch on route load, pass to component

**Navigation state in different frameworks:**

- Next.js: router.push(url, as, { state })
- SvelteKit: $page.state, set by navigation
- React Router: useLocation().state
- Vue Router: router.push({ state: {} })

### Patterns Worth Remembering

**1. Navigation State Pattern (sessionStorage)**

```typescript
// Sender (before navigation)
function navigateWithState(routePath: string, stateKey: string, stateValue: string) {
  sessionStorage.setItem(stateKey, stateValue);
  push(routePath);
}

// Receiver (after navigation)
function retrieveNavigationState(stateKey: string): string | null {
  const value = sessionStorage.getItem(stateKey);
  sessionStorage.removeItem(stateKey); // Clean up immediately
  return value;
}
```

**When to use:** SPAs without built-in router state management, need state that survives refresh but clears with tab.

**2. Maybe Functions for Null-Safe Lookups**

```typescript
function maybeGetFlavor(flavorId: string | null, flavors: Flavor[]): Flavor | null {
  if (!flavorId) return null;
  return flavors.find((f) => f.id === flavorId) ?? null;
}
```

**When to use:** Functions that perform lookups which might not find a result. Prefix with `maybe` to signal nullable return.

**3. Derived Reactive State (Svelte 5 Runes)**

```typescript
let favoriteFlavor = $derived(maybeGetFlavor($appState.favoriteFlavorId, $appState.flavors));

let favoriteButtonLabel = $derived(
  favoriteFlavor ? `❤️ ${favoriteFlavor.name}` : '❤️ Set Favorite'
);
```

**When to use:** Computed values that depend on reactive state. `$derived` automatically re-runs when dependencies change (Svelte 5+).

**4. Modal with Empty State Handling**

```svelte
<Modal open={showModal} title="Choose Item" onclose={() => (showModal = false)}>
  {#if items.length === 0}
    <div class="empty-state">
      <p>No items available. Add items first.</p>
    </div>
  {:else}
    <div class="item-list">
      {#each items as item}
        <button onclick={() => selectItem(item)}>{item.name}</button>
      {/each}
    </div>
  {/if}
</Modal>
```

**When to use:** Modals that display dynamic content which might be empty. Always handle the empty state explicitly.
