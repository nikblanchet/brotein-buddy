## Introduction

Drag-and-drop interfaces feel magical when done right - you grab something, move it, and the UI responds naturally. But behind that simple interaction lies surprising complexity: state synchronization, validation, accessibility, mobile support, and careful UX design.

Task 2.7 implements a visual drag-and-drop interface for rearranging boxes in inventory stacks. Users can reorganize their inventory by dragging boxes between and within stacks, with real-time validation preventing invalid configurations.

### What Makes This Feature Special

1. **Real-time validation** - Invalid positions show immediate visual feedback (red borders)
2. **Preview-then-commit workflow** - Changes are local until confirmed
3. **Atomic batch updates** - All changes saved in one transaction
4. **Touch-friendly** - Works on mobile devices with drag gestures
5. **Integration with existing validation** - Reuses location validation from Task 2.6

By the end of this document, you'll understand:

## Why Drag-and-Drop is Deceptively Complex

Drag-and-drop seems simple: "just let users drag things around." But there are many hidden complexities:

### 1. Mouse vs Touch Events

**Mouse events:**

- `mousedown` → `mousemove` → `mouseup`
- Single pointer, straightforward

**Touch events:**

- `touchstart` → `touchmove` → `touchend`
- Multiple fingers (multi-touch)
- Different coordinate systems
- Conflicts with scroll gestures

You need to handle BOTH or use a library that abstracts this.

### 2. Visual Feedback During Drag

When dragging, users need to see:

- The item being dragged (drag preview)
- Where it will land (drop zone indicator)
- Invalid drop zones (visual rejection)
- Scroll indicators (if dragging near edges)

Without feedback, drag-and-drop feels broken.

### 3. State Synchronization

During a drag operation, you're managing multiple state layers:

- **Original state** (before drag started)
- **Preview state** (where item appears during drag)
- **Committed state** (after drop completes)

If these get out of sync, the UI feels janky and unpredictable.

### 4. Validation Constraints

Not all positions are valid. You need to:

- Check constraints in real-time (during drag)
- Prevent invalid drops (or show errors)
- Handle edge cases (empty containers, boundaries)

For BroteinBuddy, we enforce "no floating boxes" - every box must rest on ground or another box.

### 5. Accessibility

Drag-and-drop is inherently visual. For keyboard/screen reader users, you need:

- Alternative keyboard controls
- Focus management
- ARIA labels and live regions
- Clear instructions

This is often overlooked but critical for inclusive design.

### 6. Performance

Dragging fires MANY events per second. If your drag handler is slow, the UI stutters. You need:

- Efficient state updates
- Throttled/debounced handlers
- Optimized rendering

### The Reality

Implementing all this from scratch is weeks of work. That's why we use a library.

## Library Selection: Why svelte-dnd-action

For Task 2.7, we chose **svelte-dnd-action** (v0.9.28). Let's look at why.

### Options Considered

#### Option 1: Build It Ourselves (REJECTED)

```typescript
// Custom drag-and-drop from scratch
function handleMouseDown(event, box) {
  draggedBox = box;
  startX = event.clientX;
  startY = event.clientY;
  // ... 200 more lines of mouse/touch handling
}
```

**Pros:**

- Full control over behavior
- No dependencies

**Cons:**

- Weeks of work to handle all edge cases
- Mouse + touch + keyboard = 3x complexity
- Hard to get accessibility right
- High bug risk

**Verdict:** Not worth it for a feature that's not our core differentiator.

#### Option 2: Use HTML5 Drag and Drop API (REJECTED)

The native browser API exists but has serious issues:

```html
<div draggable="true" ondragstart="{handleDragStart}">Drag me</div>
```

**Pros:**

- Native browser support
- No library needed

**Cons:**

- Terrible mobile support (basically doesn't work)
- Inconsistent cross-browser behavior
- Clunky API design
- Limited customization

**Verdict:** Not mobile-friendly, which is critical for BroteinBuddy.

#### Option 3: Use svelte-dnd-action (CHOSEN)

A Svelte-specific library designed for drag-and-drop:

```svelte
<div
  use:dndzone={{ items, flipDurationMs: 200 }}
  onconsider={handleConsider}
  onfinalize={handleFinalize}
>
  {#each items as item (item.id)}
    <div>Drag me</div>
  {/each}
</div>
```

**Pros:**

- Built specifically for Svelte (uses actions)
- Handles mouse, touch, AND keyboard
- Good mobile support
- Smooth animations
- Active maintenance
- Relatively small (no huge dependency tree)

**Cons:**

- Another dependency to manage
- Limited to list/container sorting (not free-form dragging)
- Learning curve for API

**Why we chose this:**

- Saves weeks of implementation time
- Mobile support is essential for BroteinBuddy
- Our use case (sorting within containers) matches perfectly
- Active development and good documentation
- Svelte integration is clean and idiomatic

### What svelte-dnd-action Provides

1. **Two event handlers:**
   - `consider` - Fires during drag (preview state)
   - `finalize` - Fires when drop completes (commit state)

2. **Automatic animations:**
   - Smooth transitions when items reorder
   - Flip animations (First, Last, Invert, Play)

3. **Accessibility:**
   - Keyboard controls (arrow keys to reorder)
   - Screen reader announcements

4. **Mobile support:**
   - Touch event handling
   - Drag preview on mobile
   - Scroll detection

5. **Flexible configuration:**
   - Custom animations
   - Drop target styling
   - Item transformations

This is exactly what we need without the complexity of building it ourselves.

## State Management: Preview vs Committed State

One of the trickiest aspects of drag-and-drop is managing state during the drag operation. Let's break down our approach.

### The Three States

#### 1. Original State (Snapshot)

When entering the rearrange screen, we snapshot the current boxes:

```typescript
const originalBoxes = [...$appState.boxes];
```

This is immutable - never changes while on the rearrange screen. Used for:

- Cancel functionality (revert to this)
- Determining which boxes changed (for batch update)

#### 2. Local Working State (Preview)

A mutable copy that updates during drag operations:

```typescript
let localBoxes = $state<Box[]>($appState.boxes.map((b) => ({ ...b, location: { ...b.location } })));
```

**Key points:**

- Deep copy (not just spreading arrays)
- Reactive (`$state`) for UI updates
- Modified by drag handlers in real-time
- Never touches global `$appState`

#### 3. Global Committed State (Final)

Only updated when user confirms:

```typescript
function handleConfirm() {
  // Validate everything
  const finalValidation = validateRearrangementState(localBoxes);
  if (!finalValidation.isValid) return;

  // Batch update only changed boxes
  for (const box of localBoxes) {
    const original = originalBoxes.find((b) => b.id === box.id);
    if (/* locations differ */) {
      updateBoxLocation(box.id, box.location);
    }
  }
}
```

### Why This Three-State Approach?

**Alternative: Update global state during drag**

```typescript
// BAD: Update global state in real-time
function handleDndConsider(event) {
  const { items } = event.detail;
  items.forEach((item) => {
    updateBoxLocation(item.id, item.location); // Saves to localStorage!
  });
}
```

**Problems:**

- Every drag movement writes to localStorage
- Performance nightmare (100+ writes during one drag)
- No way to cancel - changes already saved
- Validation happens after save (too late)

**Our approach with local state:**

```typescript
// GOOD: Update local working copy
function handleDndConsider(event) {
  const { items } = event.detail;
  updateStackBoxes(stackNumber, items);
  // Only touches localBoxes, not global state
}
```

**Benefits:**

- Fast (no localStorage writes during drag)
- Cancelable (just discard localBoxes)
- Validate before commit (prevent invalid saves)
- Atomic update (all changes at once)

### Visual Diagram

```
User enters screen:
  originalBoxes = snapshot($appState.boxes)  [immutable]
  localBoxes = deep copy($appState.boxes)    [mutable]

User drags box:
  → handleDndConsider() fires
  → localBoxes updated (heights recalculated)
  → UI re-renders (reactive)
  → $appState unchanged

User drops box:
  → handleDndFinalize() fires
  → localBoxes updated
  → validateAllBoxes() runs
  → validationErrors updated
  → UI shows red borders if invalid
  → $appState still unchanged

User clicks Confirm:
  → Final validation
  → Compare localBoxes to originalBoxes
  → Batch update only changed boxes
  → $appState.boxes updated
  → localStorage updated (once)
  → Navigate back to inventory

User clicks Cancel:
  → Discard localBoxes
  → Navigate back to inventory
  → $appState unchanged
```

This pattern gives us the best of both worlds: fast UI updates with safe, validated commits.

## Real-Time Validation with Visual Feedback

Drag-and-drop without validation is chaos. Users can create impossible configurations. We need real-time feedback to guide users toward valid states.

### Our Validation Requirements

From the BroteinBuddy data model:

1. **No stack gaps** - Can't have stack 3 without stacks 1 and 2
2. **No height gaps** - Can't have height 3 without heights 1 and 2
3. **No duplicates** - One box per location
4. **No floating boxes** - Every box rests on ground or another box

These rules were implemented in Task 2.6 (`location-validation.ts`). We reuse that logic here.

### Real-Time Validation Flow

#### Step 1: Validate After Every Drop

```typescript
function handleDndFinalize(event, stackNumber) {
  const { items } = event.detail;
  updateStackBoxes(stackNumber, items); // Update local state
  validateAllBoxes(); // Immediate validation
}
```

#### Step 2: Check All Boxes

```typescript
function validateAllBoxes() {
  validationErrors.clear();
  globalErrors = [];

  for (const box of localBoxes) {
    const validation = validateLocationNoGaps(
      box.location.stack,
      box.location.height,
      localBoxes,
      box.id
    );

    if (!validation.isValid && validation.error) {
      validationErrors.set(box.id, validation.error);
    }
  }

  // Trigger reactivity
  validationErrors = new Map(validationErrors);
}
```

**Why check every box?**
Moving one box can invalidate others. Example:

```
Initial state:
  Stack 1: box-1 (height 1), box-2 (height 2)
  Stack 2: box-3 (height 1)

Drag box-1 from Stack 1 to Stack 2:
  Stack 1: box-2 (height 2)  ← NOW INVALID! (height 2 without height 1)
  Stack 2: box-3 (height 1), box-1 (height 2)
```

Both stacks need revalidation.

#### Step 3: Visual Feedback

```svelte
<div
  class="box-visual"
  class:box-invalid={validationErrors.has(box.id)}
  style="background-color: {getFlavorColor(box.flavorId)};"
>
  <div class="box-flavor">{flavor?.name}</div>
  <div class="box-quantity">{box.quantity} bottles</div>

  {#if validationErrors.has(box.id)}
    <div class="box-error" title={validationErrors.get(box.id)}>
      {validationErrors.get(box.id)}
    </div>
  {/if}
</div>
```

```css
.box-visual.box-invalid {
  border: 2px solid var(--color-error, #c00);
  box-shadow: 0 0 0 3px rgba(200, 0, 0, 0.1);
}
```

**Visual cues:**

- Red border around invalid box
- Red shadow (subtle glow)
- Error message below box
- Confirm button disabled

#### Step 4: Disable Confirm Until Valid

```typescript
let isConfirmDisabled = $derived(validationErrors.size > 0 || globalErrors.length > 0);
```

```svelte
<Button variant="primary" disabled={isConfirmDisabled} onclick={handleConfirm}>
  Confirm Changes
</Button>
```

Users can't save invalid states - the UI enforces correctness.

### Why Real-Time Validation Matters

**Without real-time validation:**

1. User drags boxes around
2. Clicks "Confirm"
3. Error message: "Invalid configuration"
4. User frustrated: "What's invalid? Where?"
5. Trial and error to find the problem

**With real-time validation:**

1. User drags box to invalid position
2. Box immediately shows red border + error message
3. User sees the problem and fixes it
4. Confirm button enables when everything is valid
5. Smooth, frustration-free experience

Validation shouldn't be a gatekeeper at the end - it should be a guide throughout.

### Key Implementation Details

#### 1. Grouping Boxes by Stack

```typescript
let boxesByStack = $derived(
  groupBoxesByStack(
    localBoxes.map((box) => {
      const flavor = $appState.flavors.find((f) => f.id === box.flavorId);
      return { box, flavor: flavor || null };
    })

```

**Why `$derived`?**

- Reactive: re-computes when `localBoxes` changes
- Efficient: only runs when dependencies change
- Clean: no manual subscription management

**What does `groupBoxesByStack` return?**

```typescript
Map<number, Array<{ box: Box, flavor: Flavor | null }>>

// Example:
Map {
  1 => [{ box: box1, flavor: chocolate }, { box: box2, flavor: vanilla }],
  2 => [{ box: box3, flavor: strawberry }]
}
```

Used for rendering stacks in the template.

#### 2. Drag-and-Drop Integration

```svelte
<div
  class="stack-boxes"
  use:dndzone={{
    items: boxes.map((b) => b.box),
    flipDurationMs: 200,
    dropTargetStyle: {},
  }}
  onconsider={(e) => handleDndConsider(e, Number(stackNum))}
  onfinalize={(e) => handleDndFinalize(e, Number(stackNum))}
>
  {#each boxes as { box, flavor } (box.id)}
    <div class="box-visual">...</div>
  {/each}
</div>
```

**The `use:dndzone` directive:**

- Svelte action that adds drag-and-drop behavior
- `items`: Array of items to make draggable
- `flipDurationMs`: Animation duration for reordering
- `dropTargetStyle`: Custom CSS for drop zones (we use empty object for default)

**Event handlers:**

- `onconsider`: Fires during drag (before drop)
- `onfinalize`: Fires when drop completes

**Why pass `stackNum` to handlers?**
Each stack is a separate drag zone. When a box is dropped, we need to know which stack it landed in to update heights correctly.

#### 3. Updating Stack Positions

```typescript
function updateStackBoxes(stackNumber: number, newBoxes: Box[]) {
  // Update heights for boxes in this stack
  const updatedBoxesInStack = newBoxes.map((box, index) => ({
    ...box,
    location: { stack: stackNumber, height: index + 1 },
  }));

  // Merge with boxes from other stacks
  const boxesInOtherStacks = localBoxes.filter((box) => box.location.stack !== stackNumber);

  localBoxes = [...boxesInOtherStacks, ...updatedBoxesInStack];
}
```

**Why recalculate heights?**

After reordering boxes in a stack, their heights must be sequential starting from 1:

```
Before drag:
  Stack 1: box-1 (height 1), box-2 (height 2), box-3 (height 3)

User drags box-3 to top position:
  items = [box-3, box-1, box-2]

After updateStackBoxes:
  Stack 1: box-3 (height 1), box-1 (height 2), box-2 (height 3)
```

Heights are assigned by array index, ensuring no gaps.

**Why filter and merge?**

We're only updating one stack. Other stacks remain unchanged:

```typescript
// Keep boxes from other stacks untouched
const boxesInOtherStacks = localBoxes.filter((box) => box.location.stack !== stackNumber);

// Merge: other stacks + updated stack
localBoxes = [...boxesInOtherStacks, ...updatedBoxesInStack];
```

This is immutable update pattern - we create a new array rather than mutating.

#### 4. Batch Confirm Logic

```typescript
function handleConfirm() {
  // Final validation
  const finalValidation = validateRearrangementState(localBoxes);
  if (!finalValidation.isValid) {
    globalErrors = finalValidation.errors;
    return;
  }

  // Batch update only changed boxes
  for (const box of localBoxes) {
    const original = originalBoxes.find((b) => b.id === box.id);
    if (
      original &&
      (original.location.stack !== box.location.stack ||
        original.location.height !== box.location.height)
    ) {
      updateBoxLocation(box.id, box.location);
    }
  }

  push(ROUTES.INVENTORY);
}
```

**Why final validation?**

Even though we validate after every drop, paranoia is good. Final validation ensures:

- No race conditions
- No missed edge cases
- Explicit safety check before commit

**Why only update changed boxes?**

```typescript
if (
  original.location.stack !== box.location.stack ||
  original.location.height !== box.location.height
) {
  updateBoxLocation(box.id, box.location);
}
```

If a box wasn't moved, don't call `updateBoxLocation`. Benefits:

- Fewer state mutations
- Faster (no unnecessary work)
- Cleaner audit trail (only real changes)

**Why loop instead of one call?**

```typescript
// We do this:
for (const box of localBoxes) {
  updateBoxLocation(box.id, box.location);
}

// Why not this?
updateAllBoxLocations(localBoxes); // Doesn't exist
```

Our state management API (`stores.ts`) is designed around single-box updates. We could add a batch API, but:

- More complexity in stores.ts
- Only used here (premature optimization)
- Current approach works fine

If we needed batch updates elsewhere, we'd refactor. For now, YAGNI (You Aren't Gonna Need It).

## Testing Drag-and-Drop Interactions

Testing drag-and-drop is notoriously hard. You can't just call a function - you need to simulate mouse/touch events, timing, and state changes.

### Our Testing Strategy

We use a two-layer approach:

1. **Unit tests** for business logic (28 tests, 100% coverage)
2. **E2E tests** for drag interactions (8 tests)

### Unit Tests: Pure Logic

File: `tests/unit/rearrange-utils.test.ts` (320 lines)

Test the utility functions without any UI:

```typescript
describe('simulateMove', () => {
  it('should update box location without mutating original', () => {
    const boxes = [createBox('box-1', 'chocolate', 1, 1), createBox('box-2', 'vanilla', 1, 2)];

    const updated = simulateMove(boxes, 'box-1', { stack: 2, height: 1 });

    // Original unchanged
    expect(boxes[0].location).toEqual({ stack: 1, height: 1 });

    // Updated array has new location
    expect(updated[0].location).toEqual({ stack: 2, height: 1 });
  });
});
```

**What we test:**

- `simulateMove`: Immutability, deep copying, edge cases
- `reorderBoxesAfterMove`: Height recalculation, cascading updates
- `getAffectedBoxes`: Dependency tracking
- `validateRearrangementState`: Gap detection, error messages

**Why unit test utilities?**

- Fast (milliseconds)
- Deterministic (no flakiness)
- Easy to debug (simple inputs/outputs)
- Good coverage (test all edge cases)

**What we DON'T unit test:**

- Drag gestures (requires browser)
- Visual rendering (E2E better suited)
- User interactions (E2E better suited)

### E2E Tests: Full User Flow

File: `tests/e2e/rearrange.spec.ts` (131 lines)

Test the complete drag-and-drop experience:

```typescript
test('should navigate to rearrange screen from inventory', async ({ page }) => {
  await page.click('text=Manage Inventory');

test('should display all stacks and boxes', async ({ page }) => {
  await page.goto('/#/inventory/rearrange');

  await expect(page.locator('text=Stack 1')).toBeVisible();
  await expect(page.locator('text=Stack 2')).toBeVisible();
  await expect(page.locator('text=Chocolate')).toBeVisible();
});
```

**What we test:**

- Navigation flow (inventory → rearrange → confirm/cancel)
- Visual rendering (stacks, boxes, buttons)
- Confirm/cancel functionality
- State persistence after confirm
- Error handling (validation failures)

**Why NOT test actual drag gestures in E2E?**

Playwright CAN simulate drag-and-drop:

```typescript
// Possible but fragile
await page.dragAndDrop('[data-box-id="box-1"]', '[data-stack="2"]');
```

But it's:

- Flaky (timing issues, coordinates)
- Library-dependent (svelte-dnd-action internals)
- Slow (full browser automation)
- Brittle (breaks with UI changes)

**Our approach:**

- Unit test the logic (utilities)
- E2E test the outcomes (confirm/cancel work)
- Trust the library (svelte-dnd-action) for drag mechanics

This is pragmatic testing - focus on what matters for correctness, not 100% simulation.

## Mobile and Touch Considerations

BroteinBuddy is a Progressive Web App designed for mobile use. Drag-and-drop on mobile has unique challenges.

### Touch vs Mouse Differences

| Aspect      | Mouse                               | Touch                                 |
| ----------- | ----------------------------------- | ------------------------------------- |
| Events      | `mousedown`, `mousemove`, `mouseup` | `touchstart`, `touchmove`, `touchend` |
| Precision   | High (pixel-perfect cursor)         | Low (finger size ~40-48px)            |
| Feedback    | Hover states, cursor changes        | No hover, press-and-hold              |
| Conflicts   | None                                | Scroll, zoom, swipe gestures          |
| Multi-input | One pointer                         | Multiple fingers                      |

### How svelte-dnd-action Helps

The library handles touch events automatically:

```typescript
// We write this once:
use:dndzone={{ items, flipDurationMs: 200 }}

// Library handles:
// - Mouse events (desktop)
// - Touch events (mobile)
// - Keyboard events (accessibility)
// - Pointer events (modern browsers)
```

No special mobile code needed!

### Our Mobile UX Decisions

#### 1. Touch-Friendly Target Sizes

```css
.box-visual {
  padding: var(--space-3); /* 16px minimum */
  min-height: 48px; /* WCAG touch target minimum */
  cursor: grab;
}
```

Boxes are large enough to tap/drag comfortably.

#### 2. Responsive Grid Layout

```css
.stacks-container {
  grid-template-columns: repeat(auto-fit, minmax(180px, 1fr));
}

@media (max-width: 768px) {
  .stacks-container {
    grid-template-columns: repeat(auto-fit, minmax(140px, 1fr));
  }
}
```

Stacks shrink on small screens to fit more columns.

#### 3. Full-Width Buttons on Mobile

```css
@media (max-width: 768px) {
  .actions {
    flex-direction: column-reverse;
  }

  .actions :global(button) {
    width: 100%;
  }
}
```

Cancel and Confirm buttons stack vertically on mobile, easier to tap.

#### 4. Visual Feedback During Drag

```css
.box-visual:active {
  cursor: grabbing;
}
```

On mobile, pressing a box shows `:active` state (cursor change won't work, but other styles can).

### Testing on Mobile

E2E tests run on desktop browsers, but we manually test on:

- iPhone Safari (iOS PWA is primary target)
- Chrome on Android
- iPad (larger touch target)

Playwright can emulate mobile devices:

```typescript
test.use({ viewport: { width: 375, height: 667 } }); // iPhone SE
```

But real device testing is essential for touch interactions.

## Design Trade-offs

Every design decision involves trade-offs. Here's what we optimized for and what we sacrificed.

### What We Optimized For

#### 1. Simplicity Over Flexibility

**Decision:** Only allow dragging within and between stacks. Can't freely place boxes anywhere.

**Alternative:** Free-form drag-and-drop (place boxes at arbitrary coordinates).

**Why we chose simplicity:**

- Stack-based model matches our data structure (stack, height)
- Validation is simpler (check stack/height constraints)
- Library (svelte-dnd-action) is designed for list sorting
- Users don't need free-form placement

**Trade-off:** Less flexibility, but much clearer UX.

#### 2. Preview-Then-Commit Over Auto-Save

**Decision:** Changes are local until user clicks "Confirm".

**Alternative:** Auto-save every change to global state.

**Why we chose preview-then-commit:**

- Users can experiment without commitment
- Easy to cancel and start over
- Atomic batch updates (all or nothing)
- Validation before save (prevent invalid states)

**Trade-off:** Extra "Confirm" step, but safer UX.

#### 3. Real-Time Validation Over Validation-On-Submit

**Decision:** Validate after every drop, show errors immediately.

**Alternative:** Only validate when user clicks "Confirm".

**Why we chose real-time:**

- Users see problems immediately
- Guides toward valid states
- Prevents frustrating late errors

**Trade-off:** More validation work (runs frequently), but better UX.

#### 4. Library Over Custom Implementation

**Decision:** Use svelte-dnd-action library.

**Alternative:** Build drag-and-drop from scratch.

**Why we chose library:**

- Saves weeks of development time
- Handles edge cases we'd miss
- Mobile/touch support out of the box
- Accessibility built-in

**Trade-off:** Dependency to manage, but huge time savings.

### What We Sacrificed

#### 1. Drag Between Empty Spaces

**Can't do:** Drag a box to create a new stack in an empty column.

**Why not:** Library works with existing containers (stacks). Creating new stacks mid-drag would require custom logic.

**Workaround:** Users can manually edit box location (via Individual Box Edit screen) to create new stacks.

#### 2. Undo/Redo

**Can't do:** Press "Undo" to step back through drag operations.

**Why not:** Adds significant complexity. Would need:

- History stack (all intermediate states)
- Undo/redo buttons
- Keyboard shortcuts (Cmd+Z)
- State synchronization

**Workaround:** "Cancel" button discards all changes (revert to original).

#### 3. Drag Across Multiple Stacks at Once

**Can't do:** Drag multiple boxes simultaneously.

**Why not:** Library supports single-item drag. Multi-select would require:

- Selection UI (checkboxes?)
- Drag preview showing multiple items
- Validation for group moves

**Workaround:** Drag boxes one at a time.

#### 4. Animated Transitions for Invalid Drops

**Can't do:** Smoothly animate box back to original position if drop is invalid.

**Why not:** We prevent invalid drops with visual feedback (red borders), but we don't reject drops. Box moves, then shows error.

**Alternative approach:** Use `dropTargetStyle` to visually reject invalid zones during drag.

**Workaround:** Users see red border and error message, can drag again to fix.

## Lessons Learned

### 1. Don't Reinvent Drag-and-Drop

Drag-and-drop is a solved problem. Use a library. The time saved is enormous.

**Key insight:** Our core value is inventory management logic, not drag-and-drop mechanics. Focus on what makes our app unique, delegate the rest.

### 2. Local State for Preview Workflows

For any "preview-then-commit" workflow, use local state:

```typescript
// Pattern:
const original = snapshot(globalState);
let working = $state(deepCopy(globalState));

// User modifies working copy...

// On confirm:
commitChanges(working, globalState);

// On cancel:
discard(working);
```

This pattern works for:

- Drag-and-drop rearrangement
- Form editing (drafts)
- Bulk operations (select multiple, apply action)
- Undo/redo systems

### 3. Real-Time Validation Prevents Frustration

Showing errors immediately (not at the end) is worth the extra work:

```typescript
// BAD: Validate only on submit
function handleConfirm() {
  const errors = validate(data);
  if (errors) alert('Invalid!'); // Too late!
}

// GOOD: Validate in real-time
function handleChange() {
  const errors = validate(data);
  showErrors(errors); // User sees problems immediately
}
```

Users fix errors as they go, not at the end.

### 4. Test Logic, Not Mechanics

For complex UI interactions (drag-and-drop, animations), test the outcomes, not the mechanics:

**Don't test:** Exact mouse coordinates, drag timing, intermediate animation frames

**Do test:** Final state after drag, validation errors, navigation flow

Focus on correctness, not simulation.

### 5. Mobile is Not an Afterthought

Designing for mobile first (or at least early) prevents painful retrofits:

- Touch target sizes (minimum 44x44px)
- Responsive layouts (grid, flexbox)
- Touch events (not just mouse)
- No hover states (use :active instead)

BroteinBuddy is mobile-first, so we designed with touch in mind from the start.

## What You Should Learn From This

### Patterns Worth Remembering

#### 1. Three-State Preview Pattern

```typescript
const original = snapshot(state); // Immutable
let working = $state(copy(state)); // Mutable preview
// ... user edits working ...
// On confirm: commit(working → state)
// On cancel: discard(working)
```

Use for any multi-step editing workflow.

#### 2. Real-Time Validation with Visual Feedback

```typescript
let errors = $state(new Map());

function validate() {
  errors.clear();
  for (const item of items) {
    if (!isValid(item)) {
      errors.set(item.id, "Error message");
    }
  }
  errors = new Map(errors); // Trigger reactivity
}

// In template:
class:invalid={errors.has(item.id)}
```

Immediate feedback prevents late-stage errors.

#### 3. Batch Updates for Atomic Changes

```typescript
// Collect all changes
const changes = [];
for (const item of items) {
  if (hasChanged(item)) {
    changes.push(item);
  }
}

// Apply all at once
for (const change of changes) {
  applyChange(change);
}
```

All-or-nothing updates prevent partial state.

#### 4. Library Evaluation Criteria

When choosing a library, ask:

- Does it solve our specific use case?
- Is it actively maintained?
- Does it handle edge cases (mobile, accessibility)?
- What's the bundle size?
- How hard is it to learn?
- Can we replace it later if needed?

Don't over-engineer - if a library fits, use it.

### When to Use Drag-and-Drop

**Good use cases:**

- Reordering lists (priorities, sequences)
- Moving items between containers (Kanban boards)
- Organizing hierarchies (file trees)
- Visual editing (layout builders)

**Bad use cases:**

- Data input (forms)
- Navigation (links)
- Simple sorting (dropdowns are easier)
- Complex constraints (too many invalid states)

Drag-and-drop should feel intuitive, not require a tutorial.

3. **Real-time validation** - Show errors immediately
